Why this exists

Bad data takes too long to trace back to its cause

Asking “why” five times

  1. Incidents with bad data take too long to detect and fix. Why?
  2. Nobody can see which upstream change touched the broken field. Why?
  3. Our lineage stops at tables and services. It does not follow individual fields. Why?
  4. Field-to-field logic lives in service code (Go, C#, Kotlin and others) and at runtime, where catalog tools don't look. Why?
  5. Those tools parse SQL and warehouse logs. No vendor covers service code, streams and warehouses at field level (vendor assessment, doc 05).
  6. So we build collectors for code and runtime, and grade them against a system whose truth we already know.

What it must do

O1 · BaselineMap every fieldWhere each field comes from and where it goes, across services, topics and tables.
O2 · IncrementalStay currentUpdate the map when code, config or flags change, without a full rescan.
O3 · ImpactWarn before mergeShow what a code change breaks downstream while it is still a pull request.
O4 · Detect and resolveFind the cause fastFrom a failing check, walk upstream to the change that caused it.

What acting costs

  • Your time at four gates: spec, change, oracle and release (D20).
  • Agent cost, tracked per merged change and reviewed weekly. There is no cap; time limits stop runaway runs (D21).
  • A Neptune and Kafka stage environment in AWS.
  • From slice 2 on, owners' time to answer reconciliation queues.

What not acting costs

  • Breaking field changes are found after merge. In the demo, retyping one field (C1) broke every reader of the zip code.
  • Sensitive-data paths are found by audit, not by design. One flag sent card numbers into telemetry with no code change (C7).
  • Incidents start from a symptom with no path to the cause. In the run, lineage walked 9 dependencies to the right service automatically.
  • A catalog bought later would still miss service code.
The real use case

An online shop's order, from checkout to the finance tables

The OpenTelemetry Demo is an open-source shop (Apache-2.0) maintained by the OpenTelemetry project. It runs a dozen services in ten languages. When a shopper checks out, the order passes through payment and shipping calls, a Kafka topic and two consumers, and lands in Postgres. That mirrors the shape of our estate, and its truth is in public code we can cite line by line. Pick a scenario to see what lineage has to answer.

What we proved

We ran the shop twice and broke it ten different ways

On 27 November the demo ran here twice with 23 containers and simulated shoppers. The first run (14:06 to 14:39 UTC) switched on a flag that changes where card data goes, then made payments fail half the time. The second (16:54 to 18:43 UTC) injected nine more incidents, from a stopped consumer to a decoy and a silent failure. The prototypes scored what lineage saw against the golden graph, with every threshold fixed before the runs.

O1 · BaselineProven
Every connection we saw was expected

In both runs, 18 of 18 observed connections are in the golden graph, including all 13 the demo's own tests assert. Runtime confirmed all 17 finance columns the code says are written.

O2 · IncrementalOne case
A flag changed lineage, and we saw it

13 seconds after the flag went on, masked card numbers appeared in telemetry. No CVV or raw email ever left. The edges stopped when the flag went off.

O3 · ImpactNot run yet
Real changes are ready to replay

Thirteen changes are prepared with their expected readers and gate result: six from the demo's history, the flag flip, and six written here. The impact engine itself is wave 3.

O4 · Detect and resolve8 of 10
Caught fast, right cause first

8 of 10 incidents were caught within 2 minutes, and the true cause ranked first in all 8. The two misses fired no check at all: a silent cart failure and a traffic flood. That puts IR-5 at 80% against a 90% bar.

EngineersWhat else the run settled

  • Kafka is joined on the topic, not on trace links. The producer and consumer spans live in separate traces, as upstream warned. The topic offset (30) matched the 30 rows in accounting."order" at 14:17.
  • Envoy sees only the front door. Checkout reaches its callees directly, by container IP (172.18.0.x). The resolver never treats an IP as an identity, and 3,103 IP references stayed unresolved on purpose (D31).
  • Database spans give column-level writes. Accounting's batched EF Core insert splits into three tables and 17 columns with SQLGlot. Its shared login is never used for attribution (D27).
  • Runtime misses what code finds. Six services read a feature flag but emit no span when they do. Three of them are behind incidents I2 to I4, so which service reads which flag comes from code (D29).
  • Fixed during the run: one golden edge was missing (frontend → currency), and the SQL parser broke on quoted and batched statements. PyYAML read the key on: as true. Rate checks raised a false alarm at six events per window.
  • The second run taught five rules (D38). One flag has a targeting rule, so changing its default injected nothing until it was flipped through the rule. A silent failure fires no check, so it counts as a miss and raises a coverage finding. A cause that comes from callers is out of the dependency walk's reach. The hidden test set needs changes made close together. The lock behind I3 is visible as a LOCK TABLE statement in database spans.

How it gets built

Six waves, each proving one thing before the next starts

Agents buildAgents work from a spec pack and write code, tests and fixtures. In waves 0 and 1 a person reads every change (autonomy level 2). Proven extractors then move to approval by exception (level 3).
A harness gradesEvery change is scored against the golden graph, plus holdout scenarios the builders never see. Scores, not opinions, decide what merges.
