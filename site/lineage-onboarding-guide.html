Lineage onboarding guide

How an application flow gets its lineage captured and managed: where to start, what each step asks of your team, and what you get back. Check your flow first; the guide below explains each step.

You do three thingsOnboard each repository with one change, name owners and tiers, and write checks and tier 1 contracts.
The platform does the restReads your code on every pull request and merge, collects runtime evidence centrally, and keeps a versioned field-level graph.
You get backImpact reports on pull requests, an API for "what breaks if I change this", and alerts that arrive with the cause ranked.

Seven steps from intake to steady state

The entry points

How a flow gets in, what is collected, and where you use it

Getting in

  • One change per repository: a .lineage.yaml file and the lineage-ci step in CI.
  • Owners and tiers in the catalog, one line per service and dataset.
  • Contracts for tier 1 data: fields, types, compatibility, forbidden fields.
  • Checks on what matters: rates, errors, lag, latency, data quality.

What the platform collects

  • OpenTelemetry traces with a service.name matching .lineage.yaml.
  • Message spans that name their topic, joined on the topic name.
  • Database spans or warehouse query history (Snowflake, Databricks) for column reads and writes.
  • OpenLineage from Spark, dbt, Flink and Feast, switched on centrally.
  • Change events: deploys, flag changes, merges.

Where you use it

  • Pull requests: an impact report with readers, owners and a gate result.
  • /impact API and agent tool: ask before a pull request exists.
  • Alerts: the path upstream, ranked causes and blast radius.
  • /upstream, /diff, /explain: history, changes and evidence.
  • Owner queue: edges to confirm or dispute.

Copy and adapt

Three files to start from

.lineage.yaml

version: 1
repository: payments-api
environment: prod
owner: team-payments
services:
  - {name: checkout, path: src/checkout,
     language: go, extractors: [go-assembly]}
schemas:
  - {kind: protobuf, path: proto/orders.proto}
build: {reuse_artifacts: true, max_minutes: 5}

Service names must equal the service.name your services emit at runtime.

CI step, any CI system

# on pull requests
lineage-ci validate
lineage-ci scan --stage proposed \
  --commit $SHA --base $BASE_SHA --pr $PR_NUMBER
lineage-ci impact --pr $PR_NUMBER --comment

# on merges to the default branch
lineage-ci scan --stage merged --commit $SHA

A GitHub Action wraps the same commands. The runner arrives in wave 1 (WP-18).

A check

- id: orders-rate
  node: kafka://prod/orders
  metric: kafka.partition.current_offset
  where: {topic: orders}
  fail_if: rate_ratio < 0.5 or rate_ratio > 3.0
  min_events: 20

Set thresholds before any incident and never tune them on one.

Questions teams ask

Before you start

Do we need a golden graph?

Only to certify the flow. Covered flows rely on the scoring, the owner queue and sampled audits.

Our CI is not GitHub.

The lineage-ci CLI is the product. Run the same commands in any CI system; the GitHub Action only wraps them.

Will this slow our builds or services?

A pull request scan stays within 5 minutes at p95 and reuses what your build already produces. Runtime collection reads exported telemetry and never sits in a request path.

A service is written in a language nobody supports.

It shows as a gap with a reason, its runtime edges still appear, and a model can propose candidate edges that never become confirmed on their own. Ask for an extractor; one serves every flow that uses that language.

Who owns an edge?

The owner of the dataset or service it writes to, as recorded in the catalog. That owner receives the queue items and review requests.

What leaves our systems?

Metadata only. Source code goes to a model only for units no rule can read, and only through the approved endpoint in the platform account.
