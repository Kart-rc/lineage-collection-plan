What the outcome evidence is worth

No independently measured result was found for any of the four objectives. The detection and resolution times that are widely quoted come from vendor-funded surveys of 2022 and 2023. They size the problem. They do not show a tool's effect. The plan's own Phase 0 baseline is the number to beat.

One pipeline, four flows

The four objectives are four paths through the same components. What separates them is the trigger and how fast the answer is needed. Pick a flow to trace it on PR #482, the rename of merchant_category_code to mcc.

    What changes in the graph model

    The plan already names fields with a # suffix and has a DERIVES edge. Element level needs three additions.

    Each field mapping is its own edge

    Today a dataset edge carries a list of columns. In envelope v2 every mapping has its own key, evidence and confidence, because one column of a model can be confirmed at runtime while its neighbour is static only.

    <from URN>#<field> | DERIVES | <to URN>#<field>

    Gaps are stated, not hidden

    Dynamic SQL, an untyped UDF or DataStream code cannot be resolved to fields. The extractor emits a dataset-level edge marked opaque with a reason, and impact reports say "field-level unknown through this job" instead of ending the path quietly.

    ClassSubtypeOn the sliceHow impact treats it
    DirectIdentityraw.card_auth#mcc to fct_card_auth#mcc. A rename is identity with two names.Value impact. A removed or retyped source breaks the target.
    DirectTransformationauth_ts cast to auth_dateValue impact. A changed expression is a logic change.
    DirectAggregationfct_card_auth#declined summed over 7 days into mcc_decline_7dValue impact. A changed window is a logic change.
    IndirectJoin, filter, group by, sort, window, conditionalstatus = 'AUTH' filters the fact table; mcc is the feature's group-by keyRow-set impact. Stored once per target dataset, reported separately, never blocks alone.

    The classes and subtypes are the ones in the OpenLineage column lineage facet (spec 1-2-0), so runtime events map without translation. Its docs warn that fanning indirect dependencies out to every column produces "almost a cartesian product", which is why they are stored per dataset.

    What keeps it incremental

    Three hashes decide whether a unit is re-read

    • Content hash: the unit's own normalized source.
    • Input schema hash: the schema versions of everything it reads. This catches a SELECT * that changes meaning when an upstream column is added.
    • Extractor version: a parser upgrade.

    If none changed, the unit is skipped.

    Two rules for evidence

    • Static evidence is owned by its unit. A re-read replaces the unit's whole evidence set, so a deleted column leaves the graph at the next merge, not the next rescan.
    • Runtime evidence only adds. It leaves by decay after 30 days unseen, and the edge turns dormant.

    Two clocks on every edge

    Valid time is when the flow was true. Recorded time is when the graph learned it. RCA asks the first question: what fed this column at 02:42? An audit asks the second: what did the graph tell the PR bot when it passed the change?

    One stream of differences

    Every material edge change is published to lineage.changes. The PR report, catalog projections and RCA all read the same diff instead of comparing snapshots.

    People own intent and the oracle. Agents build against it.

    An AI factory treats the specification as the durable asset and code as something built from it. A harness, not a person reading the diff, is the first check on correctness. People stay accountable at four gates.

    The software sense of the term took shape in early 2026: Dan Shapiro's five levels of AI-assisted programming, whose top level is the "dark factory"; StrongDM's Software Factory, with its rule that code is neither written nor reviewed by people; and OpenAI's account of a product built by agents under the line "Humans steer. Agents execute." This build is the light version. Agents execute, people approve, and autonomy widens only on measured results.

    What the build borrows

    • Holdout scenarios and a twin of external systems, from StrongDM's factory.
    • A constitution, then spec, plan and tasks, from GitHub Spec Kit.
    • Approval after each stage and an audit trail per change, from the AWS AI-DLC workflows, which list 33 stages and a 134-event audit trail.
    • A near-perfect verifier before any scale, from Anthropic's account of a C compiler built by 16 parallel agents: about 100,000 lines for just under $20,000, with the warning that a weak verifier makes the agents solve the wrong problem.

    Why the gates stay

    • The no-review variant is advocated, not demonstrated. Its results are self-reported, and one detailed practitioner account describes a failed attempt and codebases that struggle after three to six months.
    • DORA's 2025 report finds AI raises delivery throughput and also raises instability.
    • METR's 2025 trial found experienced developers 19% slower with AI tools; its 2026 update is inconclusive.
    • Published cost runs from about $13 per developer-day for typical use to a $1,000 per engineer-day benchmark.
    • No regulator or card scheme was found endorsing development without human review.

    The oracle comes first

    Factory throughput is limited by verification, not by generation. Lineage is unusual in having a ground truth a machine can check: an edge exists or it does not, and a past change either broke a consumer or it did not. Four things turn that into a test.

    Golden graph

    About 15 service and dataset edges and 40 field edges for the slice, signed by the owners in Phase 0. The harness reports precision and recall per edge type and per hop.

    Change replay

    The last ten schema and logic changes on the slice, each with base commit, head commit and the consumers that actually broke. Scores change impact.

    Incident replay

    Six months of incidents with the failing check, the change timeline and the true cause. Scores root-cause ranking.

    Twin of the slice

    Kafka with a schema registry, a Flink mini cluster, a local SQL engine with the dbt project, a feature store, a model registry and a stub Git provider, started by one command. Agents never touch production.

    About two thirds of the scenarios are visible to the builder. The rest are holdout, split by scenario family and run by the harness in a separate job. The builder gets back a pass rate and failure categories, never the scenario text. Property tests cover the core (merge is idempotent, replay is deterministic) and metamorphic tests cover the extractors (reformatting a query must not change its edges).

    Work packages

    Each one is sized for a single agent in a single sandbox against a single oracle. The level is where it starts on the autonomy ladder below.

    2. L2Agent writes, person reads every changePerson mergesCore semantics, the harness, infrastructure, anything that can block or pause a team. Where the build starts.
    3. L3Agent writes, second agent reviewsPerson reviews exceptions and a weekly sample, approves a batchExtractors and services with a strong oracle. Where wave 2 runs once wave 1 holds.
    4. L4Agent writes, merges on greenPerson reviews scores weeklyExtractor rule additions and regression fixtures, once earned

    Up one level after five consecutive changes at or above the holdout threshold with no escaped defect and a clean weekly sample. Down one level on any escaped defect that reached stage or production, or any attempt to edit a protected path.

    What six people do instead of typing extractors

    • Platform lead (1): intent, G1 and G4, the autonomy ladder, the weekly factory review.
    • Factory engineers (2): the twin, the harness, the pipeline, sandboxes and budgets.
    • Spec owners (3): requirements, scenarios and G2 for the streaming, analytics and ML hops; golden graph sessions with slice owners.
    • Slice owners (about 6 teams): sign the golden graph and work the reconciliation queue.

    Controls for a card-payments estate

    • A named person approves every protected merge and every release.
    • Builder agent, reviewer agent and approver are always distinct.
    • Each run links spec version, work package, transcript, commit, scores and approval. That chain is the change record.
    • Sandboxes have no production route, no production secrets and an egress allow-list.
    • Only code and schemas reach a model, through the approved endpoint. Never production data.

    The system, before the solution

    Three loops run at once: lineage, the factory, and trust. They share one object, the golden graph with its scenario corpus. It is the factory's test oracle, the product's accuracy yardstick and the thing owners sign.

    LoopFlows inFlows out
    LineageCode and pull requests, schema versions, table DDL, job runs, query history, DQ and contract results, deploysImpact reports and gate decisions, lineage diffs, ranked causes, remediation order, accuracy numbers, catalog projections
    FactoryIntent, specs, scenarios, golden fixtures, model tokens, reviewer and approver timeMerged changes with evidence, scenario pass rates, new scenarios from escaped defects, cost per change
    TrustOwner confirmations, "this is wrong" feedback, reconciliation findingsPublished precision and recall; how strict each gate is allowed to be

    Where the constraint moves. In a conventional build it is engineering hours spent writing collectors. In the factory it moves to four places: how fast people can author the oracle, how much owner time the golden graph gets, how fast real evidence accrues, and how many changes the gates can clear. The third cannot be compressed. A 30-day decay window takes 30 days. The factory shortens the parts of the plan bound by building, not the parts bound by evidence.

    Five whys: why a factory for this system

    1. Why not staff it conventionally? The first slice needs about 108 engineer-weeks, and the long pole is the breadth of extractors, not one hard algorithm.
    2. Why is breadth the long pole? Element lineage needs an extractor per language and framework, each with a long tail of constructs.
    3. Why does that suit agents? Each extractor is a bounded unit with a crisp contract: given this code and these schemas, emit these edges.
    4. Why does a crisp contract matter? Throughput is limited by verification. Without a machine-checkable oracle a person must read every line and the gain is gone.
    5. Root: lineage has an objective, replayable ground truth. That is rare. So the first investment is the oracle, not the code.

    Hidden assumptions

    1. Element means field, column or attribute. Row-level provenance is out.
    2. "AI factory" means spec-driven delivery by agents with people at the gates, not a GPU data center.
    3. Owners will author and maintain the golden graph. Without it there is no oracle.
    4. Policy allows AI-written code when a named person approves protected changes and releases. If every change needs a human reviewer, the ladder stops at level 2.
    5. Code and schemas may go to a model through an approved endpoint. Production data never does.
    6. Agents never hold production credentials.
    7. Element lineage is needed on tier 1 and contract-bearing assets, not everywhere.
    8. The token budget is funded and tracked per merged change.
    9. Vendor facts are as read in November 2026 and move fast.

    What to keep in proportion

    • Prevention is one part of the answer. One vendor's analysis of 1,000 incident investigations put code changes at about a tenth of root causes; an earlier statement from the same vendor said about a third. Either way most incidents will not be stopped in a pull request, so detection and root-cause ranking carry as much of the outcome as the gate does.
    • Two hops stay probable. Field edges through service code and Flink come from static analysis and declared mappings. They are verified by owners for tier 1 fields and reported as gaps elsewhere.
    • The research has limits. Most vendor documentation hosts were blocked during the research and the search allowance was capped. Open-source and standards claims were read at the source. Many vendor claims rest on search summaries. Re-read a vendor's own pages before a contract or an ADR change.
    • Accuracy targets are local. No independent precision or recall for column lineage was found, and no independent measurement of lineage's effect on detection or resolution time. The golden graph and the Phase 0 baseline are the only yardsticks that count.
