# Build decisions

Nov 27, 2026 · Turns the open questions in [doc 06](06-element-lineage-factory-spec.md) and the plan's week-1 list into decisions, grounded in the real reference slice in [doc 07](07-reference-slice-otel-demo.md).

## On a page

The readiness review on 26 November found the build blocked on thirteen open decisions, no oracle, untested assumptions and an illustrative slice nobody could run. With a real system to test against, and your answers on 27 November to the calls that were yours, every decision the build needs is now made.

| Status | Count | Meaning |
| --- | --- | --- |
| Decided on evidence | 25 | Settled from the reference slice, a capture run or the research. Each is reversible, and the "revisit if" column says when |
| Decided by you | 7 | D12, D13 and D18 to D22, answered on 27 November |
| Still open, not blocking | 1 | Which of your data products becomes slice 2 (part of D22). Pick it during wave 1 |

**What this unblocks.** Wave 0 can start now. The oracle exists as fixtures, the twin runs in this sandbox, every component has a work package and a test ([doc 09](09-component-build-sheet.md)), and the policy, people and money questions are answered.

**What changed in the plan.** Four decisions change the plan, not only fill it in:

- **D7.** Phase 1 builds service edges from traces, not gateway logs.
- **D8.** Kafka hops are joined on the topic, not on trace links.
- **D23.** The twin runs a separate lineage platform beside the demo, with Neo4j standing in for Neptune.
- **D30.** Some lineage exists only while a flag is on. Edges carry a condition, and a flag change event alone can change the graph.

The first two come from reading the demo's code and its maintainers' own notes. They, and D30, were confirmed by the capture run on 27 November (doc 09).

## Collection

| Id | Decision | Evidence | Revisit if |
| --- | --- | --- | --- |
| D7 | **Service-to-service edges come from traces.** The collector's `servicegraph` connector and a parent-child span walk produce `CALLS` edges at weight 0.90. Gateway and mesh logs are used only for traffic entering the estate, and as a mesh source where one exists. **This changes Phase 1 of the plan** | Envoy fronts only the web tier and identifies callers by remote address; checkout's calls to payment, cart and shipping never pass it. The 13 edges the demo's own tests assert are found by exactly this parent-child walk over live traces. **Confirmed by the capture on 27 November:** the walk found 18 data-flow edges, all of them golden (precision 1.00), including all 13 upstream-asserted ones. The two golden edges not seen, `frontend → currency` and `frontend → shipping`, are reached only from browser pages the load generator does not open. Checkout addresses its callees by container IP, so an address is never an identity (D31) | A service mesh with workload identity is in place; then mesh logs join traces as a second source |
| D8 | **Kafka hops join on the topic.** The topic is a node. `PRODUCES` comes from producer spans' destination name; `CONSUMES` from consumer spans and the consumer group in broker metrics. Trace parent-child links are not relied on | The demo's maintainers exclude the two Kafka edges from their trace test because producer and consumer spans "live in separate traces" ([services.py:96](https://github.com/open-telemetry/opentelemetry-demo/blob/3.1.0/test/telemetry/services.py#L96)). **Confirmed by the capture:** checkout's producer spans and the consumer spans of accounting and fraud-detection all name `orders`, and the broker metrics list both consumer groups on it. At 14:17 UTC the topic's offset, 30, matched the 30 rows in `accounting."order"` | Consumers continue the trace context checkout already puts in message headers; then add trace links as extra evidence |
| D9 | **Each kind of field truth has one source.** Topic and call fields from compiled protobuf descriptors. Table columns from the ORM mappings and DDL. Field-to-field assembly inside a service from the code scanner. Runtime column use in Postgres from `pg_stat_statements`, parsed with SQLGlot | In the slice, these four are where the 36 field edges actually live. No registry or catalog holds the service-code mappings | A schema registry is adopted for the topics; then it replaces the descriptor source for topic fields |
| D10 | **Extractors are built in this order:** protobuf descriptors; the C# ORM mapping in accounting (17 edges); the Go assembly in checkout (18 edges, including the card pass-through); Postgres runtime evidence; then the remaining languages. Flink, dbt and feature extractors start with the complement in D2 | Ordered by how many golden field edges each unlocks and how mechanical the mapping is: the accounting mapping is one property per line | The vendor trial in D17 covers one of these hops well enough to buy it |
| D11 | **The telemetry pipeline is a destination, and must-not-flow checks cover it.** Exporters and backends are datasets; span and log attributes that carry data are fields | With `emitRawPii` on, checkout writes the card number and CVV into span attributes and the collector masks them. In a card estate that is a PCI-relevant flow. **Seen in the twin on 27 November:** 13 seconds after the flag went on, checkout spans arrived with `user.hash` and a card number masked to its last four digits, and payment spans with the masked number. No CVV and no email reached the export | Never |

## Closing the component gaps

D23 to D28 came out of the component review on 27 November ([doc 09](09-component-build-sheet.md)); D29 to D32 out of the capture run the same day.

| Id | Decision | Evidence | Revisit if |
| --- | --- | --- | --- |
| D23 | **The twin runs a separate lineage platform beside the demo:** its own single-node Kafka for `lineage.evidence`, Neo4j Community as the Neptune stand-in, Postgres for aliases and queues, and Parquet files for the raw archive. Nothing of the platform runs inside the demo's own containers | Sharing the demo's Kafka or Postgres would change the lag and load the checks measure. Neo4j and Neptune share Bolt and openCypher, so WP-13's writer is the same code in both | A Neptune-only feature is needed; then add a nightly run of the same tests against a stage Neptune instance, which WP-13 already requires |
| D24 | **Owners and tiers for the reference slice come from `fixtures/otel-demo-3.1.0/catalog.yaml`.** Tiers are the demo's own `service.criticality` values; owners are illustrative teams | The demo's CODEOWNERS assigns everything to one team, so routing and sign-off could not be tested without invented owners. The criticality labels are real | Slice 2 brings real owners from your service catalog |
| D25 | **Contracts for `orders` and the accounting tables are fixtures** derived from `demo.proto` and `init.sql`, with consumers generated from the golden graph and card fields forbidden | The contract gate had nothing to enforce on the slice | The demo changes either schema; the contracts change through G3 |
| D26 | **A check runner (WP-39) evaluates five checks in `fixtures/otel-demo-3.1.0/checks.yaml`** every minute over a two-minute window and publishes failures as quality assertions: topic rate, fraud-detection lag, accounting row rate, checkout errors, catalog latency | Root-cause analysis needs a failing check to start from, and the demo has none. Every metric and label the checks read was seen in the capture run. The accounting check reads the collector's per-table insert counter instead of polling `count(*)`. **Tuned on the first run:** at about three orders a minute a two-minute rate window holds six events, and the first evaluation raised a false alarm one second after an unrelated change. Rate checks now widen their window until the baseline expects 20 events (about 7 minutes here); the next evaluation had no false alarms over 10 minutes of baseline. Prototype: `code/run_checks.py` | A data quality tool is adopted; its results replace the runner's through the same envelope |
| D27 | **Postgres access history is attributed by table and statement kind, not by login,** and shared logins are reported as a hygiene finding | In the demo, accounting and product-catalog both connect as `astronomy_user`. Their tables do not overlap, so attribution by table works here; it will not in general. **The capture adds a better source:** database client spans carry the service name and the full statement. SQLGlot splits accounting's batched insert into its three tables and finds all 17 golden accounting columns, and product-catalog's eight columns read from `catalog.products`. `pg_stat_statements` stays for clients without spans | Slice 2: require one login, or an `application_name`, per service as part of onboarding |
| D29 | **Feature flags are nodes, joined to services by `CONFIGURES` edges read from code.** A flag change event (`flag://otel-demo/<key>`) reaches the graph through them, which is how RCA links a flip to the services it changed | 20 flag reads across 12 services, each cited to a line. Only 6 of the 12 emit a span when they evaluate a flag; checkout, product-catalog and email do not, and those are the services behind I2, I3 and I4. Runtime alone would have missed exactly the incidents that matter | flagd or OpenFeature hooks emit evaluation events carrying the service; then they become a second source |
| D30 | **An edge that exists only under a flag carries a `condition` and the state `latent` while the condition is false.** It moves to `active` on the flag change event, not on the next code scan. Must-not-flow checks walk latent edges too, so a dangerous path is visible before anyone switches it on | `emitRawPii` changes eight edges with no code change: five copies of the card number, CVV and email into span attributes, and three collector edges that hash and mask them on the way out. In the twin the masked values appeared 13 seconds after the flip (change C7) | Conditional edges multiply; then record conditions only for flags whose code path writes data |
| D31 | **The resolver never aliases an IP address.** Calls resolve by the service name on the callee's server span; addresses only as the `host:port` configured in the demo's `.env`; Envoy ingress by upstream cluster. The alias table is `fixtures/otel-demo-3.1.0/aliases.json` | Checkout reaches cart, currency, payment and product-catalog as `172.18.0.x`, and Envoy logs its upstream as an IP; both change on restart. The alias table resolves all 55 distinct names in the capture's traces, logs and metrics, and leaves 3,103 references by IP unresolved on purpose | A callee has no spans and is reachable only by IP; then add the orchestrator's IP-to-workload map as an alias kind with a validity window |
| D32 | **Root-cause narrowing starts at the first failing check, walks what that node depends on, keeps the callee where failing calls stop, and ranks change events that touch it, nearest in time first** | In I1 the first failure was checkout errors. Failing calls stopped at payment, and `paymentFailure` ranked first. `emitRawPii` also touches payment and ranked second, separated only by being 45 seconds earlier. Lineage narrowed the field to the right service; time decided between two flags on it | The holdout incidents show time picking wrong; then add whether a change moved away from the shipped default, and error messages on the failing spans |
| D28 | **New and re-scoped work packages:** WP-16 reconciler, WP-17 owner and tier overlay, WP-19 service edge builder, WP-39 check runner. WP-13 targets Neptune over Bolt; WP-22 reads PyFlink code and the declared feature registry; WP-24 reads ORM writes, C# first; WP-26 reads `pg_stat_statements` first | Each closes a gap in doc 09: a component with no work package, or one aimed at a technology the slice does not have | Never; later slices add work packages the same way |
