# No vendor delivers end-to-end field lineage

Nov 26, 2026 · Vendor assessment for element-level lineage, judged against baseline, incremental, change-impact and detect-and-resolve objectives. The design it feeds is the [build spec](06-element-lineage-factory-spec.md). Working notes, one file per research thread, are in [`research_notes/`](../research_notes/).

No vendor in any of the five vendor categories assessed documents element-level lineage across the buyer's full path from microservice through Kafka and Flink to the dbt warehouse, the feature store and the model: column lineage is well evidenced only for SQL warehouses, dbt and Spark, and every other hop depends on events, declared mappings or static analysis that the buyer must supply. Against the four objectives the market is uneven: baseline lineage (O1) is mature inside SQL engines; incremental lineage with queryable history (O2) is rare; pull-request impact analysis (O3) ships almost only for dbt projects, with Foundational and Gable alone claiming to analyse application code before merge; and every vendor asserts lineage-driven root-cause analysis (O4) while no independently measured reduction in time to detect or resolve was found. The streaming hop is the hardest gap and the best evidenced: OpenLineage's own Flink 2 documentation, read at source, says Flink's lineage interfaces "do not provide column level lineage information". Since late 2024 most independent lineage specialists have been absorbed by platform vendors, public pricing is thin, and published outcome figures are vendor-funded. For the build itself, the evidence supports a "light" AI factory (spec-anchored, contract-first, verified against holdouts the implementing agent cannot see, with named human approvers at plan, merge and release) and does not support a lights-off one in a card-payments estate. Together these findings back a decision to own a thin lineage core (identity, evidence log, versioned and classed edges) and adopt parsers, collectors, platform lineage and catalogs around it. One caveat governs everything below: **the session's network policy blocked most vendor documentation hosts and the web-search allowance was capped, so most vendor-specific, pricing and analyst claims rest on search summaries** and need re-reading at source before procurement or an architecture decision.

## Most vendor claims rest on search summaries, and each citation says which

The documentation sites of IBM, Collibra, Solidatus, AWS, Databricks, Snowflake, Google Cloud, Confluent, Microsoft, Monte Carlo, Datafold and Atlan could not be opened, and neither could OpenAI, StrongDM, martinfowler.com, METR, DORA, arXiv or Meta's engineering blog. A third-party page seen through a search summary is weaker than a vendor page seen the same way, and the text says "third-party" where that applies. That rule, together with preferring a primary read over a search summary, changed four findings: Monte Carlo now has a pull-request check where an earlier note recorded none, Datafold derives lineage from warehouse query logs and not from the dbt manifest, Marquez's last release listed in its own README dates from October 2024, and Google's lineage API does expose column-level search. The closing section lists what to re-verify.

## Six mechanism families, each blind at a different boundary

Products differ less by brand than by how they obtain a column-to-column edge. Six families are on sale, and two more exist only in research or in-house systems.

| Family | How it produces element-level lineage | Who relies on it | Available before merge? | Characteristic blind spot |
|---|---|---|---|---|
| Static scanners of deployed code and metadata | A scanner per technology parses SQL, stored procedures, ETL job definitions, BI reports and, for some, COBOL and JCL into column-level flows | IBM Manta, Rocket, Orion, Octopai, Informatica, Quest, Collibra, Ataccama | No | Dynamic SQL, cursors, encrypted definitions; coverage is scanner by scanner |
| Query-log and access-history mining | SQL observed in warehouse query history is parsed into column edges | Alation, Atlan, Monte Carlo, Datadog, Datafold, Elementary | No | Sees only what ran inside a retention window; procedural logic; non-SQL writes |
| Platform-native lineage | The engine records lineage for its own queries and exposes it through system tables or an API | Databricks Unity Catalog, Snowflake Horizon, Google Knowledge Catalog, AWS SageMaker Catalog; re-read by Collibra, Octopai, Alation, Precisely and SYNQ | No | Stops at the platform edge; UDFs; retention limits |
| Runtime events from engine plans (OpenLineage) | An integration reads the engine's resolved plan (Spark, Trino, Hive) or parses SQL text (Airflow, dbt) and attaches a column-lineage facet to each run event | OpenLineage producers; consumed by IBM, Collibra, Alation, Atlan, Solidatus, Ataccama, Precisely, Datadog, SYNQ, Snowflake and AWS | No | Flink and Kafka give dataset level only; column detail arrives only if the producer emits the facet |
| Static analysis of code at rest in git | SQL models are parsed to a syntax tree and qualified against schemas; application code is traced by program analysis | dbt, SQLMesh, Recce, Paradime; Foundational and Gable for application code | Yes | Python models, `SELECT *` over unknown schemas, SQL the parser cannot type; shows what could run, not what does |
| Declared or curated lineage | People, contracts or an assistant assert the mapping | Solidatus, Zeenea, IBM Custom Lineage Mappings, SYNQ custom entities, Databricks external lineage | Yes, if kept with the code | As good as its upkeep |

The first distinction that matters is between observed and potential lineage. Query-history lineage is observed lineage with a horizon. Monte Carlo's agent toolkit states: "Column lineage expires after 10 days" ([Monte Carlo push-ingestion skill](https://github.com/monte-carlo-data/mc-agent-toolkit/blob/main/skills/push-ingestion/SKILL.md); P), and Datadog "derives relationships from query history and job runs within this window", a window the user selects ([Datadog lineage docs](https://docs.datadoghq.com/data_observability/lineage/); P). A dependency exercised only at month-end can be missing on the day a change is assessed. Code-derived lineage is the mirror image. Foundational, which sells it, calls it "potential lineage — a view of what could happen when the code is executed" and argues that runtime capture misses rarely executed pipelines and rarely triggered code paths ([OpenLineage blog: lineage from code](https://github.com/OpenLineage/OpenLineage/blob/main/website/blog/lineage-from-code/index.mdx); P). dbt documents that parsing fails on constructs such as JSON unpacking and lateral joins and that for Python models "it's not possible to parse and determine the lineage" ([dbt column-level lineage](https://github.com/dbt-labs/docs.getdbt.com/blob/current/website/docs/docs/explore/column-level-lineage.md); C). SQLMesh loses upstream column lineage on `SELECT *` from an external source unless an external model supplies the schema ([SQLMesh SQL models](https://github.com/TobikoData/sqlmesh/blob/main/docs/concepts/models/sql_models.md); P).

The second distinction is that "column lineage" does not mean the same thing in every product. OpenLineage's facet separates DIRECT transformations (identity, transformation, aggregation) from INDIRECT ones (join, group-by, filter, sort, window, conditional), where the output "is impacted by the value of `inputField` column, but it's not derived from it" ([OpenLineage column lineage facet](https://github.com/OpenLineage/OpenLineage/blob/main/website/docs/spec/facets/dataset-facets/column_lineage_facet.md); C). dbt's lineage "doesn't reflect other usage like joins and filters" ([dbt column-level lineage](https://github.com/dbt-labs/docs.getdbt.com/blob/current/website/docs/docs/explore/column-level-lineage.md); C). DataHub's parser does "not consider columns referenced in filtering or organizational clauses such as `WHERE`, `GROUP BY`, `ORDER BY`, `JOIN`, `HAVING`, or `PARTITION BY` to be part of lineage" ([DataHub SQL parsing](https://github.com/datahub-project/datahub/blob/master/docs/lineage/sql_parsing.md); P). Recce takes the opposite position and records which upstream columns are used as filters or grouping keys, because, in its words, "If those upstream columns change, the current model is impacted" ([Recce impact radius](https://github.com/DataRecce/recce-docs/blob/main/docs/what-you-can-explore/impact-radius.md); P). The choice changes blast-radius results: **a changed filter column alters every downstream row, and a tool that omits indirect edges reports no impact.** A related storage lesson comes from the same specification. Spark's default setting copies every dataset-level dependency onto every output field, "producing almost a cartesian product of all dataset fields", and the documentation recommends the compact dataset-level form ([OpenLineage column lineage facet](https://github.com/OpenLineage/OpenLineage/blob/main/website/docs/spec/facets/dataset-facets/column_lineage_facet.md); C).

The third point is that no family comes with independently measured accuracy. The only figure found is DataHub's claim that its SQLGlot-based parser "generates lineage with 97-99% accuracy", stated without the benchmark behind it ([DataHub SQL parsing](https://github.com/datahub-project/datahub/blob/master/docs/lineage/sql_parsing.md); C). OpenLineage's dbt integration says its column lineage "was tested with simple projections only" ([OpenLineage dbt README](https://github.com/OpenLineage/OpenLineage/blob/main/integration/dbt/README.md); P), and sqllineage says column lineage "will not be 100% accurate" without schema metadata ([sqllineage README](https://github.com/reata/sqllineage/blob/master/README.md); P). The documented failure classes repeat across tools: scalar UDF internals, table functions, `UNNEST` and JSON extraction, `MERGE INTO`, multi-statement scripts and dynamic table references in DataHub ([DataHub SQL parsing](https://github.com/datahub-project/datahub/blob/master/docs/lineage/sql_parsing.md); C, P), dynamic SQL in IBM's scanners ([IBM docs: dynamic SQL](https://www.ibm.com/docs/en/manta-data-lineage?topic=articles-how-handle-dynamic-sql-scripts); S), and cursors and dynamic queries in Collibra ([Collibra supported SQL syntax](https://productresources.collibra.com/docs/collibra/latest/Content/CollibraDataLineage/ref_supported-sql-syntax.htm); S). DataHub, OpenMetadata, SQLMesh, Recce and the dbt add-ons all build on SQLGlot ([OpenMetadata parser](https://github.com/open-metadata/OpenMetadata/blob/main/ingestion/src/metadata/ingestion/lineage/parser.py); P, [Recce change classification](https://github.com/DataRecce/recce-docs/blob/main/docs/what-you-can-explore/change-classification.md); P), so their errors are correlated and running two of them is not an independent check.

Two further mechanisms are not sold by any assessed vendor. Meta describes combining "static code analysis for different languages, runtime instrumentation, and input and output data signals", the only public account found of field-relevant lineage through services ([Meta engineering, January 2025](https://engineering.fb.com/2025/01/22/security/how-meta-discovers-data-flows-via-lineage-at-scale/); S). LLM extraction is unproven at column level. Microsoft's SLiCE metric scores the similarity of a lineage description, not edge precision and recall ([microsoft/SLiCE](https://github.com/microsoft/SLiCE/blob/7b866f8a93517a86358f6be979bfdea738126722/README.md); P), one paper reports above 95% accuracy at table level only ([ResearchGate 391156254](https://www.researchgate.net/publication/391156254_A_Large_Language_Model-Based_Approach_for_Data_Lineage_Parsing); S), and the hybrid design found for SQL puts a deterministic parser first and the model second ([LineageX paper](https://arxiv.org/pdf/2505.23133); S). The one vendor trace is an `AI_AUGMENTATION` payload type in Gable's command-line tool ([PyPI gable](https://pypi.org/project/gable/); P).

The enterprise strand's cross-vendor finding is blunt: no commercial scanner suite or catalog documented native column-level lineage for microservice, Kafka and Flink, or feature-store hops in what was retrieved, other than through OpenLineage ingestion, and the targeted Kafka and ML queries for Atlan and IBM never ran.

The AWS-native route deserves its own statement because the estate runs there. SageMaker Catalog, built on Amazon DataZone, accepts lineage from outside only as OpenLineage run events. The API model says "Only open-lineage run event are supported as events" and caps each event at 300,000 bytes ([botocore DataZone service model](https://github.com/boto/botocore/blob/2588d4b17abe3e3ab31334970fce523a1c033fef/botocore/data/datazone/2018-05-10/service-2.json); P), and the quota is reported as 20 transactions per second per account and region ([DataZone quotas](https://docs.aws.amazon.com/datazone/latest/userguide/datazone-limits.html); S). Column facets inside a run event are honoured, so the catalog can store field edges the buyer computes. The API models for Amazon MSK, Managed Service for Apache Flink, Redshift, EMR, Athena and MWAA contain no occurrence of the word "lineage" ([botocore data directory](https://github.com/boto/botocore/tree/2588d4b17abe3e3ab31334970fce523a1c033fef/botocore/data); P). The practical reading is that AWS can hold the buyer's lineage but captures it natively only for Glue-crawled assets, Redshift queries and Spark jobs ([AWS lineage support matrix](https://docs.aws.amazon.com/sagemaker-unified-studio/latest/userguide/datazone-support-matrix.html); S). Lineage carries no separate price; it is metered through DataZone requests and storage, reported at $10 per 100,000 requests ([Amazon DataZone pricing](https://aws.amazon.com/datazone/pricing/); S). On that figure one event per minute per streaming job costs about $4.32 a month, which is the researcher's arithmetic and not a quoted price, while per-record emission from services is ruled out by the quota. Streaming lineage therefore belongs at job deployment or schema change, not per message.

### Shift-left tools analyse the pull request, and it is almost always a dbt pull request

Three distinct techniques are in use before merge, and they answer different questions. Re-parsing the changed code and diffing syntax trees (Recce, SQLMesh, and by its own description Foundational) needs no data and shows what could break. Anchoring the changed model on an existing production graph (Datadog, Datafold, Atlan, Monte Carlo) shows real consumers including BI, but inherits the look-back horizon and cannot see lineage that exists only in the pull request. Building the change in a staging schema and diffing data (dbt Advanced CI, Datadog drift detection, Datafold) shows what did change in values and costs warehouse compute.

Two findings from this group shape any build. First, only Marquez stores OpenLineage's design-time job and dataset events. DataHub's endpoint deserialises every body as a run event ([DataHub controller](https://github.com/datahub-project/datahub/blob/master/metadata-service/openapi-servlet/src/main/java/io/datahubproject/openapi/openlineage/controller/LineageApiImpl.java); P, a reading of the code and not a documented statement), OpenMetadata "accepts OpenLineage `RunEvent` payloads" and by default processes only `COMPLETE` events ([OpenMetadata OpenLineage guide](https://github.com/open-metadata/docs-om/blob/main/v2.1.x/how-to-guides/data-lineage/openlineage.mdx); P), and AWS and Google bind ingestion to run events. Lineage computed in CI therefore has no native home in a mainstream catalog and must be wrapped in a synthetic run event or written through a native API. Second, no open-source project was found that turns program analysis into field-level lineage. Joern is fully Apache-2.0, CodeQL's engine needs a commercial licence for closed-source code, and Semgrep's community edition "can only analyze code within the boundaries of a single function or file" ([Joern](https://github.com/joernio/joern/blob/master/README.md); P, [CodeQL](https://github.com/github/codeql/blob/main/README.md); P, [Semgrep](https://github.com/semgrep/semgrep/blob/develop/README.md); P). The complete list of OpenLineage producers contains no code-analysis tool other than the commercial Foundational ([OpenLineage producers](https://github.com/OpenLineage/OpenLineage/blob/main/website/static/ecosystem/producers.tsx); P).

### Across the four objectives, the gaps fall on history, non-dbt changes and proof of outcomes

For O1 the buyer can rent excellent baseline lineage for the warehouse and dbt from several families at once, and should expect none of it to extend to services, streams or the feature store. For O2 the market offers freshness more often than history. Query-log tools refresh in minutes, but lineage "as it was on a given date" is evidenced only at IBM Manta, Solidatus (by claim), Marquez and in the platforms' own event tables and node versions. For O3 the tools are good and almost all dbt-scoped; a change in a service schema or a Flink job reaches a pull-request comment only through Foundational or Gable, or through a check the buyer builds on its own graph. For O4 the working pattern (walk upstream, correlate with changes, rank by owner and importance) is documented at Monte Carlo, SYNQ, Datadog and Bigeye, and the claim that it shortens incidents is unproven, as the next section shows.

## The market is consolidating, prices are opaque and outcome claims are unproven

## Techniques the evidence supports for incremental lineage, pull-request impact and root-cause analysis

The design patterns below are drawn from open specifications and source code, which is where this research has its strongest evidence. Where a sentence is the researchers' inference and not a cited result, it says so.

### Incremental lineage: fingerprint the code, version the edges and never rely on patches alone

Public designs keep lineage current with three mechanisms. The first is an event envelope with defined merge semantics. OpenLineage's explicit lineage facets state that lineage on a run event is "data flow observed during this run, accumulative", while lineage on a design-time job or dataset event is declared and replaces what came before, and an empty `inputs` array "explicitly means that the target has no tracked upstream source" ([explicit lineage guide](https://github.com/OpenLineage/OpenLineage/blob/b9cd9fd9c323af31807d130eb2c7db23998d7f3c/proposals/explicit_lineage_facet/ExplicitLineageGuide.md); P, [LineageFacet schema](https://github.com/OpenLineage/OpenLineage/blob/b9cd9fd9c323af31807d130eb2c7db23998d7f3c/spec/facets/LineageFacet.json); P). That gives a removal signal, which is what patch-only designs lack. DataHub documents the failure directly: with incremental lineage, "lineage edges that used to exist will not be removed" ([DataHub lineage guide](https://github.com/datahub-project/datahub/blob/master/docs/features/feature-guides/lineage.md); P). Its stateful ingestion pairs removal with a fail-safe that skips deletion when more than 75% of the previous run's entities are missing ([DataHub stateful ingestion](https://github.com/datahub-project/datahub/blob/7dccde9d2427cb05e02960e716cdd42b700c256b/metadata-ingestion/docs/dev_guides/stateful.md); P).

The second mechanism is a content fingerprint per parse unit with parent hashes, so only changed units are re-parsed. SQLMesh snapshots carry data, metadata, parent-data and parent-metadata hashes computed from the parsed query, so "superficial changes to a model, such as applying formatting to its query, will not return a new fingerprint" ([SQLMesh snapshots](https://github.com/SQLMesh/sqlmesh/blob/ce229ae5208c2fdee667b993ef542c21e78d20c4/docs/concepts/architecture/snapshots.md); P). Downstream models are marked indirectly modified, and conflicts resolve to "the most conservative category (breaking)" ([SQLMesh plans](https://github.com/TobikoData/sqlmesh/blob/main/docs/concepts/plans.md); C). Hash-based invalidation has a known blind spot that dbt documents for its own state comparison: a change in a variable or environment value is not detected ([dbt state comparison caveats](https://docs.getdbt.com/reference/node-selection/state-comparison-caveats); P). Runtime evidence is the only check on lineage that changes without a code change. Schemas need versioning alongside code for the same reason, because DataHub notes that stale schema information reduces column-lineage accuracy ([DataHub SQL parsing](https://github.com/datahub-project/datahub/blob/master/docs/lineage/sql_parsing.md); C).

The third mechanism is versioned edges read with an "as of" bound. Marquez keys its column-lineage table on dataset versions and traverses it with a recursive query that takes the latest row created before a given time ([Marquez column lineage DAO](https://github.com/MarquezProject/marquez/blob/180f37b22387146187af1ef0279e3ee1d1ccd789/api/src/main/java/marquez/db/ColumnLineageDao.java); P). DataHub takes the other route: its graph "always represents the current state of the world and has no direct support for versioning or history", and a past snapshot is built by replaying the change log ([DataHub graph architecture](https://github.com/datahub-project/datahub/blob/7dccde9d2427cb05e02960e716cdd42b700c256b/docs/what/graph.md); P). AWS versions lineage nodes by event timestamp ([DataZone API model](https://github.com/boto/botocore/blob/2588d4b17abe3e3ab31334970fce523a1c033fef/botocore/data/datazone/2018-05-10/service-2.json); P). The researchers' inference is that the durable pattern is an immutable evidence log as the record with the queryable graph as a rebuildable projection. Two gaps remain. No published design stores lineage bitemporally, so none records what was believed at one time about another, which matters when a parser fix changes historical edges. And no end-to-end freshness figure for a column-level graph was found.

### Pull-request impact: classify the change, then traverse by edge class

The shipped algorithms are conservative and simple. SQLMesh's categoriser returns non-breaking for a direct change only when new projections were added, and anything else becomes breaking under automatic categorisation; its documentation gives the reason that "adding or modifying a model's `WHERE` clause is a breaking change" ([SQLMesh categorizer](https://github.com/SQLMesh/sqlmesh/blob/ce229ae5208c2fdee667b993ef542c21e78d20c4/sqlmesh/core/snapshot/categorizer.py); P, [SQLMesh plans](https://github.com/TobikoData/sqlmesh/blob/main/docs/concepts/plans.md); C). Recce adds a third class. It diffs old and new SQL scope by scope and returns a category (additive, column-scoped or model-wide) plus a per-column status of added, removed, modified or unknown, marking a column unknown "rather than silently reporting 'no-change'" ([Recce change classifier](https://github.com/DataRecce/recce/blob/1da63a366eadac567a7bd2e153b6362cea32d91d/recce/util/change_classifier.py); P). The per-column map is what makes column-level blast radius possible. The traversal rule that follows is the researchers' inference from these two tools and the OpenLineage classes: seed column-scoped changes over direct edges only, and for model-wide changes (filters, joins, grouping) mark the whole downstream dataset once.

At serialisation boundaries the evidence supports fixed compatibility rules chosen by consumer type. `buf breaking` compares a Protobuf schema with a prior version before merge ([buf README](https://github.com/bufbuild/buf/blob/main/README.md); P), Confluent Schema Registry defaults to backward compatibility with transitive variants that check all earlier versions ([Confluent schema evolution](https://docs.confluent.io/platform/current/schema-registry/fundamentals/schema-evolution.html); S), dbt contracts raise an error when a column is removed or its type changes ([dbt node selection](https://docs.getdbt.com/reference/node-selection/methods); P), and datacontract-cli grades the same contract diff from a consumer or a producer perspective ([datacontract-cli](https://github.com/datacontract/datacontract-cli/blob/08881a29a16c05e11494db4fdf5f5c572919bd31/docs/docs/compare-contract-versions.md); P). These checks do not replace lineage. By the researchers' reading of the registry rules, a field rename looks like one removal and one addition with a default, each allowed, so only a lineage lookup of the field's consumers catches it.

Two reporting rules complete the pattern. Where only table-level lineage exists for a hop, widen the result and label it as possible impact; one practice note puts it as "Do not invent column edges" ([OneUptime](https://oneuptime.com/blog/post/2026-09-07-lineage-impact-analysis-ci/view); S, a low-authority source). And show truncation honestly: Recce adds a count of hidden ancestry columns because "partial lineage is no longer presented as complete", and its team rejected automatic expansion over what it calls "CLL overwhelm" ([Recce chain truncation](https://github.com/DataRecce/recce/blob/1da63a366eadac567a7bd2e153b6362cea32d91d/docs/cll-chain-truncation.md); P). No source reports a measured pre-merge catch rate, false-positive rate or ranking algorithm for affected assets, so thresholds for blocking have to be tuned locally.

### Root-cause analysis: traverse deterministically and make the model show its path

Industry practice is a heuristic. Atlan states it as "The root cause is the most-upstream node whose change or failure timeline aligns with the downstream symptom" ([Atlan](https://atlan.com/know/mcp/data-lineage-rca-with-mcp.md); S), and Monte Carlo's documented flow is the same walk followed by a check of query and code changes ([Monte Carlo root-cause skill](https://github.com/monte-carlo-data/mc-agent-toolkit/blob/main/skills/analyze-root-cause/README.md); P). The only rigorous evaluation found is DataTrace, an academic benchmark of agents localising injected faults in database pipelines with lineage recovered through SQLGlot. Across seven proprietary models, top-1 root-cause accuracy ranged from 0.195 to 0.688 with a mean of 0.481, and among correct diagnoses 15 to 23% per model were not backed by the evidence the agent had inspected ([DataTrace README](https://github.com/HKUSTDial/datatrace/blob/48a89e59b4aeef5a01d5ed68c1a1b4d4dc84a411/README.md); P, [DataTrace analysis](https://github.com/HKUSTDial/datatrace/blob/48a89e59b4aeef5a01d5ed68c1a1b4d4dc84a411/leaderboard/analysis/proprietary_board_analysis.md); P). The paper adds that accuracy declines as lineage distance grows ([arXiv 2611.18926](https://arxiv.org/abs/2611.18926); S).

The design that follows is deterministic first. Traverse upstream over confirmed edges, on the graph as it was at incident time, to the earliest node with a failing check or a change inside the incident window. Rank candidates by temporal alignment, edge class and hop distance. Only then hand a bounded evidence set to a model for explanation, require the evidence path in its output, and score the path as well as the answer. Acceptance should come from replaying past incidents and reporting top-1 accuracy, the convention in both the data and the microservice literature. A consultancy's list of risks names the dependency plainly: "lineage gaps that produce wrong diagnoses" ([LatentView](https://www.latentview.com/blog/agentic-ai-for-data-quality/); S). Each diagnosis should therefore state how complete the lineage behind it is.

### Identity, the edge record and storage decide whether the pieces join

Field identity in the two open models is dataset identity plus a field path. OpenLineage addresses a column as namespace, name and field with per-platform naming rules, and calls Snowflake "a special case where we don't have a single standardized namespace" ([OpenLineage naming](https://openlineage.io/docs/spec/naming); P, S). DataHub warns that its identifiers are "exact, case-sensitive strings", that a warehouse reporting upper case and a BI tool reporting lower case yield "two orphaned nodes", and that "a single broken edge in the middle of a chain hides the entire downstream path" ([DataHub URN casing guide](https://github.com/datahub-project/datahub/blob/7dccde9d2427cb05e02960e716cdd42b700c256b/metadata-ingestion/docs/dev_guides/lineage_urn_casing.md); P). Datadog documents the same failure for mismatched account names ([Datadog Snowflake setup](https://docs.datadoghq.com/data_observability/quality_monitoring/data_warehouses/snowflake/); P). The supported pattern is to fix one namespace form per platform before the first event, resolve incoming references against existing entities without destructive normalisation, and record the match type. Neither model defines how a JSON path, an Avro field and a warehouse column that carry the same value are related. That link is a lineage edge, not an identity.

The edge record needs more than the open catalogs carry. DataHub's column edge has a confidence score, a query reference and a match type but no generic property map and no validity interval ([FineGrainedLineage model](https://github.com/datahub-project/datahub/blob/master/metadata-models/src/main/pegasus/com/linkedin/dataset/FineGrainedLineage.pdl); P). OpenMetadata's edge has a source type and timestamps but no confidence ([OpenMetadata edge schema](https://github.com/open-metadata/OpenMetadata/blob/main/openmetadata-spec/src/main/resources/json/schema/type/entityLineage.json); P). SYNQ's API ranks lineage origins and treats declared lineage as additive ([SYNQ lineage.proto](https://github.com/getsynq/api/blob/main/protos/synq/ingest/dwh/v1/lineage.proto); P). A record that serves all four objectives carries the edge class (direct or indirect, with indirect stored once per target dataset), the evidence type, a confidence, the identity match type and valid-from and valid-to times. Because producers differ on whether they emit indirect edges at all, it also needs a marker for which semantics each producer covers, so that an absent filter edge is not read as "no dependency". That last point is the researchers' inference.

On storage, public systems use every pattern: relational adjacency with recursive queries in Marquez, a document store with a derived graph in DataHub, and a custom in-memory graph with "billions of nodes and edges" at Meta ([ACM Digital Library](https://dl.acm.org/doi/10.1145/3722212.3724458); S). No source compares them for column-level workloads. One sizing point is available: Recce measured a project shape of 1,796 nodes and 15,520 columns at about 15.6 MB of JSON for its column-lineage map, a figure it calls directional ([Recce lineage state](https://github.com/DataRecce/recce/blob/1da63a366eadac567a7bd2e153b6362cea32d91d/docs/cll-state-and-fetching.md); P). Column-level lineage multiplies graph size by the average column count, so by the researchers' estimate a store sized for table-level lineage will be too small by one to two orders of magnitude. For AWS, the evidence supports only that Amazon Neptune has an AWS-published lineage reference pattern, which is not column-level ([AWS Big Data Blog](https://aws.amazon.com/blogs/big-data/build-data-lineage-for-data-lakes-using-aws-glue-amazon-neptune-and-spline); S). Accuracy has to be measured locally on a golden set of edges, per edge class and per producer, since the literature offers no target to borrow.

## The AI-factory evidence supports a light factory with human gates, not a lights-off one

The findings above feed a build specification, so the second question is how such a platform should be built with agents doing the execution. The source mix here is lopsided for an access reason, not a judgement of importance: Anthropic and GitHub-hosted material could be read (P or C), while StrongDM, OpenAI, Cursor, DORA, METR and the Thoughtworks and martinfowler.com reviews rest on search summaries or recall.

### The term names a spectrum from supervised agents to unreviewed code

In 2025 and 2026 a "software factory" means a development system in which humans author intent (specifications, scenarios, constraints and the harness) and coding agents plan, write, test and review the code. The vocabulary settled in early 2026. Dan Shapiro's five levels run from "spicy autocomplete" to the "dark factory", which Simon Willison describes as "a five level model of AI-assisted programming, inspired by the five (or rather six, it's zero-indexed) levels of driving automation" ([Simon Willison, 28 January 2026](https://simonwillison.net/2026/Jan/28/the-five-levels/); S). As recalled from the original, Level 3 makes the human a full-time reviewer of diffs, Level 4 has the human writing specifications and checking tests, and Level 5 is "a black box that turns specs into software" ([Dan Shapiro](https://www.danshapiro.com/blog/2026/01/the-five-levels-from-spicy-autocomplete-to-the-software-factory/); R).

The Level 5 reference case is StrongDM's Software Factory, published on 6 February 2026: a three-person team with two founding rules, "Code must not be written by humans" and "Code must not be reviewed by humans", scenarios held outside the codebase like a holdout set, behavioural clones of third-party services for testing, and the benchmark "If you haven't spent at least $1,000 on tokens today per human engineer, your software factory has room for improvement" ([Simon Willison, 7 February 2026](https://simonwillison.net/2026/Feb/7/software-factory/); S). Its orchestrator, Attractor, is published as specifications only, each "a human-readable spec intended to be directly usable by coding agents to implement/validate behavior" ([strongdm/attractor](https://github.com/strongdm/attractor); C). OpenAI's "harness engineering" account describes three engineers growing to seven who shipped roughly one million lines and about 1,500 merged pull requests in five months with "zero manually written code", after cutting a monolithic instruction file to about 100 lines that point into versioned documents and enforcing architecture with linters and structural tests ([OpenAI](https://openai.com/index/harness-engineering/); S).

Both accounts are self-reported by parties with an interest in agent adoption, both are greenfield, and no independent production audit of a no-human-review factory was found. The one detailed first-hand negative report comes from HumanLayer, which sells human-in-the-loop tooling. Its founder writes that his team tried lights-off development in July 2025, that when agents could not solve hard bugs engineers had to dig through code they had stopped reading, that sites went down and parts were rewritten, and that he "haven't been able to dig up any definitive data/findings from StrongDM" ([HumanLayer, "Why Software Factories Fail"](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/wsff.md); P). Birgitta Böckeler's distinction between spec-first, spec-anchored and spec-as-source development gives the useful middle term ([martinfowler.com](https://www.martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html); S). For a platform that will live for years, spec-anchored is the realistic target: specifications are kept and evolved, and code stays reviewable. That judgement is the researchers' inference; no retrieved evidence shows spec-as-source working at system scale.

The toolkits are interchangeable scaffolds for the same chain of principles, requirements with acceptance criteria, design, ordered tasks, implementation and verification. The stations they imply are also the same: specification, planning and decomposition, isolated implementation, automated verification, independent AI review, human approval, release, and feedback into the specifications and the harness. Humans stay accountable for intent, contracts between components, the quality of the verifier and the approval decisions. Three differences matter for a regulated build. AI-DLC is the only one found that advertises explicit approval gates with a structured audit log. OpenSpec scopes specifications to a change, which suits a system that evolves. And several size the ceremony to the work, which answers the reviewers' main criticism that one workflow over-processes small changes. A fourth point comes from the tool documentation itself: prose instructions are guidance the model may not follow. Claude Code's documentation says of its instruction file that "there's no guarantee that it'll follow your instructions" and advises "If something has to happen every time, make it a hook, a deny rule, or a managed setting" ([Claude Code best practices](https://code.claude.com/docs/en/best-practices); P).

### Verification replaces line-by-line review only when the implementer cannot weaken it

The credible substitutes for reading every line are layered, and first-party sources explain why each layer exists. Agents are lenient judges of themselves: "agents reliably skew positive when grading their own work", and a QA agent found real issues and then talked itself into approving them ([Anthropic harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps); P). Agents also satisfy whatever the verifier actually checks. In Anthropic's project to build a C compiler with 16 parallel agents, the lesson recorded is that the task verifier must be nearly perfect or the agent solves the wrong problem, and a known-good compiler served as the oracle ([Anthropic C compiler](https://www.anthropic.com/engineering/building-c-compiler); P). A benchmark exists specifically to measure "LLM agents' propensity to exploit test cases" ([ImpossibleBench](https://github.com/safety-research/impossiblebench); P), and its results as recalled show frequent cheating when tests conflict with the specification, reduced by hidden or read-only tests ([arXiv 2510.20270](https://arxiv.org/abs/2510.20270); R). Anthropic's own harness prompt states "It is unacceptable to remove or edit tests" ([Anthropic effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents); P).

The controls that follow are holdout scenarios and golden data the implementing agent cannot read, an external oracle, an independent reviewer with a fresh context and read-only tools, and deterministic gates for anything expressible as an invariant. The best quantitative datapoint on independent AI review is Anthropic's internal use of its Code Review product: pull requests receiving substantive review comments rose from 16% to 54%, fewer than 1% of findings were marked incorrect, and a review takes about 20 minutes and $15 to $25. The same post says the product "won't approve PRs — that's still a human call" ([Claude Code Review](https://claude.com/blog/code-review); P). Two cautions temper it. "A reviewer that's asked to find problems will always find *something*" ([Claude Code best practices](https://code.claude.com/docs/en/best-practices); P), so findings need severity thresholds. And no retrieved study ranks these gates by defects caught, so the factory should instrument its own.

### Measured outcomes show more output and more instability

Controlled and large-sample evidence concerns AI-assisted development in general, not factories, and it is mixed. The 2025 DORA report found that AI now improves delivery throughput but "continues to increase delivery instability" ([DORA 2025](https://dora.dev/dora-report-2025/); S), and its own summary is that "AI's primary role is as an amplifier, magnifying an organization's existing strengths and weaknesses" ([DORA report source](https://github.com/dora-team/dora.dev/tree/main/hugo/content/research/2025/dora-report); P). METR's randomised trial of 16 experienced open-source developers found early-2025 tools made them 19% slower ([METR](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/); S, R). Its February 2026 update estimates about 18% less task time with an interval of roughly minus 38% to plus 9%, so the sign is not established ([METR research index](https://metr.org/research/); S). Faros telemetry, as recalled, shows teams with high AI adoption merging 98% more pull requests while review time rose 91% and bugs per developer rose 9% ([Faros AI](https://www.faros.ai/blog/ai-software-engineering); R). Anthropic's study of its own engineers reports a self-assessed productivity gain of about 50%, with more than half saying they could "fully delegate" only 0 to 20% of their work ([Anthropic](https://www.anthropic.com/research/how-ai-is-transforming-work-at-anthropic); P). On security, the OpenSSF guide cites studies in which about 40% of generated programs had vulnerabilities and "19.7% proposed packages did not exist" ([OpenSSF guide](https://github.com/ossf/wg-best-practices-os-developers/blob/main/docs/Security-Focused-Guide-for-AI-Code-Assistant-Instructions.md); P).

The evidence separates what is demonstrated from what is advocated. Demonstrated: assistance raises output volume, agents can sustain long runs on well-specified and well-verified greenfield targets, and instability, review load and defect density rise unless tests, small batches and platforms are strong. Advocated without independent data: removing human review, a token spend target per engineer, and specifications as the only source. Even the favourable first-party cases carry warnings. The compiler's author notes that new features often broke existing functionality and that it is "easy to see tests pass and assume the job is done" ([Anthropic C compiler](https://www.anthropic.com/engineering/building-c-compiler); P).

### Costs span two orders of magnitude, so budgets belong on work packages

Typical enterprise use of one coding agent is documented at "around $13 per developer per active day and $150-250 per developer per month", with agent teams using roughly seven times the tokens of a standard session ([Claude Code costs](https://code.claude.com/docs/en/costs); P). StrongDM's benchmark is $1,000 per engineer per day ([Simon Willison](https://simonwillison.net/2026/Feb/7/software-factory/); S). Between those, the compiler project cost just under $20,000 for about 100,000 lines ([Anthropic C compiler](https://www.anthropic.com/engineering/building-c-compiler); P), and one application brief cost $9 solo against $200 with a planner, generator and evaluator harness ([Anthropic harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps); P). The researchers' inference is that for a platform of this size the cost risk lies in unbounded loops, oversized agent teams and rework, not in steady-state tokens, which argues for a token and dollar budget on each work package.

### In a card-payments estate, agents execute and named humans approve

Nothing retrieved shows a regulator or card scheme endorsing a factory in which no human approves code. The converse also holds and should be stated: no guidance from the PCI Security Standards Council, the card schemes, financial regulators or audit firms on agent-written code was retrieved, because the searches never ran. The absence is "not found", not "known not to exist". The controls that apply are written around accountable people. As recalled, PCI DSS v4.0.1 requirement 6.2.3.1 has manual code review performed by someone other than the originating author and approved by management before release, and 6.5.1 requires production changes to follow procedures with documented approval ([PCI SSC document library](https://www.pcisecuritystandards.org/document_library/); R). That wording must be checked against the current standard. The secure-development guidance that was read says "You remain responsible for the code" ([OpenSSF guide](https://github.com/ossf/wg-best-practices-os-developers/blob/main/docs/Security-Focused-Guide-for-AI-Code-Assistant-Instructions.md); P).

Three design consequences follow, and they are the researchers' application of the evidence. First, interpret "the author" conservatively as both the implementing agent and the person who directed it, so that a different, qualified human approves each production change, with AI review as a supplement. Second, put the compliance weight on deterministic controls. Anthropic reports that its own action classifier misses 17% of real over-eager actions and "is not a drop-in replacement for careful human review on high-stakes infrastructure" ([Anthropic auto mode](https://www.anthropic.com/engineering/claude-code-auto-mode); P), and its sandbox design keeps "sensitive credentials (such as git credentials or signing keys)" outside the sandbox with both filesystem and network isolation ([Anthropic sandboxing](https://www.anthropic.com/engineering/claude-code-sandboxing); P). Agents should work against recorded fixtures and emulators and never see production secrets or data. Third, capture the factory's by-products as the audit trail: the approved requirement, the plan, agent transcripts with model and harness versions, test and scanner results, review findings with their disposition, and the approver's identity. Human gates should be few and meaningful, since Anthropic observes that users accept 93% of permission prompts ([Anthropic autonomy study](https://www.anthropic.com/research/measuring-agent-autonomy); P, [Anthropic auto mode](https://www.anthropic.com/engineering/claude-code-auto-mode); P). What the buyer's assessor and internal audit will accept as review "by someone other than the author" when the author is an agent is an open question that only they can answer.

### A lineage platform suits the model because lineage is checkable

This subsection is inference throughout; no published case of a data-lineage or data-platform product built with a factory method was found. A lineage platform is close to an ideal target because most of its behaviour is a deterministic contract: SQL text in, a set of edges out; events in, graph state out. Parsers can be verified against a versioned golden corpus, compared with an independent oracle such as warehouse-reported lineage, and held to metamorphic rules, for example that renaming an alias must not change source-to-target lineage. The parts that produce prose, namely pull-request comments and root-cause narratives, need holdout scenarios and judges calibrated against human labels. The platform also decomposes into low-coupling packages joined by contracts, which fits the documented rule for parallel agents that "Two teammates editing the same file leads to overwrites. Break the work so each teammate owns a different set of files" ([Claude Code agent teams](https://code.claude.com/docs/en/agent-teams); P). Autonomy should be phased by change class: human review of every plan and pull request for the first slices, sampled review for classes whose holdout pass rate and escaped-defect rate earn it, and no relaxation for security-sensitive code or contract changes. One practical check is licensing for emulators, since LocalStack's open-source repository is now archived and commercial CI use needs review ([LocalStack](https://github.com/localstack/localstack); P).

## What this means for owning a thin lineage core and adopting the rest

One limit comes first. Build-versus-buy was not answered as a market question: the search allowance ran out before published accounts of in-house lineage platforms, with team sizes, timelines and costs, could be researched. The implications below are drawn from the capability evidence, not from precedent.

That evidence supports owning the core on five grounds. No product spans the buyer's path, and the missing hops are ones where the buyer must produce the evidence whichever product stores it. Lineage computed before merge has no native home, because the mainstream open catalogs, AWS and Google accept run events only. History is rare, and the open catalogs most likely to be adopted hold current state. Producers disagree on what a column edge means, so someone has to own the edge model that reconciles them. And consolidation makes exit cost real, which an owned identity scheme and evidence log reduce by turning any catalog into a replaceable projection.

The same evidence qualifies the position in ways a build specification should absorb. Pull-request impact for dbt is a commodity, so the platform should adopt it and build only the cross-hop check. Snowflake's external lineage, if confirmed at source, makes Horizon a credible projection target with column fidelity. Foundational and Gable deserve a time-boxed proof of concept on the service-to-topic hop before any in-house program analysis is funded, noting that both are small companies and that Gable's documentation says code is bundled and transmitted for analysis. Marquez's data model is worth copying and its release cadence argues against adopting it as the store. DataHub is a reasonable projection and interface and cannot be the historical record. OpenLineage's explicit lineage facets are the natural envelope for edges computed in CI, but they are under three months old and still labelled experimental, so consumer support should be assumed absent.

| Need | Disposition | Evidence basis |
|---|---|---|
| Identity scheme and resolver | Build | No open model relates a JSON path, an Avro field and a column; casing and namespace mismatches silently orphan nodes |
| Evidence log and versioned, classed edges | Build, thin | Open catalogs hold current state; producers differ on indirect edges; AWS and Google take run events only |
| Warehouse and dbt column lineage | Adopt | Platform lineage tables, dbt's `dbt.column_lineage` Parquet artefact ([dbt column-level lineage](https://github.com/dbt-labs/docs.getdbt.com/blob/current/website/docs/docs/explore/column-level-lineage.md); P) and SQLGlot already do this; verify whether dbt's Apache-2.0 build alone computes it |
| Spark column lineage | Adopt OpenLineage with dataset-level indirect lineage enabled | On by default; the default layout is close to a cartesian product |
| Flink field mapping | Build, small: analyse Flink SQL in CI and declare mappings for DataStream jobs | Flink 2 interfaces carry no column lineage; the extension is a proposal |
| Service-to-topic field flow | Trial Gable or Foundational; otherwise schema checks plus declared mappings | Only two vendors claim it; no open adapter from program analysis to lineage was found |
| Feature store and model hop | Build a bridge emitter | SageMaker's ML lineage is a separate, artifact-level graph |
| Pull-request impact for dbt | Adopt Recce or SQLMesh classification | Open, documented and able to block |
| Cross-hop impact check and contract gate | Build, thin, on the owned graph | No vendor covers non-dbt hops except by untested claim |
| Detection and anomaly monitoring | Buy or keep | Change correlation is where observability vendors add value; Datadog's price is public |
| Root-cause service | Build deterministic traversal with a model narrating bounded evidence | Agents alone were right about half the time in the one benchmark |
| Catalog, search and interface | Adopt as projections | DataHub, SageMaker Catalog and Snowflake Horizon accept column edges within documented limits |

Three developments would justify reopening the decision: a catalog already in use that accepts design-time events, models service and topic nodes and keeps more than a year of queryable history; Flink shipping column lineage for SQL; or a proof of concept showing that a vendor traces fields through Kafka with Avro or Protobuf at acceptable precision. The risk on the other side is building a catalog by accident, which the disposition table guards against by keeping store, search and interface on the adopt side.

## Conclusion

The market sells lineage drawing, and the buyer's problem is lineage joining. Parsing SQL into column edges is now a commodity: one open-source parser sits under most open tools, and the warehouse platforms include the result. What nobody sells is the join across serialisation boundaries, a record that separates what was observed from what was declared or inferred, and a memory of how the graph looked last month. That core is thin and every use of the graph depends on it, which is why owning it is defensible and owning much more is not. As agents become the main consumers of lineage, through the MCP servers that nearly every vendor checked now ships, selection criteria also shift from the graph viewer to the quality of the API, freshness and machine-readable confidence.

The two halves of this research turn out to ask for the same discipline. Lineage that says "unknown" instead of guessing, carries its evidence path and is scored against a golden set of edges is built the same way as a factory whose implementing agents cannot see the holdouts and whose human approvers receive an evidence bundle. The golden edge corpus the platform needs to measure accuracy is also the oracle the factory needs to verify agent-written parsers, so it should be built first, by people. Because nothing in the market proves that lineage shortens incidents, the first deliverable for O4 should be a measured local baseline for detection and resolution time. And because several of the facts this decision rests on are moving within months, it should be recorded with dated triggers and re-tested each quarter.
