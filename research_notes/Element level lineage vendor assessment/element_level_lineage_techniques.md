## 1. Extraction techniques at element level and their trade-offs

### Takeaway
No single technique covers all four layers: SQL parsing and engine-plan capture give column lineage in the warehouse and Spark, but Flink's native lineage (as of Flink master on 2026-11-26) stops at dataset level and no public standard gives field mapping for services or Kafka, so those hops need static code analysis, schema or contract mapping, or runtime payload matching. Published precision and recall figures are almost absent: the only numbers found are one vendor-claimed parser accuracy (97-99%) and one unverified academic result (precision 0.971, recall 0.934).

### Cited Findings

**SQL AST parsing with schema-aware qualification**
- [P] SQLGlot's `lineage()` takes a `schema` argument and builds on the optimizer's `qualify`, `normalize_identifiers` and `build_scope`; passing `column=None` returns every output column with a shared cache so cross-column work is deduplicated; `sources` lets a caller expand referenced queries to continue lineage across models (source at commit of 2026-11-26) — [sqlglot/lineage.py](https://github.com/tobymao/sqlglot/blob/ba0651085c690b8b49e9b9dba2f4a37dbb9055e0/sqlglot/lineage.py)
- [P] DataHub's SQL parser is "built on top of sqlglot" and the docs state: "In our benchmarks, the DataHub SQL parser generates lineage with 97-99% accuracy and outperforms other SQL parsers by a wide margin." This is **vendor-claimed**; the doc page gives no query set or scoring method (read 2026-11-26) — [DataHub SQL parsing](https://docs.datahub.com/docs/lineage/sql_parsing)
- [P] DataHub parser, supported: column-level lineage for `SELECT`, `CREATE VIEW`, CTAS, `INSERT`, `UPDATE`; subqueries; CTEs; `UNION ALL`; `SELECT *` expanded from schemas registered in DataHub; case-insensitive fuzzy matching of table names — [DataHub SQL parsing](https://docs.datahub.com/docs/lineage/sql_parsing)
- [P] DataHub parser, not supported or best-effort: scalar UDF internals (lineage points at UDF inputs only), table-valued functions (skipped), `json_extract`, `UNNEST` ("cannot reliably generate column-level lineage"), struct subfields, Snowflake multi-table inserts, multi-statement SQL / scripting, `MERGE INTO` (no column lineage), `INSERT INTO (cols) SELECT` with a non-matching column list, and dynamic table references such as Snowflake `identifier(...)` — [DataHub SQL parsing](https://docs.datahub.com/docs/lineage/sql_parsing)
- [P] DataHub parser accuracy depends on schema freshness: "In cases where the table schema information in DataHub is outdated or otherwise incorrect, we may not be able to generate accurate column-level lineage." The parse result exposes `debug_info.confidence_score`, a 0-1 value — [DataHub SQL parsing](https://docs.datahub.com/docs/lineage/sql_parsing)
- [P] DataHub's `SqlParsingAggregator` "can also resolve lineage across temp tables and table renames/swaps", but is "not officially part of the DataHub SDK" — [DataHub SQL parsing](https://docs.datahub.com/docs/lineage/sql_parsing)
- [S] sqllineage's documentation says it "requires metadata" to handle `SELECT *` or unqualified columns in joins; without metadata, column lineage "may only be partially accurate" — [sqllineage on PyPI](https://pypi.org/project/sqllineage/)
- [P] dbt's column-level lineage "relies on SQL parsing"; errors occur "when parsing fails or a column's origin is unknown (like with JSON unpacking, lateral joins, and so on)", and Python models cannot be parsed for lineage at all. dbt shows a warning pill when lineage is incomplete — [dbt column-level lineage](https://docs.getdbt.com/docs/explore/column-level-lineage)
- [P] In the dbt Fusion engine, column-level lineage is available only with `static_analysis: strict`. Fusion produces and validates "a logical plan for every rendered query in the project"; the default `baseline` mode does not fetch warehouse schemas and does not give column lineage — [dbt static analysis](https://docs.getdbt.com/docs/build/about-static-analysis)
- [P] LineageX (SFU; described in an ICDE 2025 demo paper, arXiv May 2025) outputs, per output column, two lists: columns that "contribute directly" and columns that are "referenced, such as columns from WHERE/GROUP BY". It supports only Postgres and states that "providing the schema information and database connection is highly recommended for the best result" — [LineageX README](https://github.com/sfu-db/lineagex/blob/788c14a84b03767eca872c9e3c99a884c6ee26e8/README.md); paper: [arXiv 2505.23133](https://arxiv.org/pdf/2505.23133)
- [S] A 2026 arXiv paper notes that "stored procedures and user-defined functions invoked from SQL are opaque to AST-level column extraction", so their lineage needs the body inlined or a separate per-procedure annotation — [arXiv 2610.07258](https://arxiv.org/pdf/2610.07258)
- [S, low confidence] A ResearchGate paper, "A DBT-Based Column Lineage Tracking Approach for Regulatory and Audit Compliance", is reported as measuring precision 0.971 (95% CI 0.952-0.987), recall 0.934 (0.905-0.960), F1 0.952 on a 400-edge ground truth. A second search could not reproduce these figures; venue and method are unverified — [ResearchGate 397522914](https://www.researchgate.net/publication/397522914_A_DBT-Based_Column_Lineage_Tracking_Approach_for_Regulatory_and_Audit_Compliance)

**Query-log and access-history mining**
- [S] Snowflake `ACCESS_HISTORY.objects_modified` nests per-column `directSources` and `baseSources`; Snowflake notes `baseSources` supports column lineage — [Snowflake ACCESS_HISTORY](https://docs.snowflake.com/en/sql-reference/account-usage/access_history)
- [R] Snowflake ACCESS_HISTORY: column level, up to 3 hours latency, 365 days retention — [Snowflake access history](https://docs.snowflake.com/en/user-guide/access-history)
- [S] BigQuery / Dataplex column lineage is automatic for certain job types but: load jobs and routines produce no column lineage; no upstream column lineage for external tables; a job creating more than 1,500 column-level links keeps table-level lineage only; there is no API to create, read, update, delete or search column-level lineage — [Dataplex lineage views](https://docs.cloud.google.com/dataplex/docs/lineage-views)
- [S] Databricks Unity Catalog captures lineage to column level "in near real time"; UDF lineage is table-level only; Databricks says it captures column lineage "as much as possible"; lineage before 2024-09-01 is unavailable. Sources disagree on system-table retention (rolling 1 year vs 395 days) — [Unity Catalog lineage](https://docs.databricks.com/aws/en/data-governance/unity-catalog/data-lineage.html)
- [S] Netflix's lineage system "scans system logs and metadata generated by various compute engines"; for Spark it uses "spark plan information" and for Snowflake "admin tables" — [Netflix TechBlog](https://netflixtechblog.com/building-and-scaling-data-lineage-at-netflix-to-improve-data-infrastructure-reliability-and-1a52526a7977)
- [R] Uber notes that any write that bypasses SQL "opts out" of query-parser lineage — [Uber Queryparser](https://www.uber.com/blog/queryparser)

**Engine logical-plan capture**
- [P] OpenLineage's Spark column lineage is "turned on by default". It traverses the logical plan and tracks dependencies by Spark `ExprId`: `InputFieldsCollector` reads inputs from `DataSourceV2Relation`, `DataSourceV2ScanRelation`, `HiveTableRelation` or `LogicalRelation`; `OutputFieldsCollector` matches `Aggregate` / `Project` outputs to the output schema by name; `ExpressionDependenciesCollector` records typed dependencies — [OpenLineage Spark column lineage](https://openlineage.io/docs/integrations/spark/spark_column_lineage)
- [P] Weak spot inside Spark capture: for a `JDBCRelation` the integration falls back to parsing the query string, and then "does not collect information about input field types or transformation types"; only table and field names as written in the query are captured — [OpenLineage Spark column lineage](https://openlineage.io/docs/integrations/spark/spark_column_lineage)
- [P] Trino's OpenLineage plugin uses Trino's `EventListener` interface, emits two events per query, and "supports both table and column level lineage" — [OpenLineage Trino](https://openlineage.io/docs/integrations/trino)
- [P] Flink: "lineage interfaces in Flink 2.x do not provide column level lineage information... this may be difficult to extract for the transformations defined through the programming language. However, it is possible to extract column level lineage information for Flink SQL jobs." A Flink PR (apache/flink #26089) "contains a potential extension" — [OpenLineage Flink 2.x](https://openlineage.io/docs/integrations/flink/flink2)
- [P] Confirmed in Flink source on 2026-11-26: `LineageEdge` connects a `SourceLineageVertex` to a sink `LineageVertex`; `DatasetSchemaFacet` lists a dataset's fields but there is no field-to-field mapping type — [LineageEdge.java](https://github.com/apache/flink/blob/055ae9cd0d4a876bd19be18da94aa13ee62062c1/flink-runtime/src/main/java/org/apache/flink/streaming/api/lineage/LineageEdge.java), [Flink data lineage doc](https://github.com/apache/flink/blob/055ae9cd0d4a876bd19be18da94aa13ee62062c1/docs/content/docs/internals/data_lineage.md)

**Static program analysis and taint analysis of application code**
- [S] Ant Group published field-based static taint analysis for industrial Java microservices (ICSE-SEIP 2022) and a compositional follow-up, CFTaint (ICSE 2023). The design uses function summaries, follows taint through specified sensitive fields, models containers (maps, JSON objects, lists), and deliberately does not separate instances of the same type while distinguishing fields, a trade-off for scale and recall. No precision or recall figure was retrieved — [ICSE-SEIP 2022](https://dl.acm.org/doi/10.1145/3510457.3513075), [ICSE 2023](https://ieeexplore.ieee.org/document/10172563/)
- [S] "YASA: Scalable Multi-Language Taint Analysis on the Unified AST at Ant Group" exists on arXiv (ID suggests January 2026); contents not verified — [arXiv 2601.17390](https://arxiv.org/pdf/2601.17390)
- [S] Meta (January 2025): lineage combines "static code analysis for different languages, runtime instrumentation, and input and output data signals"; static analysis tools "simulate code execution to map out data flows" — [Meta engineering](https://engineering.fb.com/2025/01/22/security/how-meta-discovers-data-flows-via-lineage-at-scale/)
- [S] A Meta talk at USENIX PEPR 2024 (Kim, Lambert, Logozzo) notes that each lineage approach "has potential false positives and false negatives" — [PEPR 2024](https://usenix.org/conference/pepr24/presentation/kim)
- [P] Code-derived lineage is expressible in OpenLineage: Foundational (vendor) describes extracting lineage from dbt, Spark and SQLAlchemy ORM code by static analysis and emitting it as static lineage, with the Job representing the code location and `SourceCodeLocationJobFacet` carrying repo and commit. It proposes a future facet for the exact code lines and code annotations as lineage hints for legacy systems (post dated 2025-02-04) — [OpenLineage blog: lineage from code](https://github.com/OpenLineage/OpenLineage/blob/b9cd9fd9c323af31807d130eb2c7db23998d7f3c/website/blog/lineage-from-code/index.mdx)
- [P] Same post, on why static is needed: runtime lineage misses rarely executed pipelines (restore jobs, annual computations), rarely triggered code paths (dbt full refresh vs incremental) and rarely viewed dashboards — [OpenLineage blog: lineage from code](https://github.com/OpenLineage/OpenLineage/blob/b9cd9fd9c323af31807d130eb2c7db23998d7f3c/website/blog/lineage-from-code/index.mdx)
- [S] Gable (vendor) states it uses static analysis of application code (TypeScript, Java, Python, Swift listed by a third party) to detect contract-breaking changes before merge and to map "where each field originates and how it's transformed". All self-reported; no accuracy figure; Kafka producer schema detection was not confirmed — [Gable blog](https://www.gable.ai/blog/how-gable-implements-data-contracts---and-stops-bad-things-from-happening)

**Schema-based and declared mapping**
- [P] ODCS v3.2.0 has property-level `transformSourceObjects` ("List of objects in the data source used in the transformation"), `transformLogic` ("Logic used in the column transformation") and `transformDescription`. Note `transformSourceObjects` lists objects, not source fields — [ODCS schema doc](https://github.com/bitol-io/open-data-contract-standard/blob/7c7597ee04ec58f67ea4a9cbcddab2043ff7d01f/docs/schema.md)
- [S] A practitioner post argues a Kafka topic schema field and a table column "may represent the same business field but are not the same physical field. Keep both identities and connect them through column lineage" (low-authority blog, September 2026) — [oneuptime blog](https://oneuptime.com/blog/post/2026-09-08-batch-streaming-lineage-one-metadata-graph/markdown)
- [S] Conduktor: Kafka-side tools "don't read message contents, so they can't show that a field in one topic becomes a field in another" — [Conduktor blog](https://www.conduktor.io/blog/kafka-data-lineage-tools)
- [S] An open-source library (faucet-lineage) emits "deterministic column-level lineage... folded over the declared transform chain, emitted only when the whole chain is mappable (never fabricated)" — [faucet-lineage](https://docs.rs/crate/faucet-lineage/1.2.2)

**Runtime payload sampling and data-content matching**
- [S] Meta's Privacy Probes "automate data flow discovery by collecting runtime signals" (January 2025) — [Meta engineering](https://engineering.fb.com/2025/01/22/security/how-meta-discovers-data-flows-via-lineage-at-scale/)
- [R] As summarised in this repo's appendix (its wording, not Meta's): Meta's probes sit in shared frameworks (logger, RPC) and sample source and sink payloads per request; edges carry a confidence score; warehouse lineage comes from executed SQL logged at runtime then parsed; AI lineage from parsed training configs plus hooks in data loaders — [Meta engineering](https://engineering.fb.com/2025/01/22/security/how-meta-discovers-data-flows-via-lineage-at-scale/)
- [S] Meta's PrivacyLib (post dated 2026-10-27) is a shared library "embedded across infrastructure layers" that instruments data reads and writes and emits metadata into a centralized lineage graph — [Meta engineering](https://engineering.fb.com/2026/10/27/security/privacylib/)
- [S] Meta's October 2025 post lists the lineage signals collected across stacks: web probes, logger, batch-processing, RPC lineage and training manifests — [Meta engineering](https://engineering.fb.com/2025/10/23/security/scaling-privacy-infrastructure-for-genai-product-innovation/)

### Inferences
- Schema freshness is a hidden dependency of every parser-based approach: `SELECT *` expansion, unqualified column resolution and case handling all need the schema as it was when the SQL ran. A lineage build therefore needs versioned schemas, not only versioned code.
- The documented failure modes are consistent across tools (dynamic SQL, UDFs and table functions, `UNNEST` / JSON extraction, structs, `MERGE`, multi-statement scripts, stored procedures, Python models). These are the places where a second technique (plan capture, access history or an LLM fallback) earns its cost.
- Engine-plan capture is more faithful than text parsing but inherits a parser-grade hole wherever the engine delegates to an opaque source (Spark `JDBCRelation`).
- For services and streams, the only fully automatic field-level evidence in the public record is Meta's payload sampling, which requires reading data content. A metadata-only programme must rely on static analysis plus declared mappings and accept lower confidence on those hops.

### Gaps
- No published precision or recall was found for: Spark plan capture, Trino, access-history lineage, static taint analysis as a lineage source, or Meta's payload matching. Meta's exact matching rules (for example exact versus substring match, sampling rate, confidence thresholds) could not be confirmed because `engineering.fb.com` was unreachable.
- DataHub's blog post with a per-parser accuracy table (DataHub vs sqllineage vs openlineage-sql, SELECT and CTAS, table and column level) exists per search but its numbers were not retrieved.
- Not found (searches not run): static analysis that traces a field from an HTTP request or ORM entity to a Kafka message field in Go or TypeScript; OpenAPI / AsyncAPI / protobuf field-mapping tools; dynamic taint tracking used for lineage outside Meta.

## 2. LLM-assisted lineage extraction (2024-2026)

### Takeaway
The public evidence is thin and mostly not column-level: one Microsoft benchmark (SLiCE, August 2025) evaluates "schema lineage" with a composite similarity metric rather than edge precision and recall, and one 2025 paper reports above 95% accuracy at table level only. No head-to-head measurement of an LLM against a deterministic parser on column-level edges, and no measured hallucination rate, was found.

### Cited Findings
- [S] "Schema Lineage Extraction at Scale: Multilingual Pipelines, Composite Evaluation, and Language-Model Benchmarks" (arXiv, August 2025) finds that open-source models at 32B scale with chain-of-thought reasoning traces reach extraction performance "comparable to" GPT-4o and GPT-4.1; a single high-quality trace noticeably improves results, but needing experts to write traces per script type limits scalability — [arXiv 2508.07179](https://arxiv.org/pdf/2508.07179)
- [S] Same paper, cost: proprietary LLMs perform strongly but each prompt must include full pipeline scripts, which "can run to hundreds of thousands of tokens" — [arXiv 2508.07179](https://arxiv.org/pdf/2508.07179)
- [S] Third-party summaries of the paper: accuracy drops as scripts get more complex, though chain-of-thought softens the drop; the dataset is described as 1,700 multilingual examples — [Pith review](https://pith.science/paper/2508.07179)
- [P] The accompanying open-source metric, SLiCE (Microsoft, MIT licence), scores four components separately (source schema, source tables, transformations, aggregations) using BLEU, fuzzy matching, F1 and AST-based similarity, with configurable weights, for Python, SQL and C# transformation code (README at commit of 2026-10-26) — [microsoft/SLiCE](https://github.com/microsoft/SLiCE/blob/7b866f8a93517a86358f6be979bfdea738126722/README.md)
- [S, low confidence] A topic summary cites LLM extraction scores of about 0.73-0.76 on SLiCE; not verified against the paper — [Emergent Mind summary](https://www.emergentmind.com/topics/data-lineage-explorer)
- [S] "A Large Language Model-Based Approach for Data Lineage Parsing" (April 2025) reports that models with 10B and 100B parameters exceed 95% **table-level** lineage accuracy with the authors' prompts, across SQL, Python, Shell and Flume scripts; the authors say they did not extensively explore stored procedures — [ResearchGate 391156254](https://www.researchgate.net/publication/391156254_A_Large_Language_Model-Based_Approach_for_Data_Lineage_Parsing)
- [S] Hybrid design, parser first: the LineageX paper (May 2025) demonstrates GPT-4o for impact analysis, with the LLM's results augmented by LineageX's parser-derived column lineage — [arXiv 2505.23133](https://arxiv.org/pdf/2505.23133)
- [S] Hybrid design for legacy code: an ACL 2026 industry-track paper describes a pipeline where a COBOL / PL/I parser first identifies modules, data definitions and control flow and an LLM then works from that structure; the same pipeline performs lineage analysis. No hallucination measurement reported in the extract — [ACL 2026 industry](https://aclanthology.org/2026.acl-industry.4.pdf)
- [S, anecdotal] A practitioner write-up splits Python / Pandas ETL lineage extraction across three LLM agents and claims coverage rises from 60-70% with SQL-only parsing to "near 100%". Not a benchmark — [HackerNoon](https://hackernoon.com/beyond-sql-parsing-extracting-lineage-from-python-etl-by-splitting-the-job-across-three-llm-agents)
- [S] An AWS Builder Center post, "Data lineage you can defend, part 2: AI-assisted lineage on AWS", describes publishing self-derived lineage through the SageMaker `PostLineageEvent` API with column-level tracing in the visualiser; details not read — [AWS Builder Center](https://builder.aws.com/content/3LST69fUL0lex3G5yZCtnUUbtdw/data-lineage-you-can-defend-part-2-ai-assisted-lineage-on-aws)
- [P] Storage hooks for non-deterministic edges already exist in an open metadata model: DataHub's `FineGrainedLineage` record carries `confidenceScore` ("between 0 (low confidence) and 1 (high confidence)", default 1.0), `transformOperation`, the originating `query` URN and a `matchType` describing how upstream field URNs were resolved — [FineGrainedLineage.pdl](https://github.com/datahub-project/datahub/blob/7dccde9d2427cb05e02960e716cdd42b700c256b/metadata-models/src/main/pegasus/com/linkedin/dataset/FineGrainedLineage.pdl)
- [P] A deterministic "say unknown rather than guess" control, usable as a pattern for LLM output: Recce's classifier marks columns `unknown` when a changed CTE or subquery cannot be tied to an outer projection, "rather than silently reporting 'no-change'" — [Recce change_classifier.py](https://github.com/DataRecce/recce/blob/1da63a366eadac567a7bd2e153b6362cea32d91d/recce/util/change_classifier.py)

### Inferences
- The two measured results do not transfer to a column-level build decision: SLiCE scores textual and structural similarity of a lineage description, and the 95% figure is table-level. Any LLM extractor for column edges needs its own golden-edge evaluation.
- The evidence favours LLMs as a fallback or enrichment layer behind a parser, not as the primary extractor: both hybrid designs found put a deterministic parser first, and the SLiCE paper flags token cost on long scripts.
- Practical hallucination controls implied by the sources: ground the prompt in the real schema; constrain output to (dataset, field) identifiers that exist in the catalog; re-validate any LLM-proposed edge by parsing where the code is parseable; store LLM edges with a lower confidence and a distinct evidence type; allow an explicit `unknown`.

### Gaps
- Not found: any benchmark comparing an LLM with SQLGlot-class parsers on column-level precision and recall; measured hallucination (false-edge) rates; cost per statement or per repository; production reports from large engineering organisations using LLM agents for stored-procedure, Spark or COBOL lineage. Search budget ran out before vendor evidence and 2026 papers could be searched further.
- The SLiCE paper's per-model scores, per-language breakdown and dataset composition were not retrieved (`arxiv.org` unreachable).

## 3. Lineage semantics at column level

### Takeaway
The de facto taxonomy is OpenLineage's two-level scheme, DIRECT (value derived from the input) versus INDIRECT (rows or values influenced by the input), with nine subtypes and a masking flag; as of August 2026 OpenLineage is replacing its column lineage facet with broader "explicit lineage" facets that keep the same transformation vocabulary. Tools disagree on whether indirect dependencies count as lineage at all (DataHub and dbt exclude them), which changes impact-analysis results materially.

### Cited Findings
- [P] OpenLineage `ColumnLineageDatasetFacet` is at version 1-2-0 (core spec 2-0-2). Each output field lists `inputFields` (namespace, name, field) with `transformations[]`, each having `type`, `subtype`, `description`, `masking`. The older `transformationDescription` and `transformationType` (IDENTITY | MASKED) are deprecated. A top-level `dataset` array holds "column level lineage that affects the whole dataset. This includes filtering, sorting, grouping (aggregates), joining, window functions, etc." — [ColumnLineageDatasetFacet.json](https://github.com/OpenLineage/OpenLineage/blob/b9cd9fd9c323af31807d130eb2c7db23998d7f3c/spec/facets/ColumnLineageDatasetFacet.json)
- [P] Definitions: DIRECT, "output column value was somehow derived from `inputField` value"; INDIRECT, "output column value is impacted by the value of `inputField` column, but it's not derived from it" — [OpenLineage column lineage facet](https://openlineage.io/docs/spec/facets/dataset-facets/column_lineage_facet/)
- [P] Subtypes. Direct: `IDENTITY` (taken as is), `TRANSFORMATION` (transformed value from the input row), `AGGREGATION` (aggregation of values from multiple input rows). Indirect: `JOIN`, `GROUP_BY`, `FILTER`, `SORT`, `WINDOW`, `CONDITIONAL` (input used in `IF`, `CASE WHEN` or `COALESCE`) — [OpenLineage column lineage facet](https://openlineage.io/docs/spec/facets/dataset-facets/column_lineage_facet/)
- [P] `masking` is a boolean for obfuscation; examples given are `hash` (a masking TRANSFORMATION) and `count` (a masking AGGREGATION); the list of masking functions "is dependent on the source system" — [OpenLineage column lineage facet](https://openlineage.io/docs/spec/facets/dataset-facets/column_lineage_facet/)
- [P] Spark emits indirect dependencies in the dataset-level `dataset` array only when `spark.openlineage.columnLineage.datasetLineageEnabled=True`. The default is `False`, which copies every indirect dependency onto every output field (the "legacy representation") — [OpenLineage column lineage facet](https://openlineage.io/docs/spec/facets/dataset-facets/column_lineage_facet/)
- [P] How Spark derives the classes: `Aggregate`, `Join`, `Filter` and `Sort` plan nodes create a pseudo-expression representing "all outputs" whose dependencies are all INDIRECT; most expressions are DIRECT; `If`, `CaseWhen` and `Coalesce` conditions are the exceptions. Merge rules along a path: any INDIRECT hop makes the result INDIRECT; among DIRECT hops the subtype is the first present of AGGREGATION, TRANSFORMATION, IDENTITY; any masking hop makes the result masking — [OpenLineage Spark column lineage](https://openlineage.io/docs/integrations/spark/spark_column_lineage)
- [P] New in 2026: `LineageFacet.json` 1-0-0 defines `LineageJobFacet` and `LineageDatasetFacet`. They allow dataset-to-dataset derivation without a job (views, aliases, curated lineage), job-to-job flow (Airflow XCom, in-memory handoffs, stored-procedure chains), mixed dataset- and field-level detail in one event, and transformation detail on a job input with no tracked upstream dataset — [LineageFacet.json](https://github.com/OpenLineage/OpenLineage/blob/b9cd9fd9c323af31807d130eb2c7db23998d7f3c/spec/facets/LineageFacet.json), [blog, 2026-08-04](https://openlineage.io/blog/explicit-lineage)
- [P] Motivation given: implicit lineage is the cartesian product of a run's inputs and outputs, so a job reading A, B and writing C, D yields four edges when two are real; "for a bulk ETL job that processes 10 independent tables in one run, most of the inferred graph is noise." The old facet is "all-or-nothing per output" — [explicit lineage guide](https://github.com/OpenLineage/OpenLineage/blob/b9cd9fd9c323af31807d130eb2c7db23998d7f3c/proposals/explicit_lineage_facet/ExplicitLineageGuide.md)
- [P] Precedence for consumers: lineage facet, then column lineage facet, then cartesian product. The docs page says the new facet "supersedes the Column Lineage Dataset Facet for the relationships it describes". Status conflict to note: the schema file and docs page are in the repository at 2026-11-26, but the developer guide still labels the feature "Experimental... We may also change it or drop the idea altogether" — [lineage dataset facet doc](https://github.com/OpenLineage/OpenLineage/blob/b9cd9fd9c323af31807d130eb2c7db23998d7f3c/website/docs/spec/facets/dataset-facets/lineage.md), [guide](https://github.com/OpenLineage/OpenLineage/blob/b9cd9fd9c323af31807d130eb2c7db23998d7f3c/proposals/explicit_lineage_facet/ExplicitLineageGuide.md)
- [P] DataHub excludes indirect dependencies by design: "We do not consider columns referenced in filtering or organizational clauses such as WHERE, GROUP BY, ORDER BY, JOIN, HAVING, or PARTITION BY to be part of lineage" — [DataHub SQL parsing](https://docs.datahub.com/docs/lineage/sql_parsing)
- [P] dbt likewise: column-level lineage "reflects the lineage from select statements in your models' SQL code. It doesn't reflect other usage like joins and filters." dbt adds a "column evolution lens" that labels each hop as transformed versus reused (passthrough or rename), and propagates descriptions along untransformed hops — [dbt column-level lineage](https://docs.getdbt.com/docs/explore/column-level-lineage)
- [S] A practitioner write-up reports the resulting trade-off: table-level lineage flags too much, and column-level lineage misses dependencies that run through a filter or a count — [Felix Isaiah, Substack](https://felixmt.substack.com/p/data-quality-and-lineage)
- [P] Change-impact tools already act on the distinction. Recce classifies a model change as `breaking` (v2 name `model_wide`) when a changed upstream column is referenced in JOIN, WHERE, GROUP BY, HAVING or ORDER BY, or when DISTINCT or a UDTF is involved; as `partial_breaking` (`column`) when a projection is removed or modified; and as `non_breaking` (`additive`) when a projection is only added — [Recce change_classifier.py](https://github.com/DataRecce/recce/blob/1da63a366eadac567a7bd2e153b6362cea32d91d/recce/util/change_classifier.py), [vocabulary map](https://github.com/DataRecce/recce/blob/1da63a366eadac567a7bd2e153b6362cea32d91d/recce/models/types.py)
- [P] SQLMesh's guidance matches: "adding or modifying a model's WHERE clause is a breaking change because downstream models contain rows that would now be filtered out" — [SQLMesh plans](https://github.com/SQLMesh/sqlmesh/blob/ce229ae5208c2fdee667b993ef542c21e78d20c4/docs/concepts/plans.md)

### Inferences
- A build should store both classes and keep indirect dependencies at dataset scope (the OpenLineage `dataset` array), not fan them out to every output column. Fanning out is the Spark default and multiplies edges without adding information.
- Suggested treatment in impact analysis, derived from the Recce and SQLMesh rules: a change to a column that feeds DIRECT edges affects only the downstream columns on those edges; a change to a column used in an INDIRECT edge (filter, join key, group key) affects the row set of the whole downstream dataset and should be reported once at dataset level with a lower default severity for value-only changes (for example a type widening) and a high severity for removals or semantic changes.
- IDENTITY and rename hops are the ones where schema-compatibility rules alone decide breakage; TRANSFORMATION and AGGREGATION hops need semantic review; masking hops are natural stop points for privacy propagation but not for breakage propagation.
- Ingesting from sources with different conventions (DataHub and dbt drop indirect edges, OpenLineage Spark keeps them) will produce a graph whose completeness varies by source. The edge record needs a "semantics covered" marker per producer so that an absent indirect edge is not read as "no dependency".

### Gaps
- No published measurement was found of how much false-positive reduction the direct / indirect split delivers in impact analysis.
- Other taxonomies (for example commercial parsers' own categories) were not searched.

## 4. Incremental lineage maintenance

### Takeaway
Public designs keep lineage current with three mechanisms: per-run events with defined merge semantics (OpenLineage: run events accumulate, job and dataset events replace), content fingerprints of models with parent hashes for dependency-aware invalidation (SQLMesh, dbt state), and audit-stamped or version-keyed edges for point-in-time reads (Marquez, DataHub). True bitemporal lineage graphs and lineage-diff algorithms are not described in any source reached, and published freshness figures are sparse.

### Cited Findings

**Event-driven updates and merge semantics**
- [P] OpenLineage explicit lineage semantics: `LineageJobFacet` on a RunEvent is "data flow observed during this run, accumulative"; on a JobEvent it is "declared, static data flow for this job, replace"; `LineageDatasetFacet` on a DatasetEvent is "structural derivation of this dataset, replace". "The event type tells a consumer whether to merge entries across events for a run (accumulative) or take the latest event as the whole picture (replace)" — [explicit lineage guide](https://github.com/OpenLineage/OpenLineage/blob/b9cd9fd9c323af31807d130eb2c7db23998d7f3c/proposals/explicit_lineage_facet/ExplicitLineageGuide.md)
- [P] In the new facet, an empty `inputs` array on a dataset entry "explicitly means that the target has no tracked upstream source" — [LineageFacet.json](https://github.com/OpenLineage/OpenLineage/blob/b9cd9fd9c323af31807d130eb2c7db23998d7f3c/spec/facets/LineageFacet.json)
- [P] Static lineage (OpenLineage 1.0, 2023): `JobEvent` and `DatasetEvent` "add facets at a point in time that will apply to an entity until a new version of the same facet is produced". Named use cases include "bootstrapping of a lineage graph with prospective runs" — [OpenLineage static lineage blog](https://openlineage.io/blog/static-lineage/)
- [P] Run-cycle rules: events for one run are accumulative unless stated otherwise. STREAMING jobs (Kafka Streams, Flink) have no expected terminal event and "typically emit events periodically at regular intervals containing complete snapshot of lineage and metrics for the captured time period". A SERVICE processing type exists for microservices, background workers and API services — [OpenLineage run cycle](https://github.com/OpenLineage/OpenLineage/blob/b9cd9fd9c323af31807d130eb2c7db23998d7f3c/website/docs/spec/run-cycle.md)

**Per-commit incremental parsing: fingerprints and dependency-aware invalidation**
- [P] SQLMesh snapshots carry a fingerprint of four hashes: `data_hash`, `metadata_hash`, `parent_data_hash`, `parent_metadata_hash`. Because fingerprints are computed from the SQLGlot-parsed query, "superficial changes to a model, such as applying formatting to its query, will not return a new fingerprint" — [definition.py](https://github.com/SQLMesh/sqlmesh/blob/ce229ae5208c2fdee667b993ef542c21e78d20c4/sqlmesh/core/snapshot/definition.py), [snapshots doc](https://github.com/SQLMesh/sqlmesh/blob/ce229ae5208c2fdee667b993ef542c21e78d20c4/docs/concepts/architecture/snapshots.md)
- [P] SQLMesh change categories include `INDIRECT_BREAKING`, `INDIRECT_NON_BREAKING` and `METADATA`, so a node's state distinguishes "my code changed" from "something upstream changed" from "only metadata changed". For an indirectly modified model with conflicting upstream categories, "the most conservative category (breaking) is assigned" — [definition.py](https://github.com/SQLMesh/sqlmesh/blob/ce229ae5208c2fdee667b993ef542c21e78d20c4/sqlmesh/core/snapshot/definition.py), [plans doc](https://github.com/SQLMesh/sqlmesh/blob/ce229ae5208c2fdee667b993ef542c21e78d20c4/docs/concepts/plans.md)
- [P] dbt `state:modified` compares the project with a previous manifest and offers sub-selectors: `.body`, `.configs`, `.relation`, `.persisted_descriptions`, `.macros` (changes to upstream macros, direct or indirect) and `.contract`. `tags` and `meta` changes are metadata-only and do not count — [dbt node selection methods](https://docs.getdbt.com/reference/node-selection/methods)
- [P] dbt state-comparison caveats that also apply to any hash-based lineage invalidation: a change in a `var` or `env_var` value is not detected; seeds over 1 MiB are compared by path only; env-aware logic causes false positives unless the `state_modified_compare_more_unrendered_values` flag is set — [dbt state comparison caveats](https://docs.getdbt.com/reference/node-selection/state-comparison-caveats)
- [P] dbt state-aware orchestration keeps "real-time shared model-level state" across jobs and rebuilds a model only when its compiled code or upstream data state changed; with Fusion, test reuse is decided from "the logical plan for the compiled code" — [dbt state-aware orchestration](https://docs.getdbt.com/docs/deploy/state-aware-about)
- [S] An open SQLMesh RFC (issue #6062) proposes using column-level lineage in the plan algorithm so that only downstream models that actually use a changed column are treated as affected — [SQLMesh issue 6062](https://github.com/SQLMesh/sqlmesh/issues/6062)
- [P] Recce computes the complete column-lineage map on the backend and caches it, so per-node requests avoid "repeated SQL parsing and manifest traversal". Measured payload for a project shape of 1,796 nodes and 15,520 columns: 15.6 MB JSON, 1.38 MB gzip, 33 ms median parse, 19.4 MB retained heap (local Node.js measurement, described as directional) — [Recce CLL state and fetching](https://github.com/DataRecce/recce/blob/1da63a366eadac567a7bd2e153b6362cea32d91d/docs/cll-state-and-fetching.md)

**Edge versioning, point-in-time reads and stale edges**
- [P] Marquez stores column lineage in a relational table keyed on (output dataset version, output field, input dataset version, input field) with `created_at` and `updated_at`. Its traversal is a recursive CTE that first selects the latest row per field pair with `created_at <= :createdAtUntil`, giving point-in-time lineage, and bounds recursion with a `depth` parameter — [V49 column_lineage.sql](https://github.com/MarquezProject/marquez/blob/180f37b22387146187af1ef0279e3ee1d1ccd789/api/src/main/resources/marquez/db/migration/V49__column_lineage.sql), [ColumnLineageDao.java](https://github.com/MarquezProject/marquez/blob/180f37b22387146187af1ef0279e3ee1d1ccd789/api/src/main/java/marquez/db/ColumnLineageDao.java)
- [P] DataHub's common `Edge` record carries `created` and `lastModified` audit stamps so that edges "support PATCH, time-travel automatically" — [Edge.pdl](https://github.com/datahub-project/datahub/blob/7dccde9d2427cb05e02960e716cdd42b700c256b/metadata-models/src/main/pegasus/com/linkedin/common/Edge.pdl)
- [P] But DataHub's time filter is not history: "The time picker can be used to filter out edges within the latest version to exclude those that were last updated outside of the time window... will not show you historical lineages" — [DataHub lineage feature guide](https://github.com/datahub-project/datahub/blob/7dccde9d2427cb05e02960e716cdd42b700c256b/docs/features/feature-guides/lineage.md)
- [P] DataHub `incremental_lineage` turns full-aspect lineage writes into patches; the documented cost is that "lineage edges that used to exist will not be removed, and so you may need to use time-based filtering to accurately determine current lineage" — [DataHub lineage feature guide](https://github.com/datahub-project/datahub/blob/7dccde9d2427cb05e02960e716cdd42b700c256b/docs/features/feature-guides/lineage.md), [incremental_lineage_helper.py](https://github.com/datahub-project/datahub/blob/7dccde9d2427cb05e02960e716cdd42b700c256b/metadata-ingestion/src/datahub/ingestion/api/incremental_lineage_helper.py)
- [P] DataHub stateful ingestion soft-deletes entities seen in the last successful run but missing in the current one, with a fail-safe: if more than 75% of the previous run's entities are missing, removal is skipped and state is not committed — [DataHub stateful ingestion](https://github.com/datahub-project/datahub/blob/7dccde9d2427cb05e02960e716cdd42b700c256b/metadata-ingestion/docs/dev_guides/stateful.md)
- [P] DataHub's architecture note on history: the graph "always represents the current state of the world and has no direct support for versioning or history"; it is a derived view that can be rebuilt, and "it is possible to build a specific snapshot of the graph in time by replaying" the change-event log up to that point — [DataHub: what is GMA graph](https://github.com/datahub-project/datahub/blob/7dccde9d2427cb05e02960e716cdd42b700c256b/docs/what/graph.md)
- [S] Meta's Unified Lineage System paper (SIGMOD/PODS 2025 Companion, 2025-06-22) describes "techniques to stitch incomplete lineage traces" and a data model that enables navigation across granularities — [ACM DL](https://dl.acm.org/doi/10.1145/3722212.3724458)
- [S] SageMaker Unified Studio's lineage graph has two traversal modes per a third-party write-up (July 2026): a server-side mode for fast path retrieval and an "Event Timestamp" mode that is client-side and exposes field-to-field detail — [DevelopersIO](https://dev.classmethod.jp/en/articles/20260712-amazon-sagemaker-data-lineage-iam-domain/)

**Published latency and freshness figures**
- [R] Snowflake ACCESS_HISTORY: up to 3 hours latency — [Snowflake access history](https://docs.snowflake.com/en/user-guide/access-history)
- [S] Dataplex lineage: 30 minutes to 24 hours to appear per a third-party guide (Atlan); Google's own figure not found — [Atlan](https://atlan.com/know/bigquery/how-data-lineage-works/)
- [S] Unity Catalog: "near real time" (no number) — [Unity Catalog lineage](https://docs.databricks.com/aws/en/data-governance/unity-catalog/data-lineage.html)
- [R] Spotify pulls warehouse query-history metadata every 6 hours; Slack's lineage store is flattened daily by a Spark job — [Spotify](https://backstage.spotify.com/docs/portal/core-features-and-plugins/data-experience/data-lineage), [Slack](https://slack.engineering/data-lineage-at-slack/)

### Inferences
- A workable incremental design can be assembled from these parts: (1) fingerprint each statement or model on its normalised AST plus the hash of its parents' output schemas; (2) re-parse only nodes whose fingerprint changed, and re-qualify (not re-parse) nodes whose parents' schemas changed; (3) write edges as versioned rows with valid-from and valid-to, closing an edge version only on a "replace"-semantics event or on an explicit empty-inputs assertion; (4) treat runtime (accumulative) evidence as append-only observations with last-seen timestamps and apply decay.
- DataHub's documented trade-off shows why naive patch-only updates fail: without a removal signal, edges accumulate forever. Replace-semantics per (producer, target) scope, or stale-entity removal with a fail-safe threshold, is the minimum needed.
- Point-in-time lineage has two proven implementations: version-keyed relational rows queried with a timestamp bound (Marquez) and replay of an immutable change log (DataHub's stated approach). Neither is bitemporal; neither records "what we believed at time T about time T0", which matters when a parser fix retroactively changes historical edges.
- Lineage diff between commits is implemented in practice as a model-level change category plus a per-column change map (Recce, SQLMesh), not as a general graph diff. A graph-of-record can derive the same by diffing the edge sets produced under two fingerprints.
- Hash-based invalidation inherits dbt's blind spots: values injected at deploy or run time (vars, environment variables, dynamic table names) change lineage without changing the hash. Runtime evidence is the only check on these.

### Gaps
- Not found (searches for bitemporal and time-versioned lineage graphs did not run): any published design that stores lineage edges bitemporally, stale-edge TTL or decay policies with measured effect, or reconciliation algorithms between static and runtime evidence beyond Meta's "stitching" (paper not readable).
- Not found: DDL or schema-change event capture designs for lineage (CDC of `information_schema`, Schema Registry version events, Debezium schema-change topics). Not searched.
- Not found: end-to-end freshness figures for a column-level graph (time from merge or run completion to queryable edge). Meta's freshness is not stated in any extract.

## 5. Change impact analysis at pull-request time

### Takeaway
The shipped algorithms are conservative and simple: SQLMesh treats only pure projection additions as non-breaking, Recce adds a third "column-scoped" category by diffing SQLGlot scopes, and schema tools (dbt contracts, buf, Schema Registry, datacontract-cli) classify changes against fixed compatibility rules. Column-level blast radius is then graph reachability from the changed columns. No source reached reports a measured pre-merge catch rate.

### Cited Findings

**Semantic diff of SQL and change classification**
- [P] SQLGlot's semantic diff implements Change Distiller (Fluri et al.), an improvement on Chawathe et al.: build a matching set between two ASTs, then generate an edit script of Insert, Remove, Move, Update and Keep operations. Leaves match by a Dice coefficient over character bigrams with threshold 0.6; inner nodes also need at least 0.6 common-leaf ratio, relaxed to 0.4 for subtrees with four or fewer leaves, and a 0.8 leaf ratio can override a low value similarity — [sqlglot posts/sql_diff.md](https://github.com/tobymao/sqlglot/blob/ba0651085c690b8b49e9b9dba2f4a37dbb9055e0/posts/sql_diff.md)
- [S] Tobiko's description of SQLMesh's original rule: a change is non-breaking only if the edit script contains nothing but Insert and Keep, with the inserts being new projections. Named edge cases: downstream `SELECT *` (handled by expanding stars with the optimizer) and functions that change cardinality such as `explode` — [Tobiko blog](https://tobikodata.com/blog/automatically-detecting-breaking-changes-in-sql-queries)
- [P] SQLMesh's current implementation (2026-11-25) no longer uses the general tree diff for this: `_is_only_projection_additions` walks both ASTs "in lockstep", requires node types, scalar arguments and non-projection child lists to match exactly, and allows extra SELECT projections only if previous projections are unchanged and ordered and the additions pass "cardinality and ordinal-reference safeguards". The docstring says this "avoids the candidate matching performed by SQLGlot's general tree diff while remaining conservative" — [SQLMesh model definition.py](https://github.com/SQLMesh/sqlmesh/blob/ce229ae5208c2fdee667b993ef542c21e78d20c4/sqlmesh/core/model/definition.py)
- [P] For SQL models, SQLMesh's categoriser returns NON_BREAKING for a direct change only in that case; anything else returns "cannot determine", which becomes BREAKING in full auto-categorisation mode. (Seed models have an analogous column-hash rule, and an indirectly modified model whose parent data hash is unchanged is NON_BREAKING.) Docstring: "Presently the implementation only returns the NON_BREAKING category iff a new projections have been added" — [SQLMesh categorizer.py](https://github.com/SQLMesh/sqlmesh/blob/ce229ae5208c2fdee667b993ef542c21e78d20c4/sqlmesh/core/snapshot/categorizer.py)
- [P+S] Column-level categorisation in SQLMesh was announced as a direction and is an open RFC; it is not in the code read on 2026-11-25. Downstream `select *` is handled "on a best-effort basis" — [SQLMesh plans](https://github.com/SQLMesh/sqlmesh/blob/ce229ae5208c2fdee667b993ef542c21e78d20c4/docs/concepts/plans.md), [RFC issue 6062](https://github.com/SQLMesh/sqlmesh/issues/6062)
- [P] Recce's classifier qualifies old and new SQL against their schemas with SQLGlot, diffs scope by scope (CTEs, subqueries, unions) bottom-up, and returns a category plus a per-column status map (`added`, `removed`, `modified`, `unknown`). A changed source table set is breaking. The per-column map is what feeds column-level impact. It also tracks counts of SQLGlot-error nodes for observability — [Recce change_classifier.py](https://github.com/DataRecce/recce/blob/1da63a366eadac567a7bd2e153b6362cea32d91d/recce/util/change_classifier.py)
- [P] Recce shows truncated lineage chains honestly: a count badge states how many ancestry columns are hidden by the current view, because "partial lineage is no longer presented as complete". The team rejected automatic expansion, citing "CLL overwhelm" as an unresolved product concern — [Recce CLL chain truncation](https://github.com/DataRecce/recce/blob/1da63a366eadac567a7bd2e153b6362cea32d91d/docs/cll-chain-truncation.md)

**Contract and schema compatibility rules**
- [P] dbt `state:modified.contract`: "Removing or changing the type of an existing column is considered a breaking change, and will raise an error." The documented breaking list: removing an existing column, changing a column's `data_type`, removing or modifying a constraint on an existing column (dbt 1.6+) — [dbt node selection methods](https://docs.getdbt.com/reference/node-selection/methods), [dbt model contracts](https://docs.getdbt.com/docs/mesh/govern/model-contracts)
- [S] dbt issues report edge cases: a proposal that unversioned contracted models warn while versioned models error, reports that the error does not always fire for versioned models, and a report that when both contract and model SQL change, `state:modified` selects the model without raising — [dbt-core #8028](https://github.com/dbt-labs/dbt-core/issues/8028), [#8030](https://github.com/dbt-labs/dbt-core/issues/8030), [#7282](https://github.com/dbt-labs/dbt-core/issues/7282)
- [S] buf breaking-change detection has four nested categories from strictest to most lenient: FILE (default; generated-code breakage per file), PACKAGE (per package), WIRE_JSON (binary wire format or JSON encoding), WIRE (binary only). `FIELD_NO_DELETE` sits under FILE and PACKAGE; buf recommends deprecating a field rather than deleting it; WIRE_JSON is suggested for Connect, gRPC-Gateway or gRPC JSON users — [buf breaking rules](https://buf.build/docs/breaking/rules/)
- [S] Confluent Schema Registry: default compatibility is BACKWARD; `_TRANSITIVE` variants check against all earlier versions instead of only the latest; for Avro and Protobuf, adding or removing a field with a default is fully compatible; JSON Schema rules depend on open versus closed content models; for Protobuf the recommended mode is BACKWARD_TRANSITIVE because adding new message types is not forward compatible; Kafka Streams supports only BACKWARD — [Confluent schema evolution](https://docs.confluent.io/platform/current/schema-registry/fundamentals/schema-evolution.html)
- [P] datacontract-cli has `changelog` and `breaking` commands for two ODCS contract versions. `breaking` takes a `--perspective`: `consumer` (default; "will the expectations of data users break?") or `producer` ("will the next contract test fail?"), and grades each change ERROR (exit 1), WARNING or INFO — [datacontract-cli compare versions](https://github.com/datacontract/datacontract-cli/blob/08881a29a16c05e11494db4fdf5f5c572919bd31/docs/docs/compare-contract-versions.md)

**Blast-radius computation, data diff and workflow**
- [S] Column-level impact analysis is described as a graph reachability problem, needing column resolution because table-level lineage gives false alarms (renaming column_x in A does not break B if B selects only column_y) — [apxml course notes](https://apxml.com/courses/data-governance-quality-observability-production/chapter-4-data-lineage-metadata-management/impact-analysis-techniques)
- [S] One CI guide recommends taking the baseline from the deployed revision rather than querying the live catalog mid-run, since production can change while the job runs (low-authority blog, September 2026) — [oneuptime blog](https://oneuptime.com/blog/post/2026-09-07-lineage-impact-analysis-ci/markdown)
- [P] dbt Advanced CI "compare changes" complements lineage with data diff: it compares the PR build with the last production state and reports changes to primary keys, rows and columns, using `event_time` to compare only overlapping time ranges and caching at most 100 changed records per model — [dbt advanced CI](https://docs.getdbt.com/docs/deploy/advanced-ci)
- [S] Paradime's lineage diff reports structural column changes in SELECT statements, then affected dbt models and connected BI assets in the PR — [Paradime docs](https://docs.paradime.io/products/bolt/ci-cd/lineage-diff.md)
- [S, low confidence, attribution unclear] One search extract attributes to a column-lineage paper a mean impact-detection F1 of 0.93 for a column-lineage method, said to outperform table-level lineage and dbt state-based selection. The extract attached this to the wrong publication page; the figure probably belongs to the dbt-based column lineage paper cited in section 1 and is unverified — [ResearchGate 397522914](https://www.researchgate.net/publication/397522914_A_DBT-Based_Column_Lineage_Tracking_Approach_for_Regulatory_and_Audit_Compliance)
- [R] Outcome evidence, survey-based: at Shopify, teams that understood the impact of their changes rose from 16% to 46% after its discovery and lineage tool — [Shopify engineering](https://shopify.engineering/solving-data-discovery-challenges-shopify)

### Inferences
- A PR-time algorithm supported by the evidence: (1) for each changed model or schema, compute a per-column change map (added, removed, modified, unknown) and a model-wide flag for row-set changes; (2) seed the graph traversal with removed and modified columns over DIRECT edges, and with the whole dataset over INDIRECT edges when the model-wide flag is set; (3) intersect with schema-compatibility verdicts (buf, registry mode, contract diff) at serialisation boundaries; (4) report "unknown" explicitly where parsing failed.
- Registry compatibility modes do not catch field renames across the service-to-stream boundary: under Avro BACKWARD, a rename looks like "remove a field, add a field with a default", both allowed individually. Lineage-based consumer lookup is what catches it. This follows from the Confluent rules above; it is an inference, not a cited result.
- The consumer versus producer perspective in datacontract-cli is a useful design idea for any gate: the same diff can be safe for the producer's tests and breaking for consumers.
- Ranking and alert-fatigue controls have to be designed without published guidance. Reasonable signals implied by the sources: edge class (direct before indirect), edge confidence, hop distance, asset tier and observed usage; plus Recce's lesson that expanding everything overwhelms reviewers.

### Gaps
- Not found: any published pre-merge catch rate, false-positive rate or precision of PR impact reports; any published ranking algorithm for affected assets (tier, usage, hop distance); alert-fatigue measurements. Searches on these did not run.
- Tobiko's post could not be opened; the description above is from a search extract, cross-checked against current SQLMesh source.
- Exact buf rule-to-category mapping should be checked on buf's rules page; third-party listings disagreed with the official page in the extract.

## 6. Incident root-cause analysis with lineage

### Takeaway
Industry practice is a heuristic: walk upstream to the most-upstream node whose failure or change aligns in time with the symptom, then correlate with code and schema changes. The only rigorous evaluation found is the 2026 DataTrace benchmark, where seven frontier LLM agents averaged 48% root-cause accuracy and accuracy fell as lineage distance grew. The commonly quoted detect and resolve times come from two vendor-commissioned surveys, and no independent study isolating lineage's effect on MTTR was found.

### Cited Findings

**Survey numbers and their provenance**
- [S] 2022: Wakefield Research for Monte Carlo surveyed "more than 300 data engineers"; most respondents take 4 hours or more to detect an incident and about 9 hours on average to resolve one. **Survey-based, vendor-commissioned, self-reported** — [VentureBeat coverage](https://venturebeat.com/ai/data-downtime-almost-doubles-as-professionals-struggle-with-quality-issues-survey-finds)
- [S] 2023: same sponsor and pollster, 200 data professionals, fielded March 2023; share taking 4 hours or more to detect rose to 68% from 62%; average time to resolution rose from 9 to 15 hours; "data downtime" nearly doubled year over year (1.89x) — [TDWI, 2023-05-04](https://tdwi.org/articles/2023/05/04/data-downtime-nearly-doubled-survey.aspx), [Monte Carlo report page](https://info.montecarlodata.com/state-of-data-quality-2023/)
- [S] Coverage describes the 9 to 15 hour change as a "166% increase". Arithmetically 15/9 is 1.67x, a 67% increase; the widely repeated "166%" appears to be the ratio misstated as an increase — [VentureBeat coverage](https://venturebeat.com/ai/data-downtime-almost-doubles-as-professionals-struggle-with-quality-issues-survey-finds)

**Algorithms described in practice**
- [S] Lineage-traversal heuristic (Atlan, MCP-based agent): "The root cause is the most-upstream node whose change or failure timeline aligns with the downstream symptom"; then map blast radius downstream; the report should include a confidence note tied to lineage completeness — [Atlan](https://atlan.com/know/mcp/data-lineage-rca-with-mcp.md)
- [S] Change correlation (Sifflet, vendor): the agent correlates "lineage, code changes, and metric drift" — [Sifflet](https://www.siffletdata.com/product-agents)
- [S] Graph-diff approach (US patent 10,776,740): generate the upstream lineage graph of the affected asset before and after the quality issue and detect a potential root cause from the difference between the two graphs — [USPTO](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/10776740)
- [S] Consultant-reported outcomes (LatentView): 2025 deployments "cluster around 50 to 70% reduction in mean time to resolution for known defect patterns" and 30-40% fewer alerts after agent-led triage. Named risks: false-positive auto-closure, root-cause hallucination on novel incidents, and "lineage gaps that produce wrong diagnoses". **Not independently verified** — [LatentView](https://www.latentview.com/blog/agentic-ai-for-data-quality/)
- [R] Uber uses lineage to scope bad-table impact, notify recent users and auto-generate upstream and downstream tests; Yelp uses job-level lineage for incident freeze and backfill; Airbnb for SLA debugging of upstream delays — [Uber](https://www.uber.com/in/en/blog/operational-excellence-data-quality/), [Yelp](https://engineeringblog.yelp.com/2022/08/spark-data-lineage.html), [Airbnb](https://medium.com/airbnb-engineering/metis-building-airbnbs-next-generation-data-management-platform-d2c5219edf19)

**Evaluations**
- [P] DataTrace (HKUST; repository of July 2026, arXiv November 2026) benchmarks agents on root-cause localisation in database pipelines. Each task has a faulty object (source column, transformation, constraint or query) and a symptom elsewhere; the pipeline is a typed artifact graph (schemas, data, queries, constraints, plans, tests, logs, issue reports) with lineage recovered via SQLGlot. Faults are injected (null, duplicate primary key, join key, rename, temporal and others), so root cause and a "reference evidence path" are known without human annotation. Corpus: 83 runnable environments, 62 domains, seven fault types — [DataTrace README](https://github.com/HKUSTDial/datatrace/blob/48a89e59b4aeef5a01d5ed68c1a1b4d4dc84a411/README.md), [arXiv 2611.18926](https://arxiv.org/abs/2611.18926)
- [P] DataTrace leaderboard on a frozen 64-task x 2 corpus (128 episodes per model, seven proprietary models): top-1 root-cause accuracy (RC@1) ranged from 0.195 to 0.688, mean 0.481; "grounded" accuracy (correct and at least half the evidence path inspected) ranged from 0.164 to 0.586. Best: RC@1 0.688, 95% CI 0.564-0.806. Fix rate for the best model was 0.320. **Measured, academic** — [DataTrace analysis](https://github.com/HKUSTDial/datatrace/blob/48a89e59b4aeef5a01d5ed68c1a1b4d4dc84a411/leaderboard/analysis/proprietary_board_analysis.md), [leaderboard](https://github.com/HKUSTDial/datatrace/blob/48a89e59b4aeef5a01d5ed68c1a1b4d4dc84a411/leaderboard/leaderboard.md)
- [P] Unsupported correct answers: among correct diagnoses, 15-23% per model were not backed by the evidence inspected; in a regression on correct episodes, each extra node on the reference path raised the log-odds of an ungrounded answer by 0.889 — [DataTrace analysis](https://github.com/HKUSTDial/datatrace/blob/48a89e59b4aeef5a01d5ed68c1a1b4d4dc84a411/leaderboard/analysis/proprietary_board_analysis.md)
- [S] From the arXiv version: root-cause accuracy declines as lineage distance grows (the five-hop estimate rests on few cases); agents "can often name a root cause from error-text clues without tracing dependencies" and "rely on lineage, data, and code to localize while rarely consulting incident reports"; in-loop training raised grounded correct diagnoses from 83.7% to 94.6% and root-cause accuracy from 29.2% to 36.7% — [arXiv 2611.18926](https://arxiv.org/abs/2611.18926)
- [S] Adjacent microservice work uses the same shape (dependency graph plus ranking): GALA (arXiv, 2026) guides LLM agents with a service dependency graph and reports AC@1, AC@3 and MRR; NetCause (arXiv, 2026) ranks hypotheses over an incident graph with a reported 16.1% accuracy gain over a rule-based baseline — [GALA](https://arxiv.org/pdf/2608.08968), [NetCause](https://arxiv.org/pdf/2606.13543)
- [S, unverifiable] A ResearchGate preprint claims "up to 40%" improvement in root-cause identification accuracy from AI-powered pipeline observability; no venue confirmed — [ResearchGate 404313953](https://www.researchgate.net/publication/404313953_AI-powered_Data_Pipeline_Observability_and_Root_Cause_Analysis)

### Inferences
- An RCA service supported by this evidence should be deterministic first: traverse upstream over confirmed edges to the earliest node with a failing check or a change event inside the incident window, rank candidates by temporal alignment, edge class and hop distance, and only then hand a bounded evidence set to an LLM for explanation. DataTrace shows agents alone are right about half the time and get worse with distance.
- Report the evidence path with every diagnosis and score it. DataTrace's finding that 15-23% of correct answers were unsupported means a plausible-sounding RCA cannot be trusted on accuracy alone; "show the path" is the control.
- RCA needs the graph as it was at incident time (section 4) and change events on the same timeline as data-quality signals; the patent's before-and-after graph diff presupposes versioned lineage.
- Use RC@1 or AC@k and MRR over replayed historical incidents as the acceptance metric for an RCA service; this is the convention in both the data and microservice literature.
- Baselines for MTTD and MTTR must be measured locally. The 4 / 9 / 15 hour figures are self-reported survey answers from a vendor's sample and are not a benchmark.

### Gaps
- Not found: causal or Bayesian root-cause ranking evaluated on data lineage graphs; any independent (non-vendor) measurement of MTTD or MTTR change attributable to lineage; RCA automation detail from Monte Carlo, Datadog, Bigeye, Uber, LinkedIn or Airbnb beyond the lines above. The academic RCA search ran once; follow-ups did not run.
- The DataTrace per-hop accuracy table and the "Agentic Self-Healing for Data & AI Pipelines" paper ([arXiv 2608.01955](https://arxiv.org/html/2608.01955v1)) were not readable.

## 7. Measuring lineage accuracy

### Takeaway
Practice is golden tests per extractor plus self-reported confidence; there is no accepted public benchmark for column-level lineage with per-edge-type precision and recall. The closest public artefacts are SLiCE (a composite similarity metric and dataset for schema lineage) and DataTrace (which evaluates use of lineage, not its extraction).

### Cited Findings
- [P] Golden tests against real engine plans: OpenLineage's Spark tests (`ColumnLevelLineageUtilsNonV2CatalogTest`, `ColumnLevelLineageUtilsV2CatalogTest`) "run Spark jobs and get an access to the last query plan executed", compute column lineage and verify it against the expected output — [OpenLineage Spark column lineage](https://openlineage.io/docs/integrations/spark/spark_column_lineage)
- [P] Vendor benchmark without method: DataHub's "97-99% accuracy" claim (see section 1) — [DataHub SQL parsing](https://docs.datahub.com/docs/lineage/sql_parsing)
- [S] DataHub has published a comparison table of SQL lineage accuracy for DataHub, sqllineage and openlineage-sql across SELECT and CTAS at table and column level; numbers not retrieved — [DataHub blog](https://datahub.com/?p=11072)
- [P] Per-edge quality signals in a production metadata model: DataHub `FineGrainedLineage.confidenceScore` (0-1) and `matchType` (`EXACT`, `NORMALIZED` if a casing mismatch was healed, `UNRESOLVED` if an upstream reference could not be resolved); the parser returns a per-query `confidence_score` — [FineGrainedLineage.pdl](https://github.com/datahub-project/datahub/blob/7dccde9d2427cb05e02960e716cdd42b700c256b/metadata-models/src/main/pegasus/com/linkedin/dataset/FineGrainedLineage.pdl), [DataHub SQL parsing](https://docs.datahub.com/docs/lineage/sql_parsing)
- [P] Surfacing incompleteness: dbt shows a warning in column lineage when parsing fails, with distinct "parsing error" and "Python error" reasons; Recce tracks counts of nodes with SQLGlot errors and marks unresolved columns `unknown` — [dbt column-level lineage](https://docs.getdbt.com/docs/explore/column-level-lineage), [Recce change_classifier.py](https://github.com/DataRecce/recce/blob/1da63a366eadac567a7bd2e153b6362cea32d91d/recce/util/change_classifier.py)
- [P] SLiCE evaluates predicted lineage against gold standards component by component (source schema, source tables, transformations, aggregations) — [microsoft/SLiCE](https://github.com/microsoft/SLiCE/blob/7b866f8a93517a86358f6be979bfdea738126722/README.md)
- [S] "An open dataset of data lineage graphs for data governance research" (Chen, Zhao; 2024) exists; contents not read — [Semantic Scholar](https://www.semanticscholar.org/paper/An-open-dataset-of-data-lineage-graphs-for-data-Chen-Zhao/65de365324970be01e52ceb8ccbfd77e2e962dc9)
- [S, low confidence] The dbt-based column lineage paper reports edge-level precision and recall with 95% confidence intervals on a 400-edge ground truth (see section 1), which is the evaluation shape a build should copy — [ResearchGate 397522914](https://www.researchgate.net/publication/397522914_A_DBT-Based_Column_Lineage_Tracking_Approach_for_Regulatory_and_Audit_Compliance)
- [P] DataTrace's scoring separates outcome (RC@1, fix rate) from evidence (evidence recall, precision, F1, and a "lucky guess" rate) — [DataTrace README](https://github.com/HKUSTDial/datatrace/blob/48a89e59b4aeef5a01d5ed68c1a1b4d4dc84a411/README.md)
- [S] Meta authors state that static and runtime approaches each have false positives and false negatives, which is the stated reason for combining them — [PEPR 2024](https://usenix.org/conference/pepr24/presentation/kim)

### Inferences
- Measure four things separately, since the sources show they fail independently: extractor correctness (golden edges per statement type), identity resolution (share of references resolved EXACT versus NORMALIZED versus UNRESOLVED), coverage (share of statements or jobs that parsed without error or "unknown"), and usefulness (replay of past changes and incidents, scored with RC@1 or catch rate).
- Report precision and recall per edge class (direct, indirect) and per producer, with confidence intervals, on a sampled golden set of a few hundred edges; 400 edges gave intervals of about plus or minus 2-3 points in the one paper found.
- Static-versus-runtime disagreement is itself a measurable accuracy signal: an edge seen by a parser and never at runtime is a candidate false positive or dormant path; a runtime edge with no static counterpart is a parser gap or an undeclared consumer.

### Gaps
- Not found: a public benchmark or dataset for column-level lineage extraction with ground-truth edges across SQL dialects, Spark or Python; any standard coverage metric definition; published static-versus-runtime reconciliation rates. Searches did not run after the budget was exhausted.

## 8. Identity resolution across systems at field level

### Takeaway
Field identity in the two open models is "dataset identity plus field path": OpenLineage uses (namespace, name, field) with per-platform naming rules, and DataHub uses a schemaField URN whose v2 field path encodes nesting, union member and key-versus-value schema. Mismatched casing and account-identifier formats silently break joins, and neither model defines how a JSON path, an Avro field and a warehouse column that carry the same value are recognised as related; that link is a lineage edge, not an identity.

### Cited Findings
- [P] OpenLineage dataset naming (namespace, name) per platform, for example: Kafka `kafka://{bootstrap server host}:{port}` + `{topic}`; Postgres `postgres://{host}:{port}` + `{database}.{schema}.{table}`; BigQuery `bigquery` + `{project id}.{dataset name}.{table name}`; AWS Glue `arn:aws:glue:{region}:{account id}` + `table/{database name}/{table name}`; Snowflake `snowflake://{organization name}-{account name}` or the legacy account-locator form + `{database}.{schema}.{table}` — [OpenLineage naming](https://openlineage.io/docs/spec/naming)
- [P] A column is addressed as dataset namespace + dataset name + `field`; there is no separate field URN in OpenLineage — [ColumnLineageDatasetFacet.json](https://github.com/OpenLineage/OpenLineage/blob/b9cd9fd9c323af31807d130eb2c7db23998d7f3c/spec/facets/ColumnLineageDatasetFacet.json)
- [P+S] Snowflake is called out as "a special case where we don't have a single standardized namespace"; IDs created with the legacy locator format will not match IDs created with the org-account format, so switching later disconnects existing lineage nodes — [OpenLineage naming](https://openlineage.io/docs/spec/naming)
- [P] Alternate identities are handled with symlinks: OpenLineage has a `SymlinksDatasetFacet`, static lineage lists "creating dataset symlinks more easily" as a use case, and Marquez's column-lineage lookup matches requested datasets against `dataset_symlinks` — [static lineage blog](https://openlineage.io/blog/static-lineage/), [ColumnLineageDao.java](https://github.com/MarquezProject/marquez/blob/180f37b22387146187af1ef0279e3ee1d1ccd789/api/src/main/java/marquez/db/ColumnLineageDao.java)
- [P] Streaming identity mismatch: Flink jobs "can read Kafka topics based on regex patterns, while OpenLineage expects each topic being identified as a separate dataset" — [OpenLineage Flink blog, 2024-11-15](https://openlineage.io/blog/flink-native-support)
- [S] DataHub schemaField URN is the parent dataset URN plus an encoded field path; fine-grained lineage uses schemaField URNs on both ends — [DataHub schemaField entity](https://docs.datahub.com/docs/generated/metamodel/entities/schemafield)
- [P] DataHub fieldPath v2 grammar: `[version=2.0].[key=True].<type-prefixed path>`, where each token carries the type (`[type=union]`, `[type=<record name>]`, `[type=string]` and so on). Requirements: unique across all fields in a schema, identify key schema versus value schema, allow evolution. Example: two union members each with a field `f` become `[version=2.0].[type=union].[type=A].[type=string].f` and `...[type=B].[type=string].f`. v1 (dot-delimited names) cannot distinguish them — [field-path-spec-v2](https://github.com/datahub-project/datahub/blob/7dccde9d2427cb05e02960e716cdd42b700c256b/docs/advanced/field-path-spec-v2.md)
- [S] In practice the encoding varies by source: Glue and Hive ingestion store v2 paths such as `[version=2.0].[type=int].eff_dt`, while Snowflake and Teradata store the plain column name; the support guidance is to read the stored schema rather than construct paths by hand — [DataHub support article](https://support.datahub.com/hc/en-us/articles/52984918574107-Constructing-v2-Schema-Field-Paths-for-Glue-Hive-Datasets-When-Using-the-OpenAPI)
- [P] DataHub URNs are "exact, case-sensitive strings"; a warehouse reporting uppercase and a BI tool reporting lowercase yield "two orphaned nodes", and "a single broken edge in the middle of a chain hides the entire downstream path". Blanket lowercasing (`convert_urns_to_lowercase`) must be enabled consistently across all sources, is unavailable on some BI connectors, and "can even merge two genuinely different tables". The recommended alternative resolves each upstream reference to the casing of the entity that already exists, only "when the match is unambiguous", and records the outcome in `matchType` — [DataHub lineage URN casing](https://github.com/datahub-project/datahub/blob/7dccde9d2427cb05e02960e716cdd42b700c256b/metadata-ingestion/docs/dev_guides/lineage_urn_casing.md)
- [P] Rename and alias handling at dataset level: DataHub's aggregator resolves temp tables and table renames or swaps; BigQuery sharded tables are normalised (`table_20230616` to `table_yyyymmdd`) so lineage links up — [DataHub SQL parsing](https://docs.datahub.com/docs/lineage/sql_parsing)
- [P] Rename handling at column level in lineage semantics: dbt labels hops as "Passthrough" or "Rename" versus transformed — [dbt column-level lineage](https://docs.getdbt.com/docs/explore/column-level-lineage)
- [S] Guidance on serialisation boundaries: keep the topic schema field and the table column as separate identities and connect them with a column-lineage edge (low-authority source) — [oneuptime blog](https://oneuptime.com/blog/post/2026-09-08-batch-streaming-lineage-one-metadata-graph/markdown)

### Inferences
- Use the dataset identity rules of OpenLineage for interoperability and append a field path that can express nesting, arrays, map values, union members and key versus value (the DataHub v2 requirements). A flat column name is insufficient for Avro, protobuf and JSON payloads.
- Never normalise identity destructively. Store the canonical (as-catalogued) name, resolve incoming references against the existing entity, and record the match type; unresolved references should stay visible rather than create silent orphans.
- Pin one namespace form per platform before the first event is emitted (the Snowflake case shows the migration cost), and use symlinks for physical-location aliases.
- Field renames across schema versions need an explicit "renamed-from" assertion: neither Avro compatibility checks nor the URN schemes carry it, though protobuf field numbers and Avro aliases can supply it where used. This is an inference; no source found addresses it directly.

### Gaps
- Not found (not searched): a published scheme for matching JSON path to Avro field to column across serialisation boundaries; field-level rename tracking across Schema Registry versions; how Meta keys fields in its asset identity model.

## 9. Graph storage patterns for element-level lineage at scale

### Takeaway
Public systems use every pattern: relational adjacency with recursive CTEs (Marquez on Postgres), a document or key-value store plus a search index with the graph as a rebuildable derived view (DataHub, Uber), property graphs (Airbnb on JanusGraph, Amundsen on Neo4j, an AWS reference on Neptune) and, at the extreme, a custom in-memory graph (Meta, billions of edges). No source reached compares these for column-level workloads, and nothing was found on Neptune Analytics, OpenSearch, Aurora with Apache AGE or Iceberg as lineage stores.

### Cited Findings
- [P] Relational adjacency: Marquez's `column_lineage` table (schema in section 4) with a recursive CTE for traversal, a `depth` bound and a `created_at` upper bound for point-in-time reads; additional indexes were added in later migrations — [V49 column_lineage.sql](https://github.com/MarquezProject/marquez/blob/180f37b22387146187af1ef0279e3ee1d1ccd789/api/src/main/resources/marquez/db/migration/V49__column_lineage.sql), [ColumnLineageDao.java](https://github.com/MarquezProject/marquez/blob/180f37b22387146187af1ef0279e3ee1d1ccd789/api/src/main/java/marquez/db/ColumnLineageDao.java)
- [P] Derived-view pattern: DataHub's components doc lists "MySQL, Elasticsearch, & Kafka for primary storage & indexing"; a change-log consumer applies each metadata change to the graph and search index; column lineage is stored inside the `upstreamLineage` aspect with upstream field URNs indexed as a searchable field (`fineGrainedUpstreams`) — [DataHub components](https://github.com/datahub-project/datahub/blob/7dccde9d2427cb05e02960e716cdd42b700c256b/docs/components.md), [metadata serving](https://github.com/datahub-project/datahub/blob/7dccde9d2427cb05e02960e716cdd42b700c256b/docs/architecture/metadata-serving.md), [FineGrainedLineage.pdl](https://github.com/datahub-project/datahub/blob/7dccde9d2427cb05e02960e716cdd42b700c256b/metadata-models/src/main/pegasus/com/linkedin/dataset/FineGrainedLineage.pdl)
- [P] DataHub's stated graph-store requirements: efficient queries combining traversal with property filtering, and efficient bidirectional traversal; the graph holds current state only and can be rebuilt from the event log — [DataHub: what is GMA graph](https://github.com/datahub-project/datahub/blob/7dccde9d2427cb05e02960e716cdd42b700c256b/docs/what/graph.md)
- [S] Meta's Unified Lineage System lineage graph has "billions of nodes and edges" and supports over a hundred use cases (SIGMOD/PODS Companion, June 2025) — [ACM DL](https://dl.acm.org/doi/10.1145/3722212.3724458)
- [S] A Meta talk at USENIX PEPR 2026 (Jha), "Architecting Scalable Data Lineage Graph for Privacy Compliance and Agentic Analysis", describes an in-memory lineage graph that processes billions of edges across web, warehouse and AI systems — [PEPR 2026](https://www.usenix.org/conference/pepr26/presentation/jha)
- [R] Reported scales and stores elsewhere, mostly table-level: Airbnb on JanusGraph with 100M+ nodes and 300M+ edges; Slack on MySQL, flattened daily by a Spark GraphX job; Uber on Cassandra plus Elasticsearch; Lyft Amundsen on Neo4j plus Elasticsearch; Yelp on Kafka then Redshift — [Airbnb](https://medium.com/airbnb-engineering/metis-building-airbnbs-next-generation-data-management-platform-d2c5219edf19), [Slack](https://slack.engineering/data-lineage-at-slack/), [Uber Databook](https://www.uber.com/blog/databook), [Amundsen](https://github.com/amundsen-io/amundsen/blob/master/docs/architecture.md), [Yelp](https://engineeringblog.yelp.com/2022/08/spark-data-lineage.html)
- [S] AWS: a Big Data Blog reference architecture stores lineage built from AWS Glue and Spline in Amazon Neptune for analysis and visualisation — [AWS Big Data Blog](https://aws.amazon.com/blogs/big-data/build-data-lineage-for-data-lakes-using-aws-glue-amazon-neptune-and-spline)
- [S] AWS: a Builder Center post lists "Amazon SageMaker Catalog (lineage API), optionally Amazon Neptune as the system of record". SageMaker Unified Studio / DataZone lineage is OpenLineage-compatible (GA December 2024), accepts events via `PostLineageEvent`, and gained support in IAM-based domains in July 2026. How SageMaker Catalog stores lineage internally is not documented in any extract — [AWS Builder Center](https://builder.aws.com/content/3LST69fUL0lex3G5yZCtnUUbtdw/data-lineage-you-can-defend-part-2-ai-assisted-lineage-on-aws), [AWS What's New, 2026-07](https://aws.amazon.com/about-aws/whats-new/2026/07/amazon-sagemaker-data-lineage-iam-domain)
- [R] SageMaker and Dataplex accept runtime RunEvents only, not static JobEvents; Dataplex keeps 30 days of lineage history — [SageMaker lineage docs](https://docs.aws.amazon.com/sagemaker-unified-studio/latest/userguide/datazone-data-lineage-what-is-openlineage.html), [Dataplex](https://docs.cloud.google.com/dataplex/docs/about-data-lineage)
- [S] A platform-side cap worth noting for edge volume: Dataplex drops to table-level lineage when one job creates more than 1,500 column-level links — [Dataplex lineage views](https://docs.cloud.google.com/dataplex/docs/lineage-views)
- [P] A size data point for column-level maps: 1,796 nodes with 15,520 columns (17,316 map entries) serialise to about 15.6 MB of JSON, about 0.9 KB per entry — [Recce CLL state and fetching](https://github.com/DataRecce/recce/blob/1da63a366eadac567a7bd2e153b6362cea32d91d/docs/cll-state-and-fetching.md)

### Inferences
- Column-level lineage multiplies graph size by the average column count (about 8.6 columns per node in the Recce sample, far more in wide warehouse tables), so a store sized for table-level lineage will be off by one to two orders of magnitude. Fanning indirect dependencies out to every output column makes it worse (section 3).
- The pattern that recurs in durable systems is an immutable event or evidence log as the system of record, with the queryable graph as a rebuildable projection. This also gives history by replay, which no graph database in the sources provides natively.
- Impact and RCA queries need: bidirectional multi-hop traversal with property filters (edge class, confidence, validity interval), a hop bound, and an "as of" bound. Marquez shows these are expressible as recursive SQL at modest scale; the Meta sources imply that at billions of edges a specialised in-memory representation was needed.
- For an AWS build, the evidence supports only this much: Neptune has an AWS-published lineage pattern, and SageMaker Catalog can be a projection target but rejects static events. Aurora PostgreSQL with recursive CTEs is a defensible small-scale start because Marquez proves the pattern; this is an inference, not an AWS recommendation.

### Gaps
- Not found (searches did not run): node and edge counts for any column-level lineage graph outside Meta; any benchmark of property graph versus relational versus RDF for lineage traversal; lineage on Neptune Analytics, OpenSearch, Aurora with Apache AGE, or Iceberg tables; time-versioned graph implementations on Neptune.
- The Meta PEPR 2026 talk abstract and the ULS paper could not be opened, so the in-memory design, freshness and query latencies are unknown.

## 10. Field-level lineage in streaming and services

### Takeaway
As of November 2026 no open standard or open-source integration delivers runtime field-level lineage for Flink (DataStream or SQL), Kafka Streams, Kafka Connect SMTs or microservices. Flink exposes dataset-level lineage natively with field lists but no mapping; Flink SQL column lineage is a proposed extension. Meta is the only organisation with public evidence of field-relevant lineage through services, and it relies on a shared instrumentation library plus payload-level signals.

### Cited Findings
- [P] Flink history: lineage interface definitions landed in Flink core in 1.19 (a Flink Jira issue surfaced by search says 1.20; not reconciled); the mechanism that builds a lineage graph from sources and sinks and exposes it through the job status listener was "merged to Flink's main branch and will be released in Flink 2.0" (post of 2024-11-15). The listed next step was to "design and implement column level lineage for Flink SQL" — [OpenLineage Flink blog](https://openlineage.io/blog/flink-native-support)
- [P] Flink 2.x today: OpenLineage's listener reads the `LineageGraph` from `JobCreatedEvent`; no job code change is needed and Flink SQL is supported at dataset level. Lineage depends on each connector implementing the interfaces; the OpenLineage doc says "Currently, only the Kafka connector supports this functionality", while Flink's own doc says the community "will gradually support all of the common connectors, such as Kafka, JDBC, Cassandra, Hive" — [OpenLineage Flink 2.x](https://openlineage.io/docs/integrations/flink/flink2), [Flink data lineage doc](https://github.com/apache/flink/blob/055ae9cd0d4a876bd19be18da94aa13ee62062c1/docs/content/docs/internals/data_lineage.md)
- [S] Connector coverage is uneven: Paimon documents implementing `LineageVertexProvider` (Flink 2.0+), while a Flink Jira issue notes that none of the CDC source connectors implemented it when filed. This partly conflicts with the "only Kafka" statement above, which may be stale — [Paimon docs](https://paimon.apache.org/docs/master/flink/lineage)
- [P] Flink 1.x integration (1.15 to 1.18): relied on reflection into private members, required a job code change, did not support Flink SQL; supported Kafka sources and sinks with Avro and Protobuf — [OpenLineage Flink blog](https://openlineage.io/blog/flink-native-support)
- [P] Column level: not in Flink's interfaces; "difficult to extract for the transformations defined through the programming language" (DataStream); possible for Flink SQL via a proposed Flink extension — [OpenLineage Flink 2.x](https://openlineage.io/docs/integrations/flink/flink2)
- [S] A Kafka Summit London 2024 talk on OpenLineage for stream processing states that column-level lineage for Flink "is a hard problem", that SQL may be easier, that UDFs "definitely break simple solutions", and that connectors are "responsible for their own lineage" — [Kafka Summit talk slides](https://www.slideshare.net/slideshow/openlineage-for-stream-processing-kafka-summit-london/267075881)
- [P] OpenLineage's model has room for these runtimes: STREAMING jobs (Kafka Streams, Flink) emitting periodic snapshot events, and SERVICE jobs (microservices, API services) emitting periodic or per-request events; explicit lineage facets add job-to-job flow for "streaming handoffs" with no intermediate dataset — [OpenLineage run cycle](https://github.com/OpenLineage/OpenLineage/blob/b9cd9fd9c323af31807d130eb2c7db23998d7f3c/website/docs/spec/run-cycle.md), [explicit lineage blog](https://openlineage.io/blog/explicit-lineage)
- [S] Kafka-native tooling does not read message contents and so cannot show field-to-field flow between topics; catalogs show column lineage only for jobs that report it — [Conduktor blog](https://www.conduktor.io/blog/kafka-data-lineage-tools)
- [R] Confluent Stream Lineage and OpenTelemetry messaging spans are topic- or service-level, not field-level; Confluent data-contract rules run in client serializers only, not in Kafka Connect, Flink SQL or ksqlDB — [Confluent Stream Lineage](https://docs.confluent.io/cloud/current/stream-governance/stream-lineage.html), [Confluent data contracts](https://docs.confluent.io/cloud/current/sr/fundamentals/data-contracts.html)
- [S+R] Meta: runtime Privacy Probes in shared frameworks (logger, RPC), static analysis across languages, and from 2025-2026 a single shared library (PrivacyLib) that wraps reads, writes and remote calls and emits to a central graph; signals span web probes, logger, batch processing, RPC lineage and training manifests — [Meta, 2025-01](https://engineering.fb.com/2025/01/22/security/how-meta-discovers-data-flows-via-lineage-at-scale/), [Meta, 2025-10](https://engineering.fb.com/2025/10/23/security/scaling-privacy-infrastructure-for-genai-product-innovation/), [Meta, 2026-10](https://engineering.fb.com/2026/10/27/security/privacylib/)
- [R] Netflix Inca traces messages (not fields) through Kafka with a message ID header, about 2 billion traces a day — [Netflix TechBlog](https://netflixtechblog.medium.com/inca-message-tracing-and-loss-detection-for-streaming-data-netflix-de4836fc38c9)
- [R] ML hops: Feast `apply` and `materialize` emit OpenLineage; Databricks feature lineage is lost if a model is logged outside the feature client; MLflow dataset logging records only what the user supplies — [Feast](https://docs.feast.dev/reference/openlineage), [Databricks](https://docs.databricks.com/aws/en/machine-learning/feature-store/lineage), [MLflow](https://mlflow.org/docs/latest/ml/dataset/)

### Inferences
- For Flink SQL, column lineage is obtainable today only outside the runtime: plan the statements in CI and read column origins from the planner, or parse the SQL with a Flink-dialect parser. For DataStream jobs, Kafka Streams topologies and Connect SMT chains, the realistic sources are static code rules plus declared mappings, with owner verification for critical paths.
- Field-level edges on service and stream hops should be stored with lower confidence than warehouse edges and a distinct evidence type, because runtime evidence on those hops confirms only the dataset-level edge.
- A shared serialisation or I/O library (the Meta pattern) is the only approach with production evidence for reaching services; the OpenLineage SERVICE job type gives a standard envelope for what such a library emits.

### Gaps
- Not found (searches did not run or returned nothing): field-level lineage for Kafka Streams topologies, Kafka Connect SMT chains, ksqlDB, protobuf / gRPC services, GraphQL resolvers or REST handlers; field-level technique detail from LinkedIn, Uber, Stripe, Airbnb, Grab, DoorDash or Pinterest. The single multi-company search returned only Netflix as a primary source.
- The Flink PR and design document for SQL column lineage were not readable; their status in November 2026 is unknown beyond "not in master".

## Synthesis: technique-by-layer matrix, recommended design patterns, open questions

### Takeaway
The evidence supports a layered build: deterministic parsers and engine plans where they exist, static code analysis and declared mappings where they do not, runtime evidence to confirm and decay, and every edge carrying its class (direct or indirect), evidence type and confidence. It does not yet support numeric accuracy targets from the literature; those have to be measured on a local golden set.

### Cited Findings
All findings used below are cited in sections 1 to 10; no new facts are introduced here. The key anchors are: OpenLineage facet semantics and explicit lineage ([spec](https://github.com/OpenLineage/OpenLineage/blob/b9cd9fd9c323af31807d130eb2c7db23998d7f3c/spec/facets/LineageFacet.json)), Flink's dataset-only lineage ([Flink source](https://github.com/apache/flink/blob/055ae9cd0d4a876bd19be18da94aa13ee62062c1/flink-runtime/src/main/java/org/apache/flink/streaming/api/lineage/LineageEdge.java)), DataHub parser limits and the 97-99% vendor claim ([docs](https://docs.datahub.com/docs/lineage/sql_parsing)), SQLMesh and Recce change classification ([SQLMesh](https://github.com/SQLMesh/sqlmesh/blob/ce229ae5208c2fdee667b993ef542c21e78d20c4/sqlmesh/core/snapshot/categorizer.py), [Recce](https://github.com/DataRecce/recce/blob/1da63a366eadac567a7bd2e153b6362cea32d91d/recce/util/change_classifier.py)), Marquez point-in-time column lineage ([DAO](https://github.com/MarquezProject/marquez/blob/180f37b22387146187af1ef0279e3ee1d1ccd789/api/src/main/java/marquez/db/ColumnLineageDao.java)), and DataTrace RCA results ([analysis](https://github.com/HKUSTDial/datatrace/blob/48a89e59b4aeef5a01d5ed68c1a1b4d4dc84a411/leaderboard/analysis/proprietary_board_analysis.md)).

**(b) Design patterns recommended by the evidence**

Incremental lineage
1. Use one event envelope with defined merge semantics: observed (run) evidence accumulates; declared and static evidence replaces the previous statement for the same (producer, target) scope; an explicit empty-inputs assertion removes edges. (OpenLineage explicit lineage.)
2. Fingerprint each parse unit on its normalised AST and include parent hashes; re-parse only changed units and propagate "indirectly modified" status downstream. Formatting-only edits must not change the fingerprint. (SQLMesh, dbt state.)
3. Keep schemas versioned alongside code, because qualification, star expansion and case resolution depend on the schema at that time. (DataHub parser limits.)
4. Store edges as versioned rows with timestamps and read lineage with an "as of" bound; keep the raw event log as the system of record so the graph can be rebuilt and replayed. (Marquez, DataHub.)
5. Do not rely on patch-only updates: pair them with last-seen timestamps and a stale-removal rule that has a fail-safe threshold. (DataHub incremental lineage and stateful ingestion.)
6. Add runtime reconciliation for what hashes cannot see: variables, environment values and dynamic names. (dbt caveats.)

PR-time impact
7. Classify each change into at least three classes with a per-column map: additive, column-scoped, model-wide; add an explicit unknown. (Recce; SQLMesh for the conservative default.)
8. Seed traversal by class: column-scoped changes follow DIRECT edges; model-wide changes (filters, joins, grouping, DISTINCT, cardinality-changing functions) mark the whole downstream dataset. (Recce, SQLMesh, OpenLineage types.)
9. Run schema-compatibility checks at every serialisation boundary and choose the rule set by consumer type: buf WIRE_JSON or stricter for protobuf, transitive registry modes for long-lived topics, contract diff from the consumer's perspective. (buf, Confluent, datacontract-cli.)
10. Use lineage to find consumers of renamed fields, since compatibility checks alone accept a rename. (Inference from registry rules.)
11. Compare against the deployed baseline, not the live catalog; add data diff for value-level confirmation where cheap. (CI guide; dbt Advanced CI.)
12. Show truncation and uncertainty in the report rather than expanding everything; overwhelm is a known failure mode. (Recce.)

Lineage-driven RCA
13. Traverse upstream deterministically to the most-upstream node whose failure or change aligns with the symptom, over the graph as it was at incident time; put change events and data-quality results on the same timeline. (Vendor descriptions; patent; section 4.)
14. Use an LLM only on a bounded evidence set and require the evidence path in the output; score grounding, not only the answer. (DataTrace.)
15. Evaluate by replaying past incidents and reporting RC@1 / AC@k and MRR; expect accuracy to fall with hop distance. (DataTrace; microservice RCA literature.)
16. State lineage completeness with each diagnosis; lineage gaps produce wrong diagnoses. (LatentView; Atlan.)

Cross-cutting
17. Keep direct and indirect dependencies distinct and store indirect ones at dataset scope. (OpenLineage.)
18. Record evidence type, confidence and identity match type on every edge. (DataHub model; Meta confidence per edge.)
19. Resolve identity non-destructively and fix namespace conventions before first emission. (DataHub casing guide; OpenLineage naming.)
