## KQ1. For each vendor: precisely how is column-level lineage derived, how fresh is it, and what breaks it? (O1 baseline, O2 incremental)

### Takeaway
Two families exist. Observability vendors (Monte Carlo, Datadog/Metaplane, SYNQ, Elementary, Bigeye) derive column lineage mainly by **parsing SQL observed in warehouse query history**, so it refreshes continuously but only reflects what actually ran inside a retention or look-back window (Monte Carlo documents a 10-day TTL on column edges; Datadog evaluates lineage over a selectable time window). Shift-left tools (dbt v2, SQLMesh, Recce, Foundational, Gable) derive it by **static analysis of code** (SQL AST, or application code), which is available before anything runs but breaks on Python models, unqualified `SELECT *`, unresolved schemas and anything the parser cannot type.

### Cited Findings

#### Group 1 — data observability

**Monte Carlo**
- Early architecture (vendor blog, pre-2024, flag as old): table-level lineage was built by parsing query logs; Monte Carlo described a heavily customised ANTLR parser for several SQL dialects, run in a Java Lambda that scans query logs. [V-search] — [Monte Carlo blog: Spark lineage for data lakes](https://montecarlodata.com/blog-building-spark-lineage-for-data-lakes)
- A separate field-level layer was added because query-log table lineage "couldn't extract parsed column information"; an architecture write-up describes the field-level back end as built on Snowflake and Elasticsearch (pre-2024, flag as old). [V-search] — [Monte Carlo field-level lineage announcement](https://www.montecarlodata.com/announcing-monte-carlos-end-to-end-field-level-lineage-to-help-teams-achieve-data-trust/); [InfoQ: field-level lineage in modern data systems](https://www.infoq.com/articles/field-level-lineage-modern-data-systems)
- Vendor-stated behaviour: for BigQuery the platform "automatically parses the SQL out of the query logs" and extends lineage through connectors to Looker and GitHub; lineage "automatically updates as the data evolves". [V-search] — [Monte Carlo blog: data lineage](https://www.montecarlodata.com/blog-data-lineage/)
- **Column lineage has a 10-day TTL.** Monte Carlo's own agent toolkit states: pushed table lineage never expires, but "Column lineage expires after 10 days: unlike table metadata and table lineage (which never expire), column lineage has a 10-day TTL, same as pulled column lineage." [V-doc, repo HEAD 2026-11-25] — [mc-agent-toolkit push-ingestion SKILL.md](https://github.com/monte-carlo-data/mc-agent-toolkit/blob/main/skills/push-ingestion/SKILL.md)
- Latency figures from the same file: pushed table lineage is visible "within seconds to a few minutes (fast direct path to Neo4j)", column lineage in "a few minutes", query logs after "at least 15-20 minutes (async processing pipeline)". Custom lineage nodes/edges created through GraphQL expire after 7 days unless `expireAt: "9999-12-31"` is set. [V-doc, 2026-11-25] — [mc-agent-toolkit push-ingestion SKILL.md](https://github.com/monte-carlo-data/mc-agent-toolkit/blob/main/skills/push-ingestion/SKILL.md)
- A push ingestion API exists for metadata, table/column lineage and query logs (`pycarlo` `send_lineage()` to `/ingest/v1/lineage`, 1 MB batch limit), intended for sources the pull model does not cover, such as integrations that do not expose query history. Pushed edges are marked so query-log-derived edges do not overwrite them. [V-doc, 2026-11-25] — [push-lineage reference](https://github.com/monte-carlo-data/mc-agent-toolkit/blob/main/skills/push-ingestion/references/push-lineage.md)
- Stack coverage as rated by Monte Carlo itself for its editor-time "Prevent" skill: dbt + any supported warehouse = full; SQL-first without dbt = partial; Databricks notebooks = partial; SQLMesh = partial; **PySpark / non-SQL pipelines = limited (manual prompting only)**. [V-doc, 2026-11-25] — [prevent skill README](https://github.com/monte-carlo-data/mc-agent-toolkit/blob/main/skills/prevent/README.md)
- dbt artifacts can be imported (`montecarlo import dbt-manifest`). [V-doc, PyPI montecarlodata 0.177.0, 2026-10-23] — [PyPI montecarlodata](https://pypi.org/project/montecarlodata/)

**SYNQ (now "Coalesce Quality")**
- The public API names four lineage origins and ranks them: `DWH_NATIVE` ("Read from the warehouse's own lineage feature, for example Snowflake SNOWFLAKE.CORE.GET_LINEAGE. Authoritative, highest fidelity"), `QUERY_HISTORY` ("Derived by parsing query history / access history"), `DECLARED` (dbt refs, hand-authored edges, BI relationships), and `VIEW_DEFINITION`. Declared lineage is additive and never replaces observed lineage. [V-doc, repo HEAD 2026-11-26; file first published 2026-06-19] — [getsynq/api lineage.proto](https://github.com/getsynq/api/blob/main/protos/synq/ingest/dwh/v1/lineage.proto)
- Column edges are carried inside table edges; an object's lineage is treated as column-level only if an edge for it carries column edges, otherwise table-level. [V-doc, 2026-11-26] — [getsynq/api lineage.proto](https://github.com/getsynq/api/blob/main/protos/synq/ingest/dwh/v1/lineage.proto)
- Non-SQL is handled by declaration, not parsing: the `ColumnLineage` custom feature exists "for the cases SQL cannot express ... A component whose transformation is written in Python, or a hand-maintained mapping, has no SQL for a parser to read." Where SQL exists, `SqlDefinition` is preferred because "the column lineage is then derived from the SQL and stays correct as the SQL changes". Limit: 10,000 edges per declaration. [V-doc, 2026-11-26; first published 2026-09-14] — [getsynq/api column_lineage.proto](https://github.com/getsynq/api/blob/main/protos/synq/entities/custom/features/v1/column_lineage.proto)
- Platforms enumerated in the API: BigQuery, ClickHouse, Snowflake, Redshift, Postgres, MySQL, Databricks, dbt Cloud, SQLMesh, DuckDB/MotherDuck, Trino, SQL Server, Oracle, Athena, Microsoft Fabric. [V-doc, 2026-11-26] — [getsynq/api data_platforms.proto](https://github.com/getsynq/api/blob/main/protos/synq/platforms/v1/data_platforms.proto)
- Git is first-class: the API exposes commit diffs (`GetDiffByCommit`, `GetDiffByChangeId`) and a git-context ingest. [V-doc, 2026-11-26] — [getsynq/api commits_service.proto](https://github.com/getsynq/api/blob/main/protos/synq/git/commits/v1/commits_service.proto)

**Foundational**
- Mechanism (vendor-authored, published on the OpenLineage blog 2025-02-04): lineage is extracted by static analysis of code "for platforms like dbt, Spark, ORMs like SQLAlchemy and other platforms by analyzing the code to identify how data is transformed and moved". It is "potential lineage — a view of what could happen when the code is executed". [V-doc, OpenLineage repo HEAD 2026-11-26] — [OpenLineage blog: lineage from code](https://github.com/OpenLineage/OpenLineage/blob/main/website/blog/lineage-from-code/index.mdx)
- Its stated rationale is the weakness of runtime/query-log lineage: rarely executed pipelines (restore jobs, annual computations), rarely triggered code paths (dbt full refresh vs incremental), and rarely viewed dashboards never show up in runtime lineage. [V-doc, vendor argument, 2025-02-04] — [OpenLineage blog: lineage from code](https://github.com/OpenLineage/OpenLineage/blob/main/website/blog/lineage-from-code/index.mdx)
- Language scope per the OpenLineage ecosystem listing: "static analysis of pipeline code across any type of programming language such as Python, Java, COBOL, Scala and more". [V-doc, 2026-11-26; vendor-supplied description] — [OpenLineage ecosystem producers](https://github.com/OpenLineage/OpenLineage/blob/main/website/static/ecosystem/producers.tsx)
- Acknowledged limit: the same post expects framework support for "dbt, Airflow, Spark" but says "there probably won't be support for legacy or home-grown systems", proposing code annotations as hints. [V-doc, 2025-02-04] — [OpenLineage blog: lineage from code](https://github.com/OpenLineage/OpenLineage/blob/main/website/blog/lineage-from-code/index.mdx)

**Gable**
- Mechanism (vendor marketing): static analysis of source code in CI/CD rather than production agents, "no production overhead, sampling, or data exposure risk"; produces field-level lineage "from originating source code to storage destinations". [V-search] — [Gable: data lineage](https://www.gable.ai/data-lineage)
- The CLI has a lineage scan command that "analyzes a project for lineage using static code analysis". [V-search] — [Gable docs: CLI lineage](https://docs.gable.ai/docs/cli/lineage.md)
- The CLI uploads static-code-analysis results to a `/sca/results` endpoint. Payload types include `CODE`, `DATA_STORE`, `EDGE`, `CODE_STRANDS`, `DATA_COMPONENTS`, `CODE_DATA_EDGES`, `COMPLIANCE` and **`AI_AUGMENTATION`**, which suggests an LLM pass over static results. It can also introspect MySQL and PostgreSQL to register tables as data assets. [V-doc, PyPI gable 0.75.3, 2026-10-27] — [PyPI gable](https://pypi.org/project/gable/)

**Recce**
- Column-level lineage is computed by SQL analysis of dbt models with SQLGlot: "Change Classification uses the SQL parsing and AST diff capabilities of SQLGlot to compare the semantic trees of the base and current SQL." [V-doc, docs repo HEAD 2026-11-24] — [Recce docs: change classification](https://github.com/DataRecce/recce-docs/blob/main/docs/what-you-can-explore/change-classification.md)
- Inputs are two sets of dbt artifacts (`manifest.json`, `catalog.json`), one for the base branch and one for the current branch. Without base artifacts the server runs in single-environment mode and shows no diffs. [V-doc, 2026-11-24] — [Recce docs: MCP server](https://github.com/DataRecce/recce-docs/blob/main/docs/setup-guides/mcp-server.md)
- Each column gets a transformation type: pass-through, renamed, derived, source, or **unknown** ("This could be due to a parse error or other unknown reason"). [V-doc, 2026-11-24] — [Recce docs: column-level lineage](https://github.com/DataRecce/recce-docs/blob/main/docs/what-you-can-explore/column-level-lineage.md)
- Unlike dbt's Catalog lineage, Recce tracks filter and grouping usage: its lineage identifies "which upstream columns are used as filters or grouping keys. If those upstream columns change, the current model is impacted." [V-doc, 2026-11-24] — [Recce docs: impact radius](https://github.com/DataRecce/recce-docs/blob/main/docs/what-you-can-explore/impact-radius.md)
- Documented limits: classification is "intentionally conservative"; logically equivalent rewrites (`a + b` → `b + a`) and added `LEFT JOIN`s may be flagged model-wide; "Modified Python models and seeds ... are always treated as model-wide changes". [V-doc, 2026-11-24] — [Recce docs: change classification](https://github.com/DataRecce/recce-docs/blob/main/docs/what-you-can-explore/change-classification.md)
- Scope is the dbt project only. Cloud warehouses supported: Snowflake, Databricks, BigQuery, Redshift. [V-doc, 2026-11-24] — [Recce docs: connect warehouse](https://github.com/DataRecce/recce-docs/blob/main/docs/setup-guides/connect-to-warehouse.md)

**dbt Labs (dbt v2 / former Fusion engine; Catalog, formerly Explorer)**
- Column-level lineage (CLL) covers models, sources and snapshots in a dbt project. In the platform it requires an **Enterprise or Enterprise+** plan; locally it requires dbt v2 with **strict static analysis**. [V-doc, docs repo HEAD 2026-11-27] — [dbt docs: column-level lineage](https://github.com/dbt-labs/docs.getdbt.com/blob/current/website/docs/docs/explore/column-level-lineage.md)
- Refresh: "dbt updates the lineage in Catalog after each run that's executed in the production or staging environment." dbt v1 jobs must run `dbt docs generate`; "Jobs running v2 refresh this metadata automatically on every job run." [V-doc, 2026-11-27] — [dbt docs: column-level lineage](https://github.com/dbt-labs/docs.getdbt.com/blob/current/website/docs/docs/explore/column-level-lineage.md)
- Local artefact: `dbt compile --generate-info-schema --static-analysis strict` writes a `dbt.column_lineage` Parquet under `target/info_schema/`, queryable with `dbt show --info column_lineage`. [V-doc, 2026-11-27] — [dbt docs: column-level lineage](https://github.com/dbt-labs/docs.getdbt.com/blob/current/website/docs/docs/explore/column-level-lineage.md)
- Documented caveats: (1) lineage "reflects the lineage from `select` statements ... It doesn't reflect other usage like joins and filters"; (2) parsing errors on ambiguous or complex SQL, e.g. complex lateral joins and JSON unpacking; (3) **Python error**: "Due to the nature of Python models, it's not possible to parse and determine the lineage"; (4) unknown errors, e.g. hard-coded table names instead of `ref`. Incomplete lineage is flagged with a warning pill. [V-doc, 2026-11-27] — [dbt docs: column-level lineage](https://github.com/dbt-labs/docs.getdbt.com/blob/current/website/docs/docs/explore/column-level-lineage.md)
- CLL is only available in `strict` static analysis mode, not in the default `baseline` mode or `off`. Things that push projects out of strict mode: unsupported types (`STRUCT`, `ARRAY`, `GEOGRAPHY`), unsupported built-in functions (`AI.PREDICT`, `JSON_FLATTEN`, `st_pointfromgeohash`), heavy Jinja introspection and post-hooks, incompatible packages, missing access to sources. UDFs need `CREATE FUNCTION` in `sql_header` or `on-run-start` to be registered. [V-doc, 2026-11-27] — [dbt docs: about static analysis](https://github.com/dbt-labs/docs.getdbt.com/blob/current/website/docs/docs/build/about-static-analysis.md)
- A "column evolution lens" labels each hop as passthrough, rename or transformed and shows the SQL transformation expression (shown to all users since September 2026). [V-doc, 2026-11-27] — [dbt release notes](https://github.com/dbt-labs/docs.getdbt.com/blob/current/website/docs/docs/dbt-versions/release-notes.md)
- dbt v2 adapters that are GA: Snowflake, BigQuery, Redshift, Databricks (DuckDB local; ClickHouse and Spark in beta). [V-doc, Sept 2026 notes] — [dbt release notes](https://github.com/dbt-labs/docs.getdbt.com/blob/current/website/docs/docs/dbt-versions/release-notes.md)
- Outside the project: Tableau dashboards are auto-generated as downstream exposures (Enterprise tiers, one Tableau site); external metadata ingestion of non-dbt tables is "supported for Snowflake only". [V-doc, 2026-11-27] — [dbt docs: downstream exposures](https://github.com/dbt-labs/docs.getdbt.com/blob/current/website/docs/docs/explore/view-downstream-exposures.md); [dbt docs: external metadata ingestion](https://github.com/dbt-labs/docs.getdbt.com/blob/current/website/docs/docs/explore/external-metadata-ingestion.md)

**SQLMesh / Tobiko (Fivetran; SQLMesh now a Linux Foundation project)**
- CLL is a by-product of parsing every model with SQLGlot: "having a first-class understanding of SQL supercharges SQLMesh with features such as transpilation, column-level lineage, and automatic change categorization". It is free and local (CLI, browser UI, VS Code extension). [V-doc, repo HEAD 2026-11-25] — [SQLMesh docs: comparisons](https://github.com/TobikoData/sqlmesh/blob/main/docs/comparisons.md)
- `SELECT *` from an external source "will prevent SQLMesh from performing some optimization steps and from determining upstream column-level lineage" unless an `EXTERNAL` model supplies the schema (`sqlmesh create_external_models`). [V-doc, 2026-11-25] — [SQLMesh docs: SQL models](https://github.com/TobikoData/sqlmesh/blob/main/docs/concepts/models/sql_models.md)
- "Turning off the optimizer may prevent column-level lineage from working for the affected model and its descendants, unless all columns in the model's query are qualified and it contains no star projections." [V-doc, 2026-11-25] — [SQLMesh docs: models overview](https://github.com/TobikoData/sqlmesh/blob/main/docs/concepts/models/overview.md)
- Python models: only SQL strings returned by a Python model are parsed into SQLGlot expressions and so carry CLL; DataFrame-returning Python models are opaque. Automatic change categorisation defaults to `off` for Python models (`full` for SQL, seeds, external). [V-doc, 2026-11-25] — [SQLMesh docs: SQL models](https://github.com/TobikoData/sqlmesh/blob/main/docs/concepts/models/sql_models.md); [SQLMesh docs: configuration](https://github.com/TobikoData/sqlmesh/blob/main/docs/guides/configuration.md)

### Inferences
- **Query-history lineage is "observed" lineage with a horizon.** Monte Carlo's 10-day column TTL and Datadog's window selector mean a column dependency exercised only monthly or quarterly can be absent at the moment a change is assessed. This is exactly the gap Foundational argues for static analysis to fill, and it matters most for change impact (O3), less for incident triage on daily pipelines (O4).
- **Static SQL lineage is "potential" lineage with blind spots at language boundaries.** dbt, SQLMesh and Recce all document the same three failure classes: Python models, star projections over objects with unknown schema, and SQL the parser cannot type. For blast-radius work the second definition is the safer one, because a changed filter column alters every output row.
- **SYNQ's API is the clearest public statement of a hybrid design**: native warehouse lineage first, then query history, then view definitions, with declared edges layered on top for non-SQL hops. That is a useful reference pattern for any in-house build.

## KQ2. Which vendors can analyze a pull request BEFORE merge and show column-level downstream impact, and how? (O3)

### Takeaway
Verified pre-merge PR analysis exists at Datadog (dbt only: downstream impact graph plus statistical drift, four git providers), Recce (dbt only: SQLGlot AST diff of base vs PR manifests, true column-level impact radius, GitHub and GitLab), dbt Advanced CI (data diff of CI build vs production, not a lineage impact report), and SQLMesh (PR environments with breaking/non-breaking categorisation). Foundational and Gable are the only two that claim impact analysis crossing from application code into the warehouse, but their PR mechanics could not be read first-hand.

### Cited Findings
- **Datadog (ex-Metaplane) — verified.** "Data Observability CI/CD checks run automatically when you open a pull request (PR) that modifies dbt models"; results are posted "as a comment on your PR, and the comment updates each time you push new changes", with a full report in Datadog. Two checks: **Impact Lineage** ("a graph of everything downstream of your changed dbt models ... which tables, dashboards, and other consumers depend on the models you modified, and route review to the right owners") and **Drift Detection** (statistical comparison of data before/after: row count, null rate, cardinality, with a threshold shown as a *warning*). Git providers: "GitHub, GitLab, Bitbucket Cloud, and Azure DevOps". [V-doc, 2026-11-26] — [Datadog docs: CI/CD](https://docs.datadoghq.com/data_observability/cicd/)
- Datadog's method: impact comes from the existing lineage graph anchored on changed dbt models; drift needs the PR to be **built in a CI schema/database** that Datadog can read (dbt Cloud CI job, or dbt Core emitting OpenLineage with the PR number in the `sourceCodeLocation` facet, `openlineage-dbt` ≥ 1.46.0). The docs describe the checks at model granularity; they do not state a column-level diff of the PR, and no merge-blocking mode is documented. [V-doc, 2026-11-26] — [Datadog docs: CI/CD](https://docs.datadoghq.com/data_observability/cicd/)
- **Recce — verified.** Impact Radius "helps you analyze changes and identify downstream impacts at the column level", going beyond dbt's `state:modified+` by "analyzing SQL code directly". Changes are classified as additive (no downstream impact), column change (only dependants of that column) or model-wide (all downstream). [V-doc, 2026-11-24] — [Recce docs: impact radius](https://github.com/DataRecce/recce-docs/blob/main/docs/what-you-can-explore/impact-radius.md)
- Recce's method: compare base-branch artifacts (from a CD job) with PR artifacts built into a **per-PR schema** (`dbt build` + `dbt docs generate`, then `recce-cloud upload`). Recce Cloud's agent then posts a PR comment with summary, key changes, impact analysis (lineage diagram), checklist and suggested actions; `/recce` in a PR comment regenerates it. [V-doc, 2026-11-24] — [Recce docs: setup CI](https://github.com/DataRecce/recce-docs/blob/main/docs/setup-guides/setup-ci.md); [Recce docs: data review summary](https://github.com/DataRecce/recce-docs/blob/main/docs/what-you-can-explore/summary.md)
- Recce blocking: "When configured as a required PR check, all checks must be approved before the PR can be merged." Providers: "Cloud supports GitHub and GitLab." PR comments and the agent are Cloud-only; the OSS tool does lineage diff and data diffs locally. [V-doc, 2026-11-24] — [Recce docs: checklist](https://github.com/DataRecce/recce-docs/blob/main/docs/collaboration/checklist.md); [Recce docs: connect git](https://github.com/DataRecce/recce-docs/blob/main/docs/setup-guides/connect-git.md); [Recce docs: Cloud vs OSS](https://github.com/DataRecce/recce-docs/blob/main/docs/whats-recce/cloud-vs-oss.md)
- **dbt Advanced CI — verified, but it is a data diff, not a lineage impact report.** With "dbt compare" enabled, dbt "compares the changes between the last applied state of the production environment ... and the latest changes from the pull request, whenever a pull request is opened or new commits are pushed", reporting changes to primary keys, rows and columns in a Compare tab and "a summary of the changes as a git comment". Enterprise/Enterprise+ only; platforms BigQuery, Databricks, Postgres, Redshift, Snowflake; up to 100 records per modified model cached for 30 days; CI and production must be on the same host. [V-doc, 2026-11-27] — [dbt docs: Advanced CI](https://github.com/dbt-labs/docs.getdbt.com/blob/current/website/docs/docs/deploy/advanced-ci.md)
- dbt CI job triggers are native for GitHub, GitLab and Azure DevOps; other providers (e.g. Bitbucket) trigger through the Administrative API with `non_native_pull_request_id`. The dbt docs frame column-level impact analysis as something a developer does in Catalog or the VS Code extension during development, not as content posted on the PR. [V-doc, 2026-11-27] — [dbt docs: CI jobs](https://github.com/dbt-labs/docs.getdbt.com/blob/current/website/docs/docs/deploy/ci-jobs.md); [dbt docs: column-level lineage](https://github.com/dbt-labs/docs.getdbt.com/blob/current/website/docs/docs/explore/column-level-lineage.md)
- **SQLMesh — verified.** The open-source GitHub Actions CI/CD bot runs unit tests and the linter on PRs, creates "PR environments that represent the code changes in the PR", will "automatically categorize and backfill data for models that have changed", posts summaries, and can gate deployment on "Required Approvers" or a deploy command. [V-doc, 2026-11-25] — [SQLMesh docs: GitHub CI/CD bot](https://github.com/TobikoData/sqlmesh/blob/main/docs/integrations/github.md)

[V-doc, 2026-11-25] — [SQLMesh docs: plans](https://github.com/TobikoData/sqlmesh/blob/main/docs/concepts/plans.md); [Tobiko Cloud overview](https://github.com/TobikoData/sqlmesh/blob/main/docs/cloud/cloud_index.md)

[V-search] — [Datafold changelog](https://www.datafold.com/changelog); [Datafold blog: testing in CI](https://www.datafold.com/blog/automating-data-quality-testing-in-ci/)

[V-doc, 2026-11-25; skill directory dates from 2026-04-01] — [prevent skill README](https://github.com/monte-carlo-data/mc-agent-toolkit/blob/main/skills/prevent/README.md)

No PR-comment feature is evidenced in the API repo. [V-doc, 2026-11-26] — [getsynq/api impact.proto](https://github.com/getsynq/api/blob/main/protos/synq/entities/impact/v1/impact.proto)
- **Soda — verified as contract verification, not lineage impact.** Contracts can be verified "locally during development, embedded programmatically within your data pipelines ... or executed remotely". [V-doc, 2026-11-25] — [soda-core README](https://github.com/sodadata/soda-core/blob/main/README.md)

### Inferences
- **Three distinct pre-merge techniques are in use**, and they answer different questions:
  1. *Re-parse changed code and diff ASTs* (Recce, SQLMesh, and by its own description Foundational): cheap, no data needed, gives true column-level "what could break".
  2. *Anchor the changed model on an existing production lineage graph* (Datadog, Datafold, Monte Carlo Prevent): shows real consumers including BI, but inherits the look-back horizon and cannot see lineage introduced by the PR itself.
  3. *Build the PR in a staging schema and diff data* (dbt Advanced CI, Datadog Drift Detection, Recce data diffs, Datafold): shows "what did change" in values, costs warehouse compute.
- Only technique 1 can warn about a breaking change **before** anything is built, and only Foundational and Gable claim to apply it upstream of the warehouse.
- Blocking is the exception, not the default: Recce documents a required check; SQLMesh gates deployment on approvers; Datadog documents warnings only; dbt's check reflects build/test success rather than impact.
- dbt Labs, despite owning the richest column lineage for dbt projects, does not (per its docs) post column-level downstream impact on the PR. That leaves room for Recce, Datafold, Datadog and Paradime-style add-ons.

### Gaps
- **Foundational PR behaviour not verified.** UR (medium): Foundational analyses pending PRs by static analysis, posts a comment listing affected downstream dbt models, tables and dashboards, and flags schema-breaking changes, across GitHub/GitLab/Azure DevOps — check [foundational.io](https://www.foundational.io/) and [docs.foundational.io](https://docs.foundational.io).
- **Datafold**: supported git providers, whether checks can block, and whether BI assets and owners appear on the PR were not verified. UR (high): GitHub, GitLab, Bitbucket, Azure DevOps; downstream BI/reverse-ETL assets listed — check [docs.datafold.com](https://docs.datafold.com).
- **Monte Carlo**: whether a native PR-comment impact check exists (as opposed to the editor-time skill and GitHub PR correlation for RCA) — not found.
- **Sifflet**: UR (medium): a dbt impact-analysis integration for GitHub/GitLab PRs exists — check [docs.siffletdata.com](https://docs.siffletdata.com). Not verified.
- **Paradime**: UR (medium): "column-level lineage diff" posted on PRs with impacted dbt models and BI dashboards — check [docs.paradime.io](https://docs.paradime.io). Not verified.
- **Secoda, Select Star, Euno, Coalesce Transform, Y42, Anomalo, Acceldata, Validio, Soda (lineage impact)**: PR impact analysis — not found.
- Whether Datadog's Impact Lineage on the PR is rendered at column level, and whether the check can be made a required status: not stated in the docs read.

## KQ4. Incident detection and resolution (O4): lineage-driven root cause, blast radius, routing, AI troubleshooting, and published MTTD / MTTR numbers

### Takeaway
The verified pattern for lineage-driven resolution is the same at Monte Carlo, SYNQ and Datadog: walk lineage upstream from the alert, correlate with query-text changes, job failures and code commits/PRs, and score downstream impact by owners and important assets. **No named-customer MTTD/MTTR figure could be verified this session**; the only quantified claims seen are vendor headlines (Monte Carlo "80%+" faster resolution with its Troubleshooting Agent; Recce "cut dbt review time by 90%").

### Cited Findings
- **Monte Carlo — root-cause toolset (documented).** The MCP server exposes `get_asset_lineage`, `get_field_lineage` ("trace to source column"), `get_queries`, `get_query_changes` ("Detect SQL text modifications"), `get_query_rca`, `get_change_timeline` ("Unified change timeline"), `get_etl_issues`/`get_etl_jobs` (Airflow, dbt, Databricks), `get_github_prs` ("Recent GitHub PRs via MC's GitHub integration"), `alert_assessment` ("~2-min triage of an incident, HIGH/MEDIUM/LOW confidence + impact") and `run_troubleshooting_agent`. [V-doc, 2026-11-25] — [analyze-root-cause README](https://github.com/monte-carlo-data/mc-agent-toolkit/blob/main/skills/analyze-root-cause/README.md)
