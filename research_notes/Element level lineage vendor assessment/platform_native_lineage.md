## Key Question 1: For each platform, is column-level lineage GA, for which engines/workloads, with what latency and retention, and through which API / system tables can it be exported?

### Takeaway

Column-level lineage is production-grade and SQL-exportable on Databricks Unity Catalog (system tables, 395-day rolling) and Snowflake (GET_LINEAGE / ACCOUNT_USAGE, 1 year), GA but narrow on Google (BigQuery jobs and Managed Service for Apache Spark only, short retention, 1,500-link cap), and on AWS it exists only where an OpenLineage RunEvent carries a columnLineage facet (Spark on Glue 5.0+/EMR, hand-posted events) with history exposed through node-version APIs rather than SQL. Microsoft Fabric/Purview remain item-level for most Fabric workloads, and every platform captures lineage at run time only: none of the five hyperscaler/warehouse platforms derives column lineage from code before it runs.

History, latency, retention, limits (O2)
- [P] Lineage nodes are versioned by event timestamp and can be read point-in-time: `GetLineageNode` accepts `eventTimestamp` ("The event time stamp for which you want to get the data lineage node") and returns `upstreamNodes` / `downstreamNodes`; `ListLineageNodeHistory` accepts `eventTimestampGTE`, `eventTimestampLTE`, `direction`, `sortOrder`. — [botocore DataZone service model](https://github.com/boto/botocore/blob/2588d4b17abe3e3ab31334970fce523a1c033fef/botocore/data/datazone/2018-05-10/service-2.json)
- [S] "all lineage nodes in Amazon DataZone data lineage have versioning"; each version opens a new tab in the lineage page for comparison. — [Amazon DataZone user guide, data lineage](https://docs.aws.amazon.com/datazone/latest/userguide/datazone-data-lineage.html)
- [P] Hard event-size limit: the `LineageEvent` blob shape has `"max": 300000` bytes. [S] The troubleshooting guide states "Lineage event has a size limit of 300KB." — [botocore DataZone service model](https://github.com/boto/botocore/blob/2588d4b17abe3e3ab31334970fce523a1c033fef/botocore/data/datazone/2018-05-10/service-2.json); [AWS docs, Troubleshooting data lineage](https://docs.aws.amazon.com/sagemaker-unified-studio/latest/userguide/datazone-lineage-troubleshooting.html)

- [P] Redshift (and Snowflake-connection) lineage is produced by a scheduled sync job (`schedule`, `lineageJobId`, `LineageSqlQueryRunDetails {queryStartTime, queryEndTime, totalQueriesProcessed, numQueriesFailed}`), so warehouse lineage latency equals the sync schedule, not query time. — [botocore DataZone service model](https://github.com/boto/botocore/blob/2588d4b17abe3e3ab31334970fce523a1c033fef/botocore/data/datazone/2018-05-10/service-2.json)
- [S] Mar 2026: an aggregated lineage view (all jobs contributing to a dataset) became the default for IdC-based domains; column detail is exposed in the event-timestamp view. — [AWS What's New, Mar 2026](https://aws.amazon.com/about-aws/whats-new/2026/03/amazon-sagemaker-unified-studio-aggregated-lineage)

#### Databricks (Unity Catalog)

- [S] Scope: Unity Catalog captures runtime lineage "down to the column level" for queries run on Databricks, with the caveat that it captures "to the column level as much as possible" and that there are cases where column lineage cannot be captured. Lineage data from before 1 September 2024 is not available. — [Databricks docs, Lineage in Unity Catalog](https://docs.databricks.com/aws/en/data-governance/unity-catalog/data-lineage.html)
- [S] Documented limitations returned by search (wording varies by doc version): lineage for UDFs is table-level only; column lineage for Lakeflow/DLT pipelines requires Databricks Runtime 13.3 LTS or later (an older doc version said column lineage was not supported for Delta Live Tables); streaming between Delta tables requires DBR 11.3 LTS or later; inserts of explicit values into a column are not captured as column lineage. — [Databricks docs (GCP), data lineage](https://docs.databricks.com/gcp/en/data-governance/unity-catalog/data-lineage); [Microsoft Learn mirror](https://learn.microsoft.com/en-in/azure/databricks/data-governance/unity-catalog/data-lineage)
- [S] Retention, system tables: "Lineage system tables retain a rolling 395-day window of data by default. Events older than the retention window are removed on a rolling basis." — [Databricks docs, Lineage system tables reference](https://docs.databricks.com/aws/en/admin/system-tables/lineage)
- [S] Retention, UI and API: for older history, "use Catalog Explorer or the lineage API, which indefinitely retain lineage captured after September 1, 2024." Azure page: "Lineage data displayed in Catalog Explorer is retained indefinitely. All lineage data captured after September 1, 2024 is available." — [Databricks docs, Lineage system tables reference](https://docs.databricks.com/aws/en/admin/system-tables/lineage); [Microsoft Learn, data lineage](https://learn.microsoft.com/en-in/Azure/databricks/data-governance/unity-catalog/data-lineage)

- [T] System-table retention is becoming configurable (Beta); when enabled the free retention period becomes 395 days for all supported system tables. — [Microsoft Tech Community post](https://techcommunity.microsoft.com/discussions/azure/system-table-retention-is-now-your-choice-not-a-fixed-number/4557491)
- [S] External lineage ("bring your own lineage") is labelled Public Preview in the docs excerpt; it is created "Manually, using the Catalog Explorer UI, the External Metadata and External Lineage APIs, or the Databricks SDK for Python"; limits are 10,000 external metadata objects and 100,000 external lineage relationships per metastore; and "External lineage is not recorded in system.access.table_lineage or system.access.column_lineage." — [Databricks docs, External lineage](https://docs.databricks.com/aws/en/data-governance/unity-catalog/external-lineage)

#### Google Cloud (Knowledge Catalog, formerly Dataplex Universal Catalog; Data Lineage API)

- [S] Naming: "As of April 10, 2026, Dataplex Universal Catalog is now called Knowledge Catalog. The API, client library, CLI, and IAM names remain unchanged." — [Knowledge Catalog release notes](https://docs.cloud.google.com/dataplex/docs/release-notes)
- [S] Capture: "Lineage information is tracked automatically when you enable the Data Lineage API." — [Use Knowledge Catalog with BigQuery](https://docs.cloud.google.com/bigquery/docs/use-knowledge-catalog)
- [S] Column-level scope: release notes list column-level lineage as generally available and supported for BigQuery jobs; the current OpenLineage/troubleshooting pages say column-level lineage is limited to BigQuery SQL transformations and Managed Service for Apache Spark (the renamed Dataproc) jobs, and that "other integrated systems (such as Cloud Data Fusion and Vertex AI) support table-level lineage only". — [Knowledge Catalog release notes](https://docs.cloud.google.com/dataplex/docs/release-notes); [Troubleshoot data lineage issues](https://docs.cloud.google.com/knowledge-catalog/docs/troubleshooting-lineage)
- [S] Column-level limits: not collected for BigQuery load jobs, copy jobs or routines; upstream column-level lineage not collected for external tables; and "Link limits exceeded: If a transformation job generates more than 1,500 column-level links, Knowledge Catalog skips column-level lineage collection and retains table-level lineage only." No CMEK for harvested lineage metadata. — [Troubleshoot data lineage issues](https://docs.cloud.google.com/knowledge-catalog/docs/troubleshooting-lineage); [Data lineage considerations](https://docs.cloud.google.com/dataplex/docs/lineage-considerations)
- [P] API data model supports field-level references natively: `EntityReference.field` = "Optional. Field path within the entity. Each nesting level should be a separate value in the repeated field ... Must be empty for asset level lineage ... Each field length is limited to 500 characters. Maximum supported nesting level is 20."; `Link.dependency_info` = "The dependency info of the link (applies only to column level links)"; `DependencyType` values are `EXACT_COPY` ("Exact data copy without any change") and `OTHER` ("Other types of dependencies like filtering or grouping"). — [googleapis, lineage.proto](https://github.com/googleapis/googleapis/blob/599771b95845d8cf0f9e1016c64bd58b61ebe27c/google/cloud/datacatalog/lineage/v1/lineage.proto)
- [P] Export / blast-radius API (O3): `SearchLinks`, `BatchSearchLinkProcesses`, and `SearchLineageStreaming`, which performs "a breadth-first search in the given direction" and "supports Column-Level Lineage (CLL) along with wildcard support to retrieve all CLL for an Entity FQN"; column-level reads need the `datalineage.events.getFields` permission; limits are `max_depth` default 5 / max 100 and `max_results` default 1,000 / max 10,000; root entities can be "FQN and field" with wildcard `*`. — [googleapis, lineage.proto](https://github.com/googleapis/googleapis/blob/599771b95845d8cf0f9e1016c64bd58b61ebe27c/google/cloud/datacatalog/lineage/v1/lineage.proto)
- [P] History model (O2): links are time-stamped aggregates, `Link.start_time` = "The start of the first event establishing this link" and `Link.end_time` = "The end of the last event establishing this link"; searches accept a `time_range` ("If unspecified, all lineage is returned. ## Key Question 2: Which OpenLineage event types does each platform accept for external lineage (RunEvent only vs JobEvent/DatasetEvent static lineage), and is column-level lineage preserved for custom/external events? Confirm or correct earlier findings (a), (b), (c).

### Takeaway

## Key Question 3: AWS specifically — what is the most complete AWS-native element-level lineage path today, what are its gaps for microservices -> Kafka -> Flink -> warehouse -> feature store -> model, and what does AWS charge for lineage?

### Takeaway

The most complete AWS-native path is SageMaker Catalog (Amazon DataZone) lineage: automatic for Glue-crawled assets, Redshift (scheduled query-log parsing) and Spark on Glue 5.0+/EMR (column-level via the built-in OpenLineage Spark integration), with everything else pushed as OpenLineage RunEvents through `PostLineageEvent`. For the buyer's chain it covers only the warehouse hop and any Spark hops natively; microservices, MSK topics, Flink jobs and the feature-store-to-model hop have no automatic capture, column lineage is not available from Flink at all through OpenLineage, and SageMaker ML lineage is a separate, artifact-level graph. Lineage has no separate price: it is metered through DataZone's request and metadata-storage dimensions.

### Inferences

- At the published rates (as returned by search), lineage cost on AWS is driven by request volume: $10 per 100,000 requests is $0.0001 per posted event, so one RunEvent per minute per streaming job is roughly 43,200 events and about $4.32 per job per month (about $4,300 per month for 1,000 jobs), whereas per-record emission from microservices is both uneconomic and impossible under the 20 TPS quota. Lineage for streaming should be emitted per job lifecycle or per schema/deploy change, not per record. (Arithmetic is mine; reads via GetLineageNode / QueryGraph are also billable requests.)
- A workable AWS-native design for the buyer's chain is "SageMaker Catalog as the system of record, fed by custom emitters": (1) CI/deploy-time RunEvents for each microservice producer and Flink job carrying schema and columnLineage facets; (2) OpenLineage Flink (2.x) listener for topic-level run evidence; (3) native Redshift sync; (4) a bridge job that reads `QueryLineage` from SageMaker AI and posts RunEvents linking feature groups and model packages. Items 1 and 4 are custom build; nothing AWS-native supplies them.
- Because AWS accepts only RunEvents, "design-time" lineage has to be disguised as runs (for example, a synthetic COMPLETE event per deployment), and node versioning by event timestamp then gives a usable change history for O2.
- The absence of a DataZone/lineage MCP server in the official AWS MCP repository suggests that agent access to lineage on AWS currently means calling the DataZone API through the generic AWS API MCP server or custom tools; a managed remote MCP may exist outside that repository (not checked).

## Key Question 4: What field-level capabilities exist for streaming (Confluent Stream Lineage granularity, schema registry rules, Flink SQL column lineage in Confluent Cloud or Amazon Managed Service for Apache Flink)?

### Takeaway

No streaming platform examined offers native field-level lineage. Confluent Stream Lineage is topic/client/statement-level with a short default window; Apache Flink's native lineage (FLIP-314) is dataset-level with schema facets but no column mappings, and the OpenLineage project states plainly that column-level lineage is not available from Flink 2.x interfaces. Field-level lineage across Kafka and Flink today requires parsing Flink SQL outside the engine or hand-declaring mappings.

### Cited Findings

- [S] Confluent Stream Lineage default view: "The graph shows producer and consumer activity from the last 10 minutes, offering a real-time view of your data streams." Flink statements appear as nodes: "A Flink statement node shows its name, status, throughput, and bytes produced and consumed per topic." — [Confluent docs, Stream Lineage](https://docs.confluent.io/cloud/current/stream-governance/stream-lineage.html)
- [S] Point-in-time lineage: "By default, the lineage shows data for the last 10 minutes, but with Point-in-time Lineage, we can adjust that to a variety of different periods going back minutes, hours, or even days." (Confluent developer course, not the product reference; exact maximum window not confirmed.) — [Confluent Developer course, Stream Lineage](https://developer.confluent.io/courses/governing-data-streams/stream-lineage)
- [T] Granularity: "Stream lineage provides insights at the topic level about data origin to destinations." — [J. Boyer, Flink studies: Confluent Cloud for Apache Flink](https://jbcodeforce.github.io/flink-studies/techno/ccloud-flink/)
- [T] Evidence that Confluent Cloud does not expose column lineage for Flink SQL: DataHub added "best-effort" column-level lineage for Confluent Cloud Flink SQL by parsing statements with sqlglot (Spark dialect, since no Flink dialect exists) and dropping ambiguous field names. — [DataHub PR #19433](https://github.com/datahub-project/datahub/pull/19433)
- [P] Apache Flink native lineage: "Apache Flink provides a native lineage support by providing an internal lineage data model and Job Status Listener for developer to integrate lineage metadata into external lineage system, for example OpenLineage. Connector coverage is incomplete: "The Flink community will gradually support all of the common connectors, such as Kafka, JDBC, Cassandra, Hive." Custom connectors must implement `LineageVertexProvider`. — [Apache Flink docs, Data Lineage](https://github.com/apache/flink/blob/055ae9cd0d4a876bd19be18da94aa13ee62062c1/docs/content/docs/internals/data_lineage.md)
- [P] Flink's lineage source classes at HEAD include dataset, vertex, edge, graph and schema facets (`LineageGraph`, `LineageEdge`, `LineageDataset`, `DatasetSchemaFacet`, `DatasetSchemaField`, `TableLineageDataset`) but no column-lineage class. — [apache/flink at commit 055ae9c](https://github.com/apache/flink/tree/055ae9cd0d4a876bd19be18da94aa13ee62062c1)
- [P] OpenLineage on Flink 2.x: "Unfortunately, lineage interfaces in Flink 2.x do not provide column level lineage information. In general, this may be difficult to extract for the transformations defined through the programming language. However, it is possible to extract column level lineage information for Flink SQL jobs. Following PR contains a potential extension to Flink to make it available." (The linked PR is apache/flink #26089; its merge status was not checked.) — [OpenLineage docs, Flink 2.x](https://github.com/OpenLineage/OpenLineage/blob/b9cd9fd9c323af31807d130eb2c7db23998d7f3c/website/docs/integrations/flink/flink2.md)

Detached-mode submissions need `openlineage.flink.enableDetachedJobTracking`. — [OpenLineage docs, Flink 2.x](https://github.com/OpenLineage/OpenLineage/blob/b9cd9fd9c323af31807d130eb2c7db23998d7f3c/website/docs/integrations/flink/flink2.md)
- [T] Flink CDC source connectors do not implement `LineageVertexProvider` as of an open Flink ticket (FLINK-39765). — [Flink dev mailing list archive](https://go.mail-archive.com/dev@flink.apache.org/msg86492.html)
- [P] Amazon Managed Service for Apache Flink and Amazon MSK expose no lineage in their APIs. — [botocore data directory](https://github.com/boto/botocore/tree/2588d4b17abe3e3ab31334970fce523a1c033fef/botocore/data)
- [P] Catalog-side modelling of streams: Databricks external metadata objects have `KAFKA`, `CONFLUENT` and `STREAM_NATIVE` system types with column mappings; Google's lineage event timestamps are defined for streaming ("the period from which the lineage is being reported"). — [databricks-sdk-py, catalog.py](https://github.com/databricks/databricks-sdk-py/blob/7745f1df880eecd6cb39a6010274a9a52fb4a76e/databricks/sdk/service/catalog.py); [googleapis, lineage.proto](https://github.com/googleapis/googleapis/blob/599771b95845d8cf0f9e1016c64bd58b61ebe27c/google/cloud/datacatalog/lineage/v1/lineage.proto)
- [T] Third-party view (Sept 2026): Flink 2.x lineage depends on connectors implementing the native interfaces (Kafka called out), and column-level mapping needs extra instrumentation. — [OneUptime blog, 8 Sep 2026](https://oneuptime.com/blog/post/2026-09-08-batch-streaming-lineage-one-metadata-graph/markdown)

### Inferences

- For a Kafka + Flink estate, element-level lineage is a build item regardless of vendor: schemas (Schema Registry) give the field inventory per topic, Flink SQL can be parsed for field mappings, DataStream/Java jobs and microservices need declared mappings (annotations or contract files), and only then can a platform catalog store the result (as columnLineage facets on AWS/Snowflake, or column relationships on Databricks).
- Confluent's 10-minute default window and "days" look-back make Stream Lineage an operational view, not a system of record for O2 history or O3 impact analysis.
- Because Flink's native lineage is emitted at job creation, it is closer to "deploy-time" lineage than batch engines' per-query capture; that is helpful for O2 (a new job version yields a new graph) but still post-submit, not pre-merge.

## Platform comparison table and open questions (cross-cutting synthesis of Key Questions 1-5)

### Takeaway

For element-level lineage that a CI job can query and that survives as history, Databricks and Snowflake are the strongest natively, Google is capable but short-lived and BigQuery/Spark-centric, AWS is workable only as an OpenLineage RunEvent store with custom emitters for everything outside Spark and Redshift, and Microsoft and the streaming platforms do not provide native field-level lineage. No platform provides static, pre-execution column lineage or a native pull-request integration.

### Inferences

- Fit against the four objectives for an AWS-based buyer with Kafka, Flink, a warehouse, a feature store and a model registry: platform-native lineage alone meets O1 only for the warehouse and Spark hops; O2 history is available (AWS node versions, Databricks/Snowflake event rows) but only for executed workloads; O3 must be assembled from a static parser plus API/SQL calls to the platform graph; O4 lineage-linked detection is native only on Databricks (Preview/Beta) in the evidence gathered.
- The portable design choice the evidence supports is OpenLineage RunEvents with schema and columnLineage facets as the interchange format (accepted with column fidelity by AWS and Snowflake, emitted by Spark, Trino, Presto, dbt, Airflow, Dagster), with a separate store for static and streaming field mappings that no platform ingests natively.
- Evidence strength is uneven: AWS, Google, Databricks external lineage, Flink, Fabric, Dagster, Trino, SAP and Oracle claims rest on primary material read directly; Snowflake, Confluent, Purview and most Databricks core-lineage claims rest on search excerpts or third parties and should be re-verified before being quoted in a decision document.
