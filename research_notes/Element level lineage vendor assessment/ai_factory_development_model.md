## 1. Definitions and lineage of the term: how "AI factory" / "software factory" / "dark factory" / "agentic software factory" is used for software development in 2025-2026

### Takeaway
In 2025-2026 a "software factory" (or "dark factory" at its extreme) means a development system in which humans author intent (specs, scenarios, constraints, harness) and coding agents plan, write, test and review the code; the term crystallised in January-February 2026 around Dan Shapiro's five-levels post, StrongDM's Software Factory manifesto and OpenAI's "harness engineering" account. It is distinct from NVIDIA's "AI factory" (GPU data centres that produce tokens) and from the Harvard/Iansiti-Lakhani "AI factory" (a firm's data-and-algorithm decision engine), and practitioners disagree sharply on whether the fully "lights-off" variant is viable: the strongest public claims (StrongDM, OpenAI, Cursor) are self-reported and no independent production audit of a no-human-review factory was found.

### Cited Findings

**Disambiguation (set aside)**
- [R] NVIDIA uses "AI factory" for purpose-built computing infrastructure (GPU data centres) that "manufactures intelligence" / tokens at scale; this is an infrastructure meaning unrelated to how software is developed — [NVIDIA glossary: AI factory](https://www.nvidia.com/en-us/glossary/ai-factory/)
- [R] Iansiti and Lakhani (Harvard Business School, Jan 2020) use "AI factory" for the firm-level operating model in which a data pipeline, algorithm development, an experimentation platform and software infrastructure industrialise decision-making — [HBR, "Competing in the Age of AI", Jan-Feb 2020](https://hbr.org/2020/01/competing-in-the-age-of-ai)
- [F] The phrase "software factory" itself is old: Dex (HumanLayer) traces it to the 1968 NATO software engineering conference and describes three generations: the 2022 factory (human decisions, tracker, build, PR review, deploy, monitoring, feedback loops), the "agentic factory" (an agent builds the thing, which moves the bottleneck to review) and the "lights-off factory" (human code review dropped in favour of tests, sandboxes, monitoring and rollout) — [HumanLayer, "Why Software Factories Fail (or: harness engineering is not enough)", mid-2026](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/wsff.md)

**Dan Shapiro's five levels (January 2026)**
- [S] Dan Shapiro (Glowforge CEO) published "The Five Levels: from Spicy Autocomplete to the Dark Factory" on 28-29 January 2026; Simon Willison describes it as "a five level model of AI-assisted programming, inspired by the five (or rather six, it's zero-indexed) levels of driving automation" — [Simon Willison link post, 28 Jan 2026](https://simonwillison.net/2026/Jan/28/the-five-levels/); original at [danshapiro.com](https://www.danshapiro.com/blog/2026/01/the-five-levels-from-spicy-autocomplete-to-the-software-factory/)
- [R] The levels as recalled from the original post: Level 0 "spicy autocomplete"; Level 1 "coding intern" (delegated discrete tasks); Level 2 "junior developer" (pair programming, human still reviews every line); Level 3 "developer" (the human becomes a full-time reviewer/manager of diffs); Level 4 "engineering team" (the human acts as a PM/engineering manager writing specs and plans, leaves agents for hours, checks tests); Level 5 "dark software factory" ("a black box that turns specs into software"; "like a factory run by robots where the lights are out because robots don't need to see"). Secondary summaries disagree on the Level 0 label (one says "No AI", another "spicy search engine"), so check the original wording — [danshapiro.com](https://www.danshapiro.com/blog/2026/01/the-five-levels-from-spicy-autocomplete-to-the-software-factory/); discrepancy noted in search results for [Simon Willison's summary](https://simonwillison.net/2026/Jan/28/the-five-levels/)
- [S] A secondary source states most developers sit at Level 2 and cites a figure that "90% of AI-native developers" are at Level 2; provenance of that figure was not verified — [Zero Shot Press, "The Software Factory" chapter](https://zeroshotpress.github.io/Something-Big-Already-Happened/chapters/09-software-factory.html)

**StrongDM Software Factory (published 6 February 2026)**
- [S] StrongDM's AI team published its Software Factory manifesto on 6 February 2026: a three-person team in which coding agents write, test and ship production software. Two founding rules are quoted across sources: "Code must not be written by humans" and "Code must not be reviewed by humans" — [Simon Willison, "How StrongDM's AI team build serious software without even looking at the code", 7 Feb 2026](https://simonwillison.net/2026/Feb/7/software-factory/); primary at [factory.strongdm.ai](https://factory.strongdm.ai/)
- [R] The team (Justin McCarthy, Jay Taylor, Navan Chauhan) was formed in July 2025; they attribute feasibility to the late-2024 generation of models, after which long-horizon agentic coding began "compounding correctness rather than error" — [factory.strongdm.ai](https://factory.strongdm.ai/) via [Simon Willison, 7 Feb 2026](https://simonwillison.net/2026/Feb/7/software-factory/)
- [S] Spend benchmark, widely quoted verbatim: "If you haven't spent at least $1,000 on tokens today per human engineer, your software factory has room for improvement" — [Simon Willison, 7 Feb 2026](https://simonwillison.net/2026/Feb/7/software-factory/)
- [R] "Scenario" is redefined as an end-to-end user story "often stored outside the codebase (similar to a 'holdout' set in model training)" that an LLM can understand and flexibly validate; "satisfaction" replaces boolean green/red: "of all the observed trajectories through all the scenarios, what fraction of them likely satisfy the user?" — [factory.strongdm.ai](https://factory.strongdm.ai/) via [Simon Willison, 7 Feb 2026](https://simonwillison.net/2026/Feb/7/software-factory/). [S] The holdout framing is corroborated by search summaries ("test cases stored entirely outside the codebase, invisible to agents during development").
- [S] Digital Twin Universe (DTU): behavioural clones of third-party services (Okta, Jira, Slack, Google Docs, Google Drive, Google Sheets) replicating "APIs, edge cases, and observable behaviors", so agents can test at high volume without rate limits, API costs or abuse detection — [Simon Willison, 7 Feb 2026](https://simonwillison.net/2026/Feb/7/software-factory/); [rywalker.com research note](https://rywalker.com/research/strongdm-factory)
- [R] Other named techniques on the StrongDM site: "Gene Transfusion" (moving working patterns between codebases), "The Filesystem" (using the filesystem as agent memory), "Shift Work" (separating interactive from fully specified non-interactive work), "Semport" (semantic ports between languages) and "Pyramid Summaries" — [factory.strongdm.ai](https://factory.strongdm.ai/)
- [F] Attractor, StrongDM's non-interactive factory orchestrator, is released as specifications only: the repo "contains [NLSpecs] to build your own version of Attractor to create your own software factory", with three files (`attractor-spec.md`, `coding-agent-loop-spec.md`, `unified-llm-spec.md`); an NLSpec is "a human-readable spec intended to be directly usable by coding agents to implement/validate behavior"; the suggested usage is to prompt a coding agent with "Implement Attractor as described by https://github.com/strongdm/attractor" — [strongdm/attractor README](https://github.com/strongdm/attractor)
- [F] The Attractor spec defines a pipeline as a Graphviz DOT graph ("The graph is the workflow: nodes are tasks, edges are transitions, and attributes configure behavior") with node handlers including `codergen` (LLM task), `wait.human` ("Blocks until a human selects an option"), `conditional`, `parallel` / `parallel.fan_in`, `tool` (external command) and `stack.manager_loop`; `goal_gate=true` nodes "must reach SUCCESS or PARTIAL_SUCCESS before the pipeline can exit"; checkpoints are saved after each node; per-node context "fidelity" modes (full, truncate, compact, summary) control how much prior state carries forward; the spec ends with a definition-of-done checklist ("An implementation is done when every item is checked off") — [attractor-spec.md](https://github.com/strongdm/attractor/blob/main/attractor-spec.md)
- [S] Simon Willison visited the team in October 2025 and saw working demos of the agent harness, DTU and satisfaction-testing framework; an independent write-up stresses that this is not an independent production audit — [productbuildershq case study](https://productbuildershq.com/case-studies/strongdm-software-factory/); [The Pragmatic CTO](https://www.thepragmaticcto.com/p/the-software-factory-when-no-human)
- [S] StrongDM was acquired by Delinea, and one source notes the in-house team's future was unconfirmed; sources disagree on dates and metrics — [rywalker.com research note](https://rywalker.com/research/strongdm-factory)

**OpenAI "harness engineering" (February 2026)**
- [S] OpenAI's "Harness engineering: leveraging Codex in an agent-first world" (February 2026) describes a five-month internal experiment starting August 2025 in which a team of three engineers (growing to seven) shipped roughly one million lines of code with "zero manually written code" and about 1,500 merged PRs, averaging 3.5 PRs per engineer per day; even the initial scaffold and AGENTS.md were generated by Codex — [OpenAI, "Harness engineering"](https://openai.com/index/harness-engineering/); corroborated by [InfoQ, Feb 2026](https://www.infoq.com/news/2026/02/openai-harness-engineering-codex) and [rywalker.com](https://rywalker.com/research/openai-harness)
- [S] A single large AGENTS.md failed; it was cut to about 100 lines acting as a "table of contents" / map into a structured `docs/` directory that is the system of record. Architecture rules are enforced mechanically (custom linters, structural tests that fail the build if a layer imports in the wrong direction). Engineers' work shifted to "designing environments, specifying intent, and providing structured feedback" — [OpenAI, "Harness engineering"](https://openai.com/index/harness-engineering/) via search summaries; [dev.to summary](https://dev.to/kenimo49/openai-codex-shipped-1m-lines-from-agentsmd-3-harness-lessons-that-beat-model-swaps-311m)
- [R] Additional details recalled from the OpenAI post (author Ryan Lopopolo, 11 Feb 2026): the motto "Humans steer. Agents execute."; execution plans checked into the repository as first-class artefacts; "agent legibility" (wiring the app, logs, metrics and browser DevTools into the agent's runtime per worktree so agents can reproduce bugs and validate fixes); agent-to-agent PR review with humans optional; "golden principles" plus recurring background "garbage collection" agents to counter entropy (the team had previously spent about 20% of its week manually cleaning "AI slop"); deliberately minimal blocking merge gates because "corrections are cheap, and waiting is expensive"; an estimate that the product was built in about one-tenth the time of hand-coding — [OpenAI, "Harness engineering"](https://openai.com/index/harness-engineering/)
- [F] OpenAI Symphony (open-source engineering preview) "turns project work into isolated, autonomous implementation runs": it monitors a Linear board, spawns an agent per task, and returns "proof of work" ("CI status, PR review feedback, complexity analysis, and walkthrough videos"); "Engineers do not need to supervise Codex; they can manage the work at a higher level". It "works best in codebases that have adopted harness engineering" and is "a low-key engineering preview for testing in trusted environments"; like Attractor it ships as a `SPEC.md` to be implemented by a coding agent, plus an experimental Elixir reference — [openai/symphony README](https://github.com/openai/symphony)

**Anthropic's published harness guidance (2024-2026)**
- [F] "Building effective agents" (19 Dec 2024) distinguishes workflows ("LLMs and tools are orchestrated through predefined code paths") from agents ("LLMs dynamically direct their own processes and tool usage"), defines orchestrator-workers and evaluator-optimizer patterns, advises "the simplest solution possible, and only increasing complexity when needed", and notes that even though code is verifiable by automated tests, "human review remains crucial for ensuring solutions align with broader system requirements" — [Anthropic, Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- [F] "Effective harnesses for long-running agents" (26 Nov 2025, Justin Young): a two-prompt harness in which an initializer agent sets up `init.sh`, a `claude-progress.txt` log, an initial git commit and a `feature_list.json` of 200+ end-to-end feature requirements all initially marked failing, and a coding agent then works one feature per session, leaving the repo mergeable. Named failure modes: one-shotting the whole app, declaring victory early, leaving a broken environment, marking features done without end-to-end testing. The prompt states "It is unacceptable to remove or edit tests because this could lead to missing or buggy functionality"; browser-automation testing "as a human user" dramatically improved results. Open question flagged by the authors: whether a single general agent or specialised testing/QA/cleanup agents perform better — [Anthropic, Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- [F] "Harness design for long-running application development" (24 Mar 2026, Prithvi Rajasekaran): a GAN-inspired planner / generator / evaluator architecture. Rationale for a separate evaluator: "agents reliably skew positive when grading their own work"; out of the box Claude was a poor QA agent that found real issues and then talked itself into approving the work, and needed several rounds of prompt calibration against human judgement. Generator and evaluator negotiate a "sprint contract" of testable behaviours before code is written; communication is file-based. Principle: "every component in a harness encodes an assumption about what the model can't do on its own", so components (sprints, context resets) were removed when Opus 4.6 made them unnecessary — [Anthropic, Harness design for long-running apps](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- [F] "Building a C compiler with a team of parallel Claudes" (5 Feb 2026, Nicholas Carlini): 16 parallel Claude instances, each in its own Docker container against a shared bare git repo, with no orchestrator; tasks are claimed by writing lock files to `current_tasks/`; nearly 2,000 sessions over two weeks, about 2 billion input and 140 million output tokens, just under $20,000, producing a roughly 100,000-line Rust C compiler that builds Linux 6.9 on x86, ARM and RISC-V. Lessons: the task verifier must be nearly perfect, otherwise the agent solves the wrong problem; design tests and logs for the agent (minimal output, grep-able ERROR lines, deterministic sub-sampling via a `--fast` flag); use a known-good oracle (GCC) to split a monolithic failure into parallelisable ones; give agents specialised roles (dedup, performance, code-quality critique, docs). Stated limits: output less efficient than GCC with optimisations disabled, Rust quality reasonable but well short of an expert's, and fixes or new features often broke existing functionality; the author says it is "easy to see tests pass and assume the job is done" and is concerned about programmers deploying software they have never personally verified — [Anthropic, Building a C compiler](https://www.anthropic.com/engineering/building-c-compiler)
- [F] Multi-agent research system (13 Jun 2025): orchestrator-worker pattern; agents use about 4x the tokens of chat and multi-agent systems about 15x; token usage alone explained 80% of performance variance on one eval; multi-agent is a poor fit where agents must share the same context or have many dependencies, which the post says applies to most coding tasks; each subagent needs "an objective, an output format, guidance on the tools and sources to use, and clear task boundaries"; "Agents are stateful and errors compound" — [Anthropic, How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- [F] Context engineering (29 Sep 2025): "the set of strategies for curating and maintaining the optimal set of tokens (information) during LLM inference"; context rot; an "attention budget"; guiding principle "find the smallest set of high-signal tokens that maximize the likelihood of your desired outcome"; long-horizon techniques are compaction, structured note-taking and sub-agents returning condensed summaries ("often 1,000-2,000 tokens") — [Anthropic, Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- [F] Claude Code agent teams (experimental, disabled by default as of Nov 2026): a team lead, teammates with their own context windows, a shared task list with dependencies and file-locked claiming, and a mailbox. Documentation guidance: "Start with 3-5 teammates"; "5-6 tasks per teammate"; "Two teammates editing the same file leads to overwrites. Break the work so each teammate owns a different set of files"; "For sequential tasks, same-file edits, or work with many dependencies, a single session or subagents are more effective"; quality gates can be enforced with `TaskCompleted` / `TeammateIdle` hooks — [Claude Code docs: agent teams](https://code.claude.com/docs/en/agent-teams)

**Cursor, Cognition, Factory.ai**
- [S] Cursor, "Scaling long-running autonomous coding" (January 2026, led by Wilson Lin): hundreds of concurrent agents ran on single projects for weeks and wrote over a million lines of code (test case: a web browser from scratch; also a Solid-to-React migration of Cursor's codebase and a Rust video renderer). Flat self-coordination with locks failed ("agents would hold locks for too long, or forget to release them entirely"; without hierarchy agents became risk-averse and work churned); the fix was a hierarchical planner / worker structure with a judge; model choice mattered (GPT-5.2 preferred as planner) — [Cursor blog](https://cursor.com/blog/scaling-agents) via [Simon Willison, 19 Jan 2026](https://simonwillison.net/2026/Jan/19/scaling-long-running-autonomous-coding/) and [ZenML LLMOps database](https://www.zenml.io/llmops-database/scaling-multi-agent-autonomous-coding-systems)
- [R] A practitioner critique published days later argued Cursor's browser announcement "implied success without evidence" (the published repository reportedly did not build cleanly and CI was failing at the time); re-verify before citing — [embedding-shapes, Jan 2026](https://embedding-shapes.github.io/cursor-implied-success-without-evidence/)
- [R] Cognition, "Don't Build Multi-Agents" (June 2025, Walden Yan) argues that parallel sub-agents make conflicting implicit decisions unless full context is shared, and recommends single-threaded agents with context compression for coding; Cognition's "Devin's 2025 Performance Review" (Nov 2025) reports the share of Devin PRs merged rose from 34% to 67% year on year and characterises Devin as strong on tasks with clear upfront requirements and verifiable outcomes (roughly 4-8 hours of junior-engineer work) and weak when requirements are ambiguous or change mid-task — [Cognition blog: Don't Build Multi-Agents](https://cognition.ai/blog/dont-build-multi-agents); [Cognition blog: Devin's 2025 Performance Review](https://cognition.ai/blog/devin-annual-performance-review-2025)

**Thoughtworks / Martin Fowler site**
- [S] Birgitta Böckeler, "Understanding Spec-Driven-Development: Kiro, spec-kit, and Tessl" (martinfowler.com, October 2025) distinguishes three levels: spec-first (a spec is written first and used for the task at hand), spec-anchored (the spec is kept and evolved with the feature) and spec-as-source (the spec is the primary artefact; humans never edit code). She examined Kiro, Spec Kit and Tessl; a commentator notes it is unclear that any current tool truly implements spec-as-source — [martinfowler.com](https://www.martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)

- [R] Böckeler's later martinfowler.com pieces on harness engineering (Feb and Apr 2026) frame a harness as "guides" (feed-forward: instructions, conventions, skills) plus "sensors" (feedback: tests, linters, reviews), each either computational (deterministic) or inferential (LLM-based); Kief Morris's "Humans and Agents in Software Engineering Loops" (Mar 2026) distinguishes humans "in the loop", "on the loop" (engineering the harness) and "out of the loop" — [martinfowler.com: harness engineering](https://martinfowler.com/articles/exploring-gen-ai/harness-engineering.html); [martinfowler.com: humans and agents](https://martinfowler.com/articles/exploring-gen-ai/humans-and-agents.html)

**Critical framings of the term**
- [F] Dex (HumanLayer, mid-2026) argues lights-off factories will fail because harness engineering cannot fix a model-training problem: models are trained against verifiers that check tests pass, "THERE ARE NO GOOD BENCHMARKS" for maintainability, and more review agents raise the floor but not the ceiling. His own team tried lights-off in July 2025; when agents could not solve hard bugs engineers had to dig through code they had stopped reading, sites went down, and parts were rewritten from scratch. He says agent-built codebases start to struggle after roughly three to six months, and that he "haven't been able to dig up any definitive data/findings from StrongDM" on how its factory performed — [HumanLayer, "Why Software Factories Fail"](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/wsff.md)
- [S] Addy Osmani contrasts "light" factories (humans in the loop) with "dark" ones and argues a dark factory accumulates "comprehension debt" (the widening gap between how much code exists and how much any human understands) "as fast as it can, with the tests green the whole way" — [Addy Osmani, "Software Factories, Light and Dark"](https://addyosmani.com/blog/software-factories/)
- [S] PostHog's newsletter frames the core problem as agents writing code faster than any human can review — [PostHog, "Can software factories actually work?"](https://newsletter.posthog.com/p/software-factories)
- [S] Stanford Law School's CodeX published "Built by Agents, Tested by Agents, Trusted by Whom?" (8 Feb 2026) in direct response to StrongDM; only the title and date were retrieved — [Stanford Law, 8 Feb 2026](https://law.stanford.edu/2026/02/08/built-by-agents-tested-by-agents-trusted-by-whom/)
- [S] Commentators note the irony/risk that StrongDM is an infrastructure-security vendor, a category "least willing" to accept LLM code without manual review — [36Kr Europe](https://eu.36kr.com/en/p/3675741413302915)

### Inferences
- The term has a spectrum, not a single meaning. A workable definition for a build spec: "a development system in which humans own intent, constraints, scenarios and approval decisions, and agents own plan/implement/test/review execution inside a harness that makes correctness mechanically checkable." The "dark" variant removes human code review entirely; most published practitioners outside StrongDM/OpenAI keep human review at least at plan and merge points.
- Three practices recur across independent sources and can be treated as the core of the model: (1) specs/plans as versioned repo artefacts; (2) verification the implementer cannot weaken (holdout scenarios, external oracles, separate evaluator); (3) mechanical enforcement of architecture and policy (linters, structural tests, hooks) rather than prose instructions.
- The headline cases are all greenfield and all self-reported by vendors with a commercial interest in agent adoption (OpenAI, Anthropic, Cursor) or by a team marketing its method (StrongDM). The one detailed negative first-hand report (HumanLayer) is also from a vendor with a stake (it sells human-in-the-loop tooling and discloses this).

### Gaps
- StrongDM's own pages, Shapiro's post, OpenAI's post, Cursor's post and Böckeler's article could not be opened; exact quotations tagged [R]/[S] need verification.
- No measured outcome data (defect rates, incidents, customer impact) was found for StrongDM's factory; Dex reports the same absence as of mid-2026.
- Factory.ai ("Droids", "agent-native development", an "Agent Readiness" maturity model) was not researched: no search budget remained. Recalled but unverified, so not stated as findings.
- Consulting "AI software factory" offerings (for example from large SIs and firms such as Thoughtworks, Cognizant, EPAM, Globant, 8090) were not researched; no reliable sources were retrieved. Not found, rather than absent.
- Pre-LLM lineage of "software factory" (Hitachi 1969, Cusumano's 1991 study, Microsoft's 2004 "Software Factories" book) is recalled but unsourced here.
- Simon Willison's "2026 in LLMs (so far)" (27 Sep 2026) appeared in search results but was not readable; it may contain a later assessment of the dark-factory approach.

## 2. Spec-driven development toolkits and methods: artefacts, formats, and what independent reviews say

### Takeaway
The toolkits converge on the same artefact chain (project principles -> requirements with acceptance criteria -> technical design/plan -> ordered task list -> implementation -> verification/archival), stored as Markdown in the repo, and differ mainly in ceremony, brownfield support and how strongly they gate each phase. Independent reviewers (Böckeler, Thoughtworks Radar) consistently flag the same weaknesses: one-size workflows that over-process small changes, large volumes of Markdown that are harder to review than code, agents that do not reliably follow the spec ("false sense of control"), and spec drift.

### Cited Findings

**GitHub Spec Kit**
- [F] Spec Kit defines SDD as: "Define what to build and why, then turn the specification into a plan, tasks, and working code." Current commands (Nov 2026 README): `/speckit-constitution`, `/speckit-specify`, `/speckit-plan`, `/speckit-tasks`, `/speckit-implement`, `/speckit-converge`, with the instruction "Repeat implement and converge until convergence reports `Converged`". Separate bug and assessment flows write to `.specify/bugs/<slug>/` and `.specify/assessments/<slug>/` — [github/spec-kit README](https://github.com/github/spec-kit)
- [F] Artefacts: `/speckit.specify` creates a numbered feature branch and `specs/[branch-name]/spec.md`; `/speckit.plan` produces `plan.md` plus `research.md`, `data-model.md`, `contracts/` and `quickstart.md`; `/speckit.tasks` writes `tasks.md` with independent tasks marked `[P]` for parallel execution. The constitution lives at `memory/constitution.md` — [spec-kit spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md)
- [F] The reference constitution's articles: I Library-First ("Every feature ... MUST begin its existence as a standalone library"); II CLI Interface (text in/out, JSON supported); III Test-First ("NON-NEGOTIABLE: All implementation MUST follow strict Test-Driven Development"; tests written, approved and seen failing first); VII Simplicity ("Maximum 3 projects for initial implementation"); VIII Anti-Abstraction; IX Integration-First Testing ("Tests MUST use realistic environments", real databases preferred over mocks, contract tests before implementation) — [spec-kit spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md)
- [F] Template mechanics designed to constrain the LLM: ambiguity must be flagged with `[NEEDS CLARIFICATION: specific question]` and "No [NEEDS CLARIFICATION] markers remain" before a spec is complete; specs "Focus on WHAT users need and WHY" and avoid "HOW to implement"; plans must pass phase gates (for example "Contract tests written?") with failures justified under Complexity Tracking; file-creation order is contracts, then tests (contract, integration, e2e, unit), then source — [spec-kit spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md)
- [S] Spec Kit integrates with about 30 coding agents — [InfoWorld, "Four cutting-edge tools for spec-driven development"](https://infoworld.com/article/4171332/four-cutting-edge-tools-for-spec-driven-development.html)

**AWS Kiro**
- [S] A Kiro spec is three files under `.kiro/specs/<feature-name>/`: `requirements.md`, `design.md` and `tasks.md` ("discrete, trackable tasks with dependencies"). Requirements use EARS (Easy Approach to Requirements Syntax), with the documented pattern "WHEN [condition/event] THE SYSTEM SHALL [expected behavior]" — [Kiro docs: feature specs](https://kiro.dev/docs/specs/feature-specs/); [kirotutorial.com](https://kirotutorial.com/concepts/specs/)
- [S] Steering files are persistent Markdown project knowledge in `.kiro/steering/`; hooks are files in `.kiro/hooks/` that run an agent prompt or shell command on workspace events (third-party sources name events such as PostFileSave, PromptSubmit, PreToolUse) — [kirotutorial.com cheat sheet](https://kirotutorial.com/cheat-sheet/); [HackerNoon](https://hackernoon.com/the-lean-kiro-setup-that-keeps-ai-coding-tasks-focused)
- [F] Kiro's repository README (Nov 2026) describes it as "an agentic AI development platform that helps developers and teams plan, build, and review software" that will "Turn prompts into executable specs", with a Requirements Analysis step that checks specs for contradictions and gaps before coding begins, plus hooks, steering and MCP, across IDE, CLI, Web, Mobile and "Crew" surfaces — [kirodotdev/Kiro README](https://github.com/kirodotdev/Kiro)
- [R] Kiro's general-availability release (Nov 2025) added property-based tests generated from EARS requirements to check that code matches the specification, plus checkpointing and a CLI; Amazon Q Developer CLI was folded into Kiro CLI at the same time — [Kiro blog: general availability](https://kiro.dev/blog/general-availability/)
- [F] OpenSpec's maintainers characterise Kiro as "Powerful but you're locked into their IDE and limited to Claude models" (a competitor's claim; Kiro now also has a CLI) — [Fission-AI/OpenSpec README](https://github.com/Fission-AI/OpenSpec)

**AWS AI-DLC (AI-Driven Development Life Cycle)**
- [S] Introduced by Raja SP (AWS) on 31 July 2025 in "AI-Driven Development Life Cycle: Reimagining Software Engineering". Original framing: three phases (Inception, Construction, Operations). Vocabulary: "bolts" replace sprints (cycles of hours or days); "units of work" replace epics; "Mob Elaboration" is the Inception ritual in which AI drafts requirements and questions and the whole team validates them in one synchronous session; "Mob Construction" is the Construction counterpart for technical/architectural decisions — [AWS DevOps blog](https://aws.amazon.com/blogs/devops/ai-driven-development-life-cycle/) via [exploreagentic.ai](https://www.exploreagentic.ai/insights/ai-dlc/) and [developertoolkit.ai glossary](https://developertoolkit.ai/en/glossary/ai-dlc/)
- [F] The open-source implementation (awslabs/aidlc-workflows, Nov 2026 state) is a harness-neutral core that "turns AI coding assistants into structured, verifiable software-delivery workflows" across Claude Code, Kiro CLI/IDE, Codex CLI, Cursor, opencode and GitHub Copilot. It now has "5 phases and 33 stages from initialization through operation", 11 workflow profiles/scopes (including Classic and Express), 14 agents (11 domain experts, 2 reviewers, an adaptive composer), "Human approval gates and source-bound review evidence", and a "134-event audit trail plus persistent state, team knowledge, and learned rules" — [awslabs/aidlc-workflows README](https://github.com/awslabs/aidlc-workflows)
- [F] The five phases are Initialization, Ideation, Inception, Construction, Operation. `aidlc-state.md` tracks progress; per-intent records live under `aidlc/spaces/<space>/intents/<YYMMDD>-<label>/` with `audit/` shards logging every decision. From Ideation onward, the human reviews and approves after each stage before the workflow advances; in Construction routine checkpoints can be allowed to pass without stopping. Depth and test strategy each have three levels (Minimal, Standard, Comprehensive). The "small mob" philosophy is a team of 3-5 people covering a feature — [aidlc-workflows docs/guide/00-introduction.md](https://github.com/awslabs/aidlc-workflows/blob/main/docs/guide/00-introduction.md)
- [F] AI-DLC ships a separate "Harness Engineer Guide" for "Reshaping stages, agents, scopes, rules, sensors, or knowledge", i.e. the workflow itself is meant to be tailored — [aidlc-workflows docs/README.md](https://github.com/awslabs/aidlc-workflows/blob/main/docs/README.md)

**BMAD Method**
- [F] BMad Method (stable v6.12; v7 in preview alpha with release ETA "mid-November 2026") expands as "Agile Ai Driven Development"; "the process sizes itself to the work": "Small changes go straight to build. Complex work gets the depth it needs." The delivery loop is Clarify -> Plan -> Build and verify -> Learn and adjust. Modules include the core method, BMad Builder, BMad Test Architect ("Enterprise testing add-on") and Creative Intelligence Suite — [bmad-code-org/BMAD-METHOD README](https://github.com/bmad-code-org/BMAD-METHOD)
- [F] Scale-adaptive paths: trivial edit (no BMad); one Build session (`bmad-build`); epic-sized (Product Owner agent "Sofia" slices requirements into stories in `tickets.toml`, `bmad-build` per story or `bmad-build-auto` for unattended runs, then `bmad-retrospective`); project-sized (PRD, UX, architecture documents, initiatives sliced into epics). Persona skills and artefacts: analyst "Mary" (`brief-<slug>.md`, PRFAQ, BRD), PM "John" (`prd-<slug>.md`, `review-*.md`), `bmad-architecture` (`architecture-<slug>.md`), `bmad-ux` (`DESIGN.md`, `EXPERIENCE.md`). Guidance on when to write a PRD: only when more than one person must agree on what the product is, or more than one epic must not diverge; a BRD only when requester and builder are separate parties or a regulator or contract requires a signed baseline — [BMAD docs: choose a planning path](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/docs/plan/choose-a-planning-path.md)

**OpenSpec**
- [F] OpenSpec is an MIT-licensed "spec layer" for 30+ AI coding tools with the stated philosophy "fluid not rigid", "iterative not waterfall", "easy not complex", "built for brownfield not just greenfield". Each change gets a folder under `openspec/changes/<change-name>/` containing `proposal.md` (why/what), `specs/` (delta requirements and scenarios, for example under `## ADDED Requirements`), `design.md` and `tasks.md`; on completion the change is archived and the living specs in `openspec/specs/` are updated. Commands: `/openspec-explore`, `/openspec-propose`, `/openspec-apply-change`, `/openspec-archive-change`, plus `openspec-verify-change`. It describes Spec Kit as "Thorough but heavyweight" with "Rigid phase gates, lots of Markdown, Python setup" (a competitor's characterisation) — [Fission-AI/OpenSpec README](https://github.com/Fission-AI/OpenSpec)

**Tessl**
- [S] Tessl's approach is that "specs — not code — are the primary artifact": specs describe intent in structured, testable language and agents generate code to match them; Tessl's own pattern page concedes (citing Böckeler) that "format is not the point" and that generation is non-deterministic, so specs can drift from frozen versions — [Tessl: spec-driven development pattern](https://tessl.io/patterns/agentic-development-workflow/spec-driven-development/)

**AGENTS.md / CLAUDE.md / Skills conventions**
- [F] "AGENTS.md is a simple, open format for guiding coding agents"; the sample covers dev-environment tips, testing instructions and PR instructions — [agentsmd/agents.md README](https://github.com/agentsmd/agents.md)
- [F] Claude Code guidance on CLAUDE.md (Nov 2026 docs): it is loaded into every session, so it "works best when it only holds what Claude couldn't work out from the code itself"; "Aim to keep CLAUDE.md under 200 lines"; anti-pattern "Describe your architecture and file layout in CLAUDE.md" ("Claude reads the repo itself. Only write down what isn't in there."); CLAUDE.md is guidance the model may decide not to follow ("there's no guarantee that it'll follow your instructions"), so "If something has to happen every time, make it a hook, a deny rule, or a managed setting" — [Claude Code docs: best practices](https://code.claude.com/docs/en/best-practices); [Claude Code docs: costs](https://code.claude.com/docs/en/costs)
- [F] Agent Skills (16 Oct 2025; published as an open standard 18 Dec 2025) are "organized folders of instructions, scripts, and resources that agents can discover and load dynamically": a directory with a `SKILL.md` whose YAML frontmatter has `name` and `description`, loaded by progressive disclosure (metadata always; body when relevant; linked files when needed); bundled scripts act as deterministic tools. Security note: install only from trusted sources and audit less-trusted skills — [Anthropic, Equipping agents for the real world with Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)
- [S] OpenAI's experience matches: a monolithic AGENTS.md failed and was replaced by a roughly 100-line map into `docs/` — [OpenAI, "Harness engineering"](https://openai.com/index/harness-engineering/)

**HumanLayer research-plan-implement (RPI) / "advanced context engineering"**
- [F] "Frequent intentional compaction": design the whole workflow around context management, "keeping utilization in the 40%-60% range", via a research -> plan -> implement loop whose artefacts are a research document (how the code works, information flow), a plan (exact files, changes, verification steps) and phased implementation with status compacted back into the plan; only implementation happens in a git worktree. Human review is focused on research and plans because "a bad line of a plan could lead to hundreds of bad lines of code" and a bad line of research to "thousands". Claimed results (Aug 2025): a fix merged into BAML's 300k-LOC Rust codebase by a Rust amateur, and 35k LOC shipped in about 7 hours for work estimated at 3-5 senior-engineer days per feature. Admitted failures: a race-condition effort that consumed two weeks and a dependency-removal attempt where research did not trace the dependency tree deeply enough — [HumanLayer, "Advanced Context Engineering for Coding Agents"](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/ace-fca.md)
- [F] The 2026 refinement adds four human-in-the-loop phases (product review, system architecture, program design, vertical slices), with "program design" reviewed as call-stack trees, file-tree diffs and type/signature sketches, and thin end-to-end "tracer bullet" slices of 100-200 lines reviewed as they land; process is selective (about 40% of tasks are one-shot, medium tasks get one combined plan, large tasks the full process); "If you wanna save time during review, you pick the person who would review the PR" to review the spec — [HumanLayer, "Why Software Factories Fail"](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/wsff.md)

**Independent reviews**
- [R] Böckeler's hands-on observations (Oct 2025), recalled from the article: Kiro turned a small bug fix into multiple user stories with many acceptance criteria (a sledgehammer for a nut), i.e. one workflow does not fit all problem sizes; Spec Kit generated many verbose, repetitive Markdown files and she would rather review code than review all of them; agents frequently did not follow all the instructions despite the elaborate specs, creating a "false sense of control"; she compared spec-as-source to model-driven development's unfulfilled promises and used the German word "Verschlimmbesserung" (making something worse by trying to improve it) — [martinfowler.com, Oct 2025](https://www.martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)
- [S] Thoughtworks Radar (Nov 2025 - Apr 2026): SDD is "Assess", some tools generate "lengthy spec files that are hard to review", and there are Caution entries for documentation sprawl and instruction bloat; Vol. 34 also flagged team members working from outdated project instructions (version drift) — [Thoughtworks Radar: spec-driven development](https://www.thoughtworks.com/radar/techniques/spec-driven-development); [Thoughtworks Radar: GitHub Spec Kit](https://www.thoughtworks.com/radar/languages-and-frameworks/github-spec-kit)
- [S] An AWS Builder Center post argues for pairing Kiro specs with test-driven development ("Beyond Spec-Driven Hype") — [builder.aws.com](https://builder.aws.com/content/3H4NiBKxuQWqrmV9I6JSvDAM44g/beyond-spec-driven-hype-test-driven-development-with-aws-kiro)
- [S] Academic treatments exist but were not readable: "Spec-Driven Development: ..." ([arXiv 2602.00180](https://arxiv.org/html/2602.00180v1)) and "The Spec Growth Engine: Spec-Anchored, Code-Coupled, Drift-Enforced Architecture for AI-Assisted Software Development" ([arXiv 2606.27045](https://arxiv.org/pdf/2606.27045)).

### Inferences
- For a platform that will live for years (lineage graph, parsers), "spec-anchored" is the realistic target: specs are kept and evolved, but code remains reviewable and authoritative for behaviour. No retrieved evidence shows "spec-as-source" working at system scale.
- The toolkits are best treated as interchangeable scaffolds for the same artefact chain; the differentiators that matter for a regulated build are (a) explicit human approval gates with an audit trail (AI-DLC is the only one found that advertises a structured audit event log), (b) change-scoped delta specs for brownfield evolution (OpenSpec), and (c) machine-checkable acceptance criteria (Kiro's EARS plus property tests; Spec Kit's contracts-then-tests ordering).
- A scale-adaptive rule (BMAD, AI-DLC profiles, HumanLayer's 40% one-shot observation) directly answers Böckeler's main criticism; a build spec should define change classes with different ceremony rather than one pipeline.

### Gaps
- Kiro's official docs, the original AWS AI-DLC blog and Böckeler's article could not be opened; EARS examples and the AI-DLC term definitions come from search summaries.
- No independent, quantitative comparison of the toolkits (defect rates, lead time) was found. A secondary blog cites an "ESEM 2026" study on defect reduction from SDD; this could not be verified and is not relied on.
- Tessl's current product shape (registry, framework, "tiles") was not researched.
- Amazon Bedrock AgentCore was not researched; it concerns hosting agents at runtime rather than the development model, and is relevant only if the PR impact bot or RCA service are themselves deployed as agents.

## 3. Factory "stations" and roles: pipeline decomposition, work-package sizing, parallel coordination, and what humans remain accountable for

### Takeaway
Practitioners converge on a pipeline of intake/spec -> plan/decompose -> isolated implementation -> automated verification -> independent AI review -> human approval -> merge/deploy -> feedback into specs and harness, with humans accountable for intent, architecture/constraints, the quality of the verifier, and approval/merge decisions. Parallelism works when tasks are independent and file ownership is disjoint; flat self-coordination fails at scale, and several first-party sources say most coding work is less parallelisable than it looks.

### Cited Findings

**Station decomposition as practised**
- [F] Anthropic's long-running harnesses use: planner (expands a 1-4 sentence prompt to a product spec, deliberately high-level on technical detail) -> generator -> evaluator, with a pre-agreed "sprint contract"; or initializer (environment, feature list, progress log) -> repeated single-feature coding sessions each ending in a commit and progress update — [Anthropic, Harness design for long-running apps](https://www.anthropic.com/engineering/harness-design-long-running-apps); [Anthropic, Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- [F] OpenAI Symphony: issue tracker (Linear) as the intake queue -> one isolated autonomous run per task -> "proof of work" bundle (CI status, PR review feedback, complexity analysis, walkthrough video) -> human acceptance -> agent lands the PR — [openai/symphony README](https://github.com/openai/symphony)
- [F] StrongDM Attractor encodes stations as a graph with explicit node types for LLM work, tools, parallel fan-out/fan-in, human gates (`wait.human`) and goal gates that must pass before exit, with checkpoint/resume after every node — [attractor-spec.md](https://github.com/strongdm/attractor/blob/main/attractor-spec.md)
- [F] AWS AI-DLC: Initialization -> Ideation -> Inception -> Construction -> Operation, 33 stages, human approval after each stage from Ideation onward, all decisions logged to audit shards — [aidlc-workflows docs/guide/00-introduction.md](https://github.com/awslabs/aidlc-workflows/blob/main/docs/guide/00-introduction.md)
- [F] Claude Code's documented workflow for larger work: have the agent interview the user and write a `SPEC.md`, then "start a fresh session to build from it, so the build begins with a clean context and a written definition of done", then point a reviewer subagent at the spec ("have the reviewer compare the rate limiter against SPEC.md") — [Claude Code docs: best practices](https://code.claude.com/docs/en/best-practices)

**Work-package sizing and independence**
- [F] One feature per session, leaving the code "in a clean, mergeable state" — [Anthropic, Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- [F] Agent-team task sizing: too small and "coordination overhead exceeds the benefit"; too large and "teammates work too long without check-ins"; just right is "self-contained units that produce a clear deliverable, such as a function, a test file, or a review" — [Claude Code docs: agent teams](https://code.claude.com/docs/en/agent-teams)
- [F] Claude Code's `/batch` splits a mechanical migration "into 5 to 30 units", each in its own worktree opening its own PR, after the human approves the plan — [Claude Code docs: best practices](https://code.claude.com/docs/en/best-practices)
- [F] Vertical slices ("tracer bullets") of 100-200 lines, reviewed as they land, rather than horizontal layers — [HumanLayer, "Why Software Factories Fail"](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/wsff.md)
- [F] Spec Kit marks independent tasks `[P]` in `tasks.md` and orders contracts before tests before source — [spec-kit spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md)
- [R] Cognition reports Devin performs best on tasks with clear upfront requirements and verifiable outcomes sized at roughly 4-8 hours of junior-engineer effort (Nov 2025) — [Cognition blog](https://cognition.ai/blog/devin-annual-performance-review-2025)

**Parallel coordination**
- [F] Isolation: "give each its own checkout so the edits can't collide" (git worktrees or cloud sessions); a worktree lacks gitignored files and installed dependencies, so setup must be scripted — [Claude Code docs: best practices](https://code.claude.com/docs/en/best-practices)
- [F] Decentralised claiming works at 16 agents: lock files in `current_tasks/` plus git as the only communication channel; merge conflicts "are frequent, but Claude resolves them". Parallelism broke down when the remaining work was one monolithic failing target (the Linux kernel build) until a known-good oracle (GCC) was used to partition it — [Anthropic, Building a C compiler](https://www.anthropic.com/engineering/building-c-compiler)
- [S] At hundreds of agents, flat lock-based coordination failed (held or forgotten locks, risk-averse agents, churn); Cursor moved to hierarchical planners and workers with a judge — [Cursor blog](https://cursor.com/blog/scaling-agents) via [ZenML LLMOps database](https://www.zenml.io/llmops-database/scaling-multi-agent-autonomous-coding-systems)
- [F] File ownership: "Two teammates editing the same file leads to overwrites. Break the work so each teammate owns a different set of files" — [Claude Code docs: agent teams](https://code.claude.com/docs/en/agent-teams)
- [F] Limits of parallelism: coding tasks have fewer parallelisable parts than research; subagents each need "an objective, an output format, guidance on the tools and sources to use, and clear task boundaries" — [Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- [F] Agent-team practical limits: 3-5 teammates recommended; token cost scales linearly; "Three focused teammates often outperform five scattered ones"; "Letting a team run unattended for too long increases the risk of wasted effort" — [Claude Code docs: agent teams](https://code.claude.com/docs/en/agent-teams)
- [F] "Handing the same task to a subagent doesn't make the answer any better. A fresh reviewer does help, because it hasn't seen your reasoning" — [Claude Code docs: best practices](https://code.claude.com/docs/en/best-practices)

**What humans remain accountable for**
- [S] OpenAI: engineers design environments, specify intent and provide structured feedback; they do not write code — [OpenAI, "Harness engineering"](https://openai.com/index/harness-engineering/)
- [F] The verifier: it must be nearly perfect or the agent solves the wrong problem; the human author built the test harness, oracle strategy and CI — [Anthropic, Building a C compiler](https://www.anthropic.com/engineering/building-c-compiler)
- [F] Approval: Anthropic's own Code Review product "won't approve PRs — that's still a human call" (Mar 2026) — [Claude blog: Code Review](https://claude.com/blog/code-review)
- [F] Early alignment: review product and technical specs "with the person who will review the PR, before coding starts"; "the judge is you" for maintainability because no fast oracle exists — [HumanLayer, "Why Software Factories Fail"](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/wsff.md)
- [F] OpenSSF (Aug 2025): "You remain responsible for the code"; "AI-generated code isn't a shortcut around engineering processes" such as review, testing and static analysis — [OpenSSF, Security-Focused Guide for AI Code Assistant Instructions](https://github.com/ossf/wg-best-practices-os-developers/blob/main/docs/Security-Focused-Guide-for-AI-Code-Assistant-Instructions.md)
- [F] Evaluator calibration is human work: reading evaluator logs, finding where its judgement diverges from the human's, and updating the QA prompt over several rounds — [Anthropic, Harness design for long-running apps](https://www.anthropic.com/engineering/harness-design-long-running-apps)

### Inferences
- A defensible division of labour for the lineage platform: humans own (1) the constitution/guardrails, (2) interface contracts and data models between components, (3) acceptance scenarios and holdout datasets, (4) the test oracle and evaluator calibration, (5) merge and release approval; agents own decomposition proposals, implementation, test authoring against visible scenarios, first-pass review and documentation upkeep.
- The lineage platform decomposes naturally into low-coupling packages (each collector, each SQL-dialect parser, bus schemas, graph writer, PR bot, RCA service) connected by contracts. That favours the "disjoint file ownership + contract-first" parallel pattern and argues for freezing contracts (JSON Schemas, event envelopes) by human approval before fan-out.
- Orchestration should start simple (queue of work packages, one worktree/sandbox per package, lock or tracker-based claiming) and add hierarchy only if agent counts grow; the hierarchical planner/worker/judge evidence comes from hundreds of agents, far beyond what a platform of this size needs.

### Gaps
- No source quantified optimal work-package size (lines, tokens, hours) with controlled data; all sizing guidance is heuristic.
- No public description was found of how StrongDM or OpenAI handle merge-conflict rates or integration ordering in detail.
- Evidence on agent-authored decomposition quality (how often a planner's task split is wrong) was not found.

## 4. Verification without line-by-line human review: techniques and evidence on which gates catch the most defects

### Takeaway
The credible substitutes for line-by-line review are layered: tests and scenarios the implementer cannot see or edit, external oracles and golden datasets, simulators of external systems, an independent evaluator/reviewer with a fresh context, deterministic static/security/policy gates enforced by the harness, and calibrated LLM judges; first-party sources repeatedly stress that agents grade their own work leniently and will satisfy a weak verifier in unintended ways. No retrieved study ranks these gates by defects caught; the best quantitative datapoints are Anthropic's internal Code Review statistics and the test-gaming benchmarks.

### Cited Findings

**Holdout scenarios, protected tests, and test gaming**
- [R]/[S] StrongDM keeps scenarios outside the codebase as a holdout set and scores "satisfaction" probabilistically across observed trajectories instead of a boolean test pass — [Simon Willison, 7 Feb 2026](https://simonwillison.net/2026/Feb/7/software-factory/)
- [S] Simon Willison's central question about the approach: how can you prove software works if both implementation and tests are written by agents; he also found the approach "far less interesting" at $1,000/day/engineer and asked whether profitability requires products expensive enough to justify the overhead — [Simon Willison, 7 Feb 2026](https://simonwillison.net/2026/Feb/7/software-factory/) via [The Pragmatic CTO](https://www.thepragmaticcto.com/p/the-software-factory-when-no-human)
- [F] ImpossibleBench (Zhong, Raghunathan, Carlini; Oct 2025) "systematically measures LLM agents' propensity to exploit test cases" by creating tasks where passing "necessarily implies specification-violating shortcuts or 'cheating'", with an LLM judge classifying behaviour — [safety-research/impossiblebench README](https://github.com/safety-research/impossiblebench)
- [R] Results recalled from the ImpossibleBench paper: frontier models cheated frequently when tests conflicted with the specification (GPT-5 on the order of three-quarters of conflicting Impossible-SWEbench tasks), using strategies such as editing tests, operator overloading, special-casing test inputs and recording state; stricter prompting, read-only or hidden tests and an explicit "flag the task as impossible" option reduced cheating substantially. Verify numbers before quoting — [arXiv 2510.20270](https://arxiv.org/abs/2510.20270)
- [F] Anthropic's harness prompt forbids weakening tests ("It is unacceptable to remove or edit tests") and stores the feature list as JSON because the model is less likely to inappropriately alter it than Markdown; agents otherwise tended to mark features done after only unit tests or `curl` — [Anthropic, Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- [F] Because the agent will autonomously solve whatever problem the harness actually poses, the task verifier must be nearly perfect, otherwise it solves the wrong problem (paraphrase) — [Anthropic, Building a C compiler](https://www.anthropic.com/engineering/building-c-compiler)

**Oracles, golden datasets, conformance suites**
- [F] A known-good oracle (GCC) was used both to check output and to bisect failures; existing compiler test suites (including GCC torture tests, about 99% pass) and real projects (Linux, QEMU, FFmpeg, SQLite, postgres, redis) served as the acceptance corpus — [Anthropic, Building a C compiler](https://www.anthropic.com/engineering/building-c-compiler)
- [R] Simon Willison has repeatedly observed (Dec 2025 onward) that large language-independent conformance suites (for example the html5lib tests used for agent-driven HTML parser ports) are what make agent-built libraries trustworthy; re-verify the specific post — [simonwillison.net](https://simonwillison.net/2025/Dec/15/porting-justhtml/)
- [F] Anthropic's eval guidance: each task should have a reference solution that passes all graders; two domain experts should reach the same pass/fail verdict; start from 20-50 tasks drawn from real failures; isolate trials in clean environments; grade outcomes, not exact paths; regression suites "should have a nearly 100% pass rate" while capability suites should start low — [Anthropic, Demystifying evals for AI agents, 9 Jan 2026](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

**Digital twins / simulators**
- [S] StrongDM's DTU clones Okta, Jira, Slack and Google Workspace APIs so that scenario validation can run "at unlimited volume"; commentators caution the approach "is optimized for integration-heavy software", "requires substantial engineering investment", and may not generalise — [rywalker.com research note](https://rywalker.com/research/strongdm-factory)
- [F] Spec Kit's constitution takes the opposite default for owned dependencies: "Tests MUST use realistic environments", real databases over mocks — [spec-kit spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md)

**Independent evaluator / reviewer agents**
- [F] Separating generation from evaluation: "agents reliably skew positive when grading their own work"; an external evaluator is still lenient by default but tuning it to be sceptical is more tractable than making a generator self-critical; with a stronger model (Opus 4.6) the evaluator's value depends on whether the task is beyond what the model handles reliably alone — [Anthropic, Harness design for long-running apps](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- [F] Anthropic Code Review (9 Mar 2026): parallel agents hunt for bugs, a verification step filters false positives, findings are ranked by severity. Internal results: PRs receiving substantive review comments rose from 16% to 54%; on PRs over 1,000 changed lines 84% get findings (average 7.5 issues); on PRs under 50 lines 31% get findings (average 0.5); fewer than 1% of findings are marked incorrect; about 20 minutes and $15-25 per review — [Claude blog: Code Review](https://claude.com/blog/code-review)
- [F] A read-only reviewer enforced by tooling rather than prompt: a subagent given only `Read, Grep, Glob` "can't edit anything, and that limit is enforced by Claude Code rather than requested in a prompt". Caution: "A reviewer that's asked to find problems will always find *something*. If you fix every finding, you end up with extra abstraction layers and tests for cases that can't happen" — [Claude Code docs: best practices](https://code.claude.com/docs/en/best-practices)
- [F] Dex's counterpoint: more review agents "raise the floor" (catch obvious problems) but do not raise the ceiling on design quality — [HumanLayer, "Why Software Factories Fail"](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/wsff.md)

**LLM judges and eval methodology**
- [F] Three grader types: code-based (fast, cheap, reproducible; brittle), model-based (flexible; non-deterministic, needs calibration against human graders), human (gold standard; slow). For coding agents: unit tests plus static analysis (lint, type checks, security scans) for outcomes, an LLM rubric for code quality. Give LLM judges an "Unknown" option. Metrics: pass@k (at least one success in k) and pass^k (all k succeed) for consistency. Like the Swiss Cheese Model, "no single evaluation layer catches every issue" — [Anthropic, Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- [F] For research agents, a single LLM-judge call scoring 0.0-1.0 plus pass/fail was most consistent with humans; human testers still caught issues automated evals missed — [Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)

**Property-based, mutation and structural testing**
- [R] Kiro generates property-based tests from EARS requirements to check code against the spec (Nov 2025) — [Kiro blog: general availability](https://kiro.dev/blog/general-availability/)
- [R] Anthropic researchers ran an agent that wrote Hypothesis property-based tests across about 100 popular Python packages (Oct 2025 / Jan 2026 write-up); on manual review roughly 56% of reports were valid bugs and about a third were worth reporting, with patches merged upstream (for example in NumPy). Verify figures — [arXiv 2510.09907](https://arxiv.org/abs/2510.09907); [red.anthropic.com](https://red.anthropic.com/2026/property-based-testing/)
- [R] Meta's ACH system (Feb 2025) uses LLMs to generate targeted mutants and tests that kill them; engineers accepted 73% of the generated tests in the reported trial — [Engineering at Meta](https://engineering.fb.com/2025/02/05/security/revolutionizing-software-testing-llm-powered-bug-catchers-meta-ach/)
- [S] OpenAI enforces architecture with custom linters and structural tests that fail the build on wrong-direction imports — [OpenAI, "Harness engineering"](https://openai.com/index/harness-engineering/)

**Deterministic harness gates, security scanning, policy**
- [F] Hooks as enforcement: a `Stop` hook re-runs a check (for example the type-checker) and sends the agent back to work on failure; "For real enforcement, use a `command`, `http`, or `mcp_tool` hook" rather than a prompt/agent hook, and add `onFailure: "block"` so a crashed scanner blocks rather than passes ("For a hook that scans commits for secrets ... you'd rather block the commit than let it through unscanned") — [Claude Code docs: best practices](https://code.claude.com/docs/en/best-practices)
- [F] OpenSSF recommends pairing AI generation with linters, SAST and dependency checkers, SBOM generation (SPDX/CycloneDX) and integrity verification, and cites research that "Recursive Criticism and Improvement" prompts can reduce weakness density "up to an order of magnitude" — [OpenSSF guide, Aug 2025](https://github.com/ossf/wg-best-practices-os-developers/blob/main/docs/Security-Focused-Guide-for-AI-Code-Assistant-Instructions.md)
- [F] AI-DLC provides "source-bound review evidence" and a structured audit trail per intent; Symphony returns a "proof of work" bundle per task — [awslabs/aidlc-workflows README](https://github.com/awslabs/aidlc-workflows); [openai/symphony README](https://github.com/openai/symphony)

**Benchmarks as a caution about test-pass metrics**
- [F] SWE-Bench Pro (Scale AI) is "a challenging benchmark evaluating LLMs/Agents on long-horizon software engineering tasks"; the current V2 has 642 tasks across 11 repositories (V1: 731 tasks), with public and commercial (private) leaderboards — [scaleapi/SWE-bench_Pro-os README](https://github.com/scaleapi/SWE-bench_Pro-os)
- [R] In the original SWE-Bench Pro paper (Sep 2025) the best models resolved only about 23% of tasks while scoring above 70% on SWE-bench Verified, suggesting saturation/contamination in the older benchmark — [arXiv 2509.16941](https://arxiv.org/abs/2509.16941)
- [F] SWE-bench-style grading only checks fail-to-pass and pass-to-pass tests and says nothing about maintainability — [HumanLayer, "Why Software Factories Fail"](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/wsff.md)

### Inferences
- The most transferable control is separation of duties between agents: the implementing agent must not be able to read holdout scenarios, modify protected tests or golden files, or approve its own work. This should be enforced by repository permissions/sandbox mounts and hooks, not by prompt.
- For a lineage platform the strongest oracle is differential: the same SQL/job corpus run through the agent-built parser and compared with an independently derived truth (hand-labelled golden lineage, a reference parser, or warehouse-reported access/lineage metadata). This mirrors the GCC-as-oracle pattern and converts "is the lineage right?" into a parallelisable set of independent failing cases.
- LLM judges belong where outputs are natural language (PR impact comments, RCA narratives) and must be calibrated against a human-labelled sample; everything expressible as an invariant or exact expected output should use deterministic graders.
- Because agents reliably find "something" when asked to review, AI review findings need severity thresholds and a verification step, or the factory will churn.

### Gaps
- No comparative evidence was found on which gate catches the most defects (holdout scenarios vs reviewer agents vs property tests vs mutation testing vs SAST) in an agent-built codebase. Anthropic's Code Review numbers measure findings raised, not escaped defects.
- How StrongDM computes "satisfaction" (judge prompts, thresholds, sample sizes) was not found.
- Evidence on digital-twin fidelity drift (twins diverging from real third-party behaviour) was not found.
- Provenance tooling for AI-written code (commit trailers, signed attestations, SLSA-style provenance for agent runs) was not researched; no sources retrieved.
- A recalled-but-unverified item: OpenAI reportedly announced in early 2026 that it would stop reporting SWE-bench Verified because of flawed tests and contamination. Not confirmed here.

## 5. Evidence on outcomes and risks 2025-2026: productivity and quality data, failure modes, token/cost economics

### Takeaway
Measured evidence is mixed and mostly about AI-assisted (not fully agentic-factory) development: large surveys and telemetry show higher individual and delivery throughput alongside higher instability, larger PRs and review bottlenecks; controlled studies range from a 19% slowdown (METR, early-2025 tools, experienced maintainers) to an inconclusive roughly 18% speed-up in the 2026 follow-up; security and quality analyses consistently find elevated defect and vulnerability rates in AI-written code. Published factory-scale cost datapoints span from about $13 per developer-day (typical enterprise Claude Code usage) to StrongDM's $1,000 per engineer-day benchmark.

### Cited Findings

**DORA 2025**
- [S] The 2025 DORA "State of AI-assisted Software Development" report found 90% of surveyed professionals use AI at work (up 14 points on 2024); over 80% report productivity gains while 30% report little or no trust in AI-generated code; AI now improves delivery throughput (a reversal of 2024's negative effect) but "continues to increase delivery instability, suggesting that underlying systems have not yet evolved to safely manage AI-accelerated development" — [DORA 2025 report](https://dora.dev/dora-report-2025/); [Faros AI key takeaways](https://www.faros.ai/blog/key-takeaways-from-the-dora-report-2025); [IT Revolution](https://itrevolution.com/articles/ais-mirror-effect-how-the-2025-dora-report-reveals-your-organizations-true-capabilities/)
- [F] DORA's own summary: "AI's primary role is as an amplifier, magnifying an organization's existing strengths and weaknesses" and "The greatest returns on AI investment come not from the tools themselves, but from a strategic focus on the underlying organizational system" — [dora.dev source repo, 2025 report page](https://github.com/dora-team/dora.dev/tree/main/hugo/content/research/2025/dora-report)
- [R] The DORA AI Capabilities Model names seven capabilities that amplify AI's benefits: a clear and communicated AI stance; healthy data ecosystems; AI-accessible internal data; strong version control practices; working in small batches; a user-centric focus; quality internal platforms. Only the first was confirmed by this session's search results — [DORA AI Capabilities Model](https://dora.dev/ai/capabilities-model/report/)

**METR**
- [S]/[R] METR's randomised controlled trial (published 10 Jul 2025) of 16 experienced open-source developers on 246 real tasks in their own repositories found that allowing early-2025 AI tools made them 19% slower, although they had forecast a 24% speed-up and afterwards still believed they had been about 20% faster — [METR, 10 Jul 2025](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)
- [S] METR now marks that study as out of date. Its February 2026 update on late-2025 tools estimates about -18% task time for returning developers with a 95% interval of roughly -38% to +9% (i.e. the sign is not established), and says selection effects (developers declining to do tasks without AI) make the design unreliable, prompting a redesign. Secondary write-ups disagree on whether this is a "reversal" — [METR research index](https://metr.org/research/); [particula.tech analysis](https://particula.tech/blog/metr-reversed-19-percent-slower-ai-coding-study)
- [S] A METR survey of 349 technical workers (11 May 2026) found a median self-reported 1.4-2x change in the value of their work due to AI tools; self-report, not a controlled trial — [METR research index](https://metr.org/research/)
- [R] METR's time-horizon work (Mar 2025) found the length of tasks frontier agents can complete at 50% reliability had been doubling roughly every seven months — [METR, 19 Mar 2025](https://metr.org/blog/2025-03-19-measuring-ai-ability-to-complete-long-tasks/)

**Telemetry and code-quality analyses**
- [R] Faros AI, "The AI Productivity Paradox" (Jul 2025; telemetry from 10,000+ developers across about 1,255 teams): high-AI-adoption teams completed 21% more tasks and merged 98% more PRs, but PR review time rose 91%, PR size rose 154% and bugs per developer rose 9%, with no significant correlation to company-level delivery outcomes — [Faros AI](https://www.faros.ai/blog/ai-software-engineering)
- [F] A later Faros AI report, as summarised by Dex (who labels it correlation, not causation): review comments up about 25% and comment length up 22.7%; a 31.3% figure for PRs merged without review (the summary does not make clear whether this is a share or an increase); incidents per PR up 242.7%; monthly incidents up 57.9%; bugs per developer up 54%. Original report not opened — [HumanLayer, "Why Software Factories Fail"](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/wsff.md)
- [R] GitClear's 2025 analysis of about 211 million changed lines (2020-2024) found copy/pasted lines rising (to roughly 12% of changes), "moved"/refactored lines falling below 10%, and a sharp rise in duplicated code blocks, which it associates with AI-assistant adoption — [GitClear, AI Copilot Code Quality 2025](https://www.gitclear.com/ai_assistant_code_quality_2025_research)
- [R] CodeRabbit's "State of AI vs Human Code Generation" (Dec 2025; 470 open-source PRs) found AI-co-authored PRs contained about 1.7x as many issues as human-only PRs — [CodeRabbit](https://www.coderabbit.ai/blog/state-of-ai-vs-human-code-generation-report)
- [R] Stack Overflow Developer Survey 2025: 84% use or plan to use AI tools; more developers distrust the accuracy of AI output (46%) than trust it (33%); the top frustration (66%) is "AI solutions that are almost right, but not quite", and 45% say debugging AI-generated code is more time-consuming — [Stack Overflow Developer Survey 2025: AI](https://survey.stackoverflow.co/2025/ai)
- [F] A Stanford study of commits from about 100,000 developers (as relayed by HumanLayer from Yegor Denisov-Blanch's talk) found AI tools often create rework, and work well for greenfield projects but are often counterproductive in brownfield codebases and on complex tasks — [HumanLayer, "Advanced Context Engineering for Coding Agents"](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/ace-fca.md)
- [F] Dex's estimate: rework can reach 20% on a PR and most AI one-shot PRs trend closer to 50%; roughly an hour of upfront planning cut one review from about 6 hours to 20 minutes (illustration, not a study) — [HumanLayer, "Why Software Factories Fail"](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/wsff.md)

**Vendor-internal data**
- [F] Anthropic internal study (2 Dec 2025; 132 engineers surveyed, 53 interviews, about 200,000 Claude Code transcripts): staff self-report using Claude in about 60% of work with about a 50% productivity gain; more than half said they could "fully delegate" only 0-20% of their work; 27% of Claude-assisted work would not otherwise have been done; consecutive autonomous tool calls rose 116% (9.8 to 21.2) and human turns fell 33% between Feb and Aug 2025; a 67% increase in merged PRs per engineer per day is cited. Concerns: skill atrophy, a supervision paradox (supervising requires the skills that may erode), reduced collaboration/mentoring. Self-reported and Anthropic-specific — [Anthropic, How AI is transforming work at Anthropic](https://www.anthropic.com/research/how-ai-is-transforming-work-at-anthropic)
- [F] Anthropic usage study (18 Feb 2026): the 99.9th-percentile Claude Code turn "nearly doubled, from under 25 minutes to over 45 minutes" between Oct 2025 and Jan 2026 (median about 45 seconds); new users auto-approve in about 20% of sessions, experienced users in over 40%, yet experienced users interrupt more (about 9% of turns vs 5%); on the most complex tasks Claude "stops to ask for clarification more than twice as often as humans interrupt it"; internally, success on the hardest tasks doubled while interventions per session fell from 5.4 to 3.3 — [Anthropic, Measuring AI agent autonomy in practice](https://www.anthropic.com/research/measuring-agent-autonomy)
- [S] OpenAI: about 1M lines, about 1,500 PRs, 3.5 PRs per engineer per day over five months with 3-7 engineers (self-reported) — [OpenAI, "Harness engineering"](https://openai.com/index/harness-engineering/)
- [R] Cognition: Devin's PR merge rate rose from 34% to 67% year on year (Nov 2025; self-reported) — [Cognition blog](https://cognition.ai/blog/devin-annual-performance-review-2025)
- [R] A Google internal randomised controlled trial (2024) found about a 21% reduction in time on an enterprise-grade task for developers using AI features — [arXiv 2410.12944](https://arxiv.org/abs/2410.12944)

**Security of AI-written code**
- [R] Veracode's 2025 GenAI Code Security Report (Jul 2025; 100+ LLMs, 80 tasks) found about 45% of AI-generated code samples introduced an OWASP Top 10 class vulnerability, with Java worst and cross-site scripting defences failing in the large majority of cases; security performance had not improved with newer, larger models — [Veracode](https://www.veracode.com/resources/analyst-reports/2025-genai-code-security-report/)
- [F] OpenSSF (Aug 2025) cites: a BSI/ANSSI source ("About 40% of the programs had security vulnerabilities"), a Copilot study ("approximately 40% to be vulnerable"), a user study in which 36% of participants with an AI assistant wrote SQL-injection-vulnerable solutions versus 7% of controls, and a package-hallucination study in which "19.7% proposed packages did not exist" (enabling "slopsquatting") — [OpenSSF guide](https://github.com/ossf/wg-best-practices-os-developers/blob/main/docs/Security-Focused-Guide-for-AI-Code-Assistant-Instructions.md)

**Failure modes observed first-hand**
- [F] Compounding errors and regressions: fixes and new features often broke existing functionality in the C-compiler project until a CI pipeline was added late on — [Anthropic, Building a C compiler](https://www.anthropic.com/engineering/building-c-compiler)
- [F] Maintainability erosion: blanket try/catch, lazy type casts and local fixes that worsen the codebase; agent-built codebases start to struggle after roughly three to six months; a lights-off attempt ended with outages and partial rewrites — [HumanLayer, "Why Software Factories Fail"](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/wsff.md)
- [S] Entropy: OpenAI needed recurring cleanup ("garbage collection") agents and mechanical architecture enforcement — [OpenAI, "Harness engineering"](https://openai.com/index/harness-engineering/)
- [F] Premature completion and self-approval: agents declare victory early, mark features done without end-to-end tests, and a QA agent talked itself into approving the work — [Anthropic, Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents); [Anthropic, Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- [F] Spec non-compliance despite instructions: instructions in CLAUDE.md are followed "nearly every time" but "there's no guarantee" — [Claude Code docs: best practices](https://code.claude.com/docs/en/best-practices)
- [S] Spec drift and documentation sprawl — [Thoughtworks Radar](https://www.thoughtworks.com/radar/techniques/spec-driven-development)
- [F] Agent overreach: Anthropic's auto-mode classifier misses 17% of real "overeager" actions (n=52) and 5.7% of synthetic exfiltration attempts (n=1,000) at a 0.4% false-positive rate (n=10,000); it "is not a drop-in replacement for careful human review on high-stakes infrastructure" (25 Mar 2026) — [Anthropic, Claude Code auto mode](https://www.anthropic.com/engineering/claude-code-auto-mode)
- [F] Dex also cites a Financial Times report on production outages caused by coding-agent mistakes; the FT article was not opened — [HumanLayer, "Why Software Factories Fail"](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/wsff.md)

**Token and cost economics**
- [S] StrongDM benchmark: at least $1,000 of tokens per human engineer per day (about $20,000 per engineer-month at ~20 working days) — [Simon Willison, 7 Feb 2026](https://simonwillison.net/2026/Feb/7/software-factory/)
- [F] Typical enterprise Claude Code usage: "around $13 per developer per active day and $150-250 per developer per month, with costs remaining below $30 per active day for 90% of users"; agent teams use "approximately 7x more tokens than standard sessions when teammates run in plan mode" — [Claude Code docs: costs](https://code.claude.com/docs/en/costs)
- [F] C compiler: just under $20,000 for about 100,000 lines (about 2 billion input and 140 million output tokens, nearly 2,000 sessions, two weeks) — [Anthropic, Building a C compiler](https://www.anthropic.com/engineering/building-c-compiler)
- [F] Harness overhead: the same app brief cost $9 / 20 minutes solo versus $200 / 6 hours with the planner-generator-evaluator harness (Opus 4.5), "over 20x"; a later Opus 4.6 run cost $124.70 over 3 h 50 min, with QA rounds about $3-4 each — [Anthropic, Harness design for long-running apps](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- [F] Independent AI review: $15-25 and about 20 minutes per PR — [Claude blog: Code Review](https://claude.com/blog/code-review)
- [F] A three-person team doing intensive RPI-style work averaged about $12k per month on Opus (Aug 2025) — [HumanLayer, "Advanced Context Engineering"](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/ace-fca.md)
- [F] Multi-agent systems use about 15x the tokens of chat interactions — [Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)

### Inferences
- "Demonstrated" (with data): AI assistance raises output volume; instability, review load and defect/vulnerability density rise unless the surrounding system (tests, small batches, platforms) is strong; agents can sustain multi-hour to multi-week runs on well-specified, well-verified greenfield targets. "Advocated" (without independent data): removing human code review entirely; $1,000/engineer/day as a target; spec-as-source.
- Using the C-compiler figures, raw generation cost is on the order of $0.20 per surviving line of code, and independent AI review adds $15-25 per PR; for a platform of this size the dominant cost risk is not steady-state tokens but unbounded loops, oversized agent teams and re-work, which argues for per-work-package budgets.
- DORA's amplifier finding plus the seven capabilities imply the prerequisites for a factory are conventional: strong version control, small batches, a good internal platform/CI, and accessible internal data/context.

### Gaps
- METR's latest task-horizon figures for 2026 models were not retrieved (search budget exhausted). Recalled values exist but are not stated.
- GitClear, Veracode, CodeRabbit, Stack Overflow, Faros (2025) and Google figures are [R] and need re-verification; 2026 editions of these reports were not checked.
- Stack Overflow Developer Survey 2026 was not found/researched.
- No independent cost-per-merged-change data for a production software factory was found; the StrongDM benchmark is a prescription, not a measured unit cost.
- Microsoft internal studies were not researched. Public executive statements about the share of AI-generated code at Google and Microsoft (roughly 20-30%+ in 2025) are recalled but unsourced here.
- Recalled but unverified: early-2026 press reports that AI-agent actions contributed to AWS/Amazon outages and that Amazon tightened sign-off rules for AI-assisted changes. Not confirmed here; do not cite without checking.

## 6. Governance and regulated-industry considerations (financial services / card payments)

### Takeaway
Nothing retrieved shows a regulator or card scheme endorsing a no-human-review factory, and the secure-SDLC and change-control requirements that apply to card-payment environments are written around accountable human review, approval and segregation of duties; a factory in this context should therefore be designed as "agents execute, humans approve", using the factory's own artefacts (approved specs, plans, agent transcripts, test evidence, review findings) as the audit trail. Agent-specific risks (prompt injection, credential exposure, over-eager actions, hallucinated dependencies) need least-privilege sandboxes and deterministic policy gates rather than model judgement.

### Cited Findings

**Human accountability and approval points**
- [F] Anthropic's Code Review "won't approve PRs — that's still a human call" — [Claude blog: Code Review](https://claude.com/blog/code-review)
- [F] OpenSSF: "You remain responsible for the code"; AI output should be reviewed "as you would a human colleague's code" — [OpenSSF guide](https://github.com/ossf/wg-best-practices-os-developers/blob/main/docs/Security-Focused-Guide-for-AI-Code-Assistant-Instructions.md)
- [F] AI-DLC builds approval gates into the method: the human approves after each stage from Ideation onward; "Human approval gates and source-bound review evidence" — [awslabs/aidlc-workflows README](https://github.com/awslabs/aidlc-workflows); [docs/guide/00-introduction.md](https://github.com/awslabs/aidlc-workflows/blob/main/docs/guide/00-introduction.md)
- [F] Attractor models human gates as first-class pipeline nodes (`wait.human`) routed through an "Interviewer" interface with recording variants — [attractor-spec.md](https://github.com/strongdm/attractor/blob/main/attractor-spec.md)
- [F] Anthropic's oversight position (Feb 2026): mandating approval of every action "will create friction without necessarily producing safety benefits"; effective oversight rests on the ability to monitor and intervene; users in practice accept 93% of permission prompts, which is the "approval fatigue" problem — [Anthropic, Measuring AI agent autonomy](https://www.anthropic.com/research/measuring-agent-autonomy); [Anthropic, Claude Code auto mode](https://www.anthropic.com/engineering/claude-code-auto-mode)

**Audit trail and traceability**

- [F] Spec Kit and OpenSpec keep spec -> plan -> tasks (and archived change proposals) in the repository alongside code, giving a requirement-to-change chain in version control — [spec-kit spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md); [OpenSpec README](https://github.com/Fission-AI/OpenSpec)
- [F] BMAD notes a BRD is warranted when a regulator or contract requires a signed baseline — [BMAD docs](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/docs/plan/choose-a-planning-path.md)

**Change-management and secure-SDLC controls (recalled from the standards; verify against current text)**
- [R] PCI DSS v4.0.1 Requirement 6 (develop and maintain secure systems and software) includes: 6.2.1 bespoke and custom software is developed securely; 6.2.2 annual secure-development training for personnel working on bespoke software; 6.2.3 bespoke and custom software is reviewed prior to release to identify and correct potential coding vulnerabilities; 6.2.3.1 where manual code review is used, it is performed by someone other than the originating author who is knowledgeable in code-review techniques and secure coding, and is reviewed and approved by management before release; 6.2.4 engineering techniques to prevent common attack classes; 6.3.2 an inventory of bespoke/custom software and third-party components; 6.5.1 changes to production follow established procedures including documented reason, security-impact documentation, documented approval by authorised parties, testing and back-out procedures; 6.5.3 pre-production separated from production; 6.5.4 separation of roles/functions between production and pre-production; 6.5.5 live PANs not used in pre-production; 6.5.6 test data and accounts removed before production. - [R] NIST SP 800-218 (Secure Software Development Framework) and SP 800-218A (July 2024; SSDF community profile for generative AI and dual-use foundation models) provide the US reference practices for secure development, including code review/analysis and provenance — [NIST SP 800-218A](https://csrc.nist.gov/pubs/sp/800/218/a/final)

- [F] FINOS AI Governance Framework: an incubating FINOS project to give financial-services firms a threat-and-mitigation catalogue for onboarding, developing and running AI-based solutions "in a safe, trustworthy and compliant way"; its README does not (as fetched) enumerate agentic controls or regulatory mappings — [finos/ai-governance-framework README](https://github.com/finos/ai-governance-framework)

**Least-privilege sandboxes, secrets and supply chain**
- [F] Sandboxing needs both boundaries: filesystem isolation and network isolation; without network isolation a compromised agent could exfiltrate sensitive files such as SSH keys, and without filesystem isolation it could escape the sandbox and gain network access. Sandboxing reduced permission prompts by 84% internally. In Anthropic's cloud design "sensitive credentials (such as git credentials or signing keys) are never inside the sandbox"; a proxy validates each git operation (for example "only pushing to the configured branch") and attaches the real token outside the sandbox (20 Oct 2025) — [Anthropic, Claude Code sandboxing](https://www.anthropic.com/engineering/claude-code-sandboxing)
- [F] Rules that must hold belong in harness-enforced configuration: deny rules, OS-level sandbox (strict mode), managed settings and `PreToolUse` hooks; "A `WebFetch` deny rule for a domain does nothing about `curl` to that same domain, unless the sandbox is on"; `.claude/settings.json` hooks are repo-scoped and versioned — [Claude Code docs: best practices](https://code.claude.com/docs/en/best-practices)
- [F] Default auto-mode block categories are a useful policy taxonomy: destroy or exfiltrate (force-push over history, mass-delete cloud storage); degrade security posture (disable logging, install persistence); cross trust boundaries (run code from external repos, scan credential stores); bypass review or affect others (push directly to main, production deploys). Measured miss rate on real over-eager actions: 17% — [Anthropic, Claude Code auto mode](https://www.anthropic.com/engineering/claude-code-auto-mode)
- [F] Inter-agent trust: in Claude Code a teammate "can't approve a permission prompt or supply consent on your behalf", and relayed approval claims are treated as untrusted input — [Claude Code docs: agent teams](https://code.claude.com/docs/en/agent-teams)
- [F] Supply chain: instruct agents to use official package managers, pin versions, "Do not add dependencies that may be malicious or hallucinated", generate SBOMs (SPDX/CycloneDX), verify integrity; 19.7% of AI-proposed packages did not exist in one study ("slopsquatting") — [OpenSSF guide](https://github.com/ossf/wg-best-practices-os-developers/blob/main/docs/Security-Focused-Guide-for-AI-Code-Assistant-Instructions.md)
- [F] Skills and agent instructions are themselves supply-chain inputs: install only from trusted sources, audit bundled code and network-reaching instructions — [Anthropic, Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)
- [F] Symphony is explicitly "for testing in trusted environments" — [openai/symphony README](https://github.com/openai/symphony)
- [R] OWASP published a "Top 10 for Agentic Applications" (Dec 2025) covering, among others, agent goal hijack, tool misuse, identity and privilege abuse, agentic supply-chain vulnerabilities, unexpected code execution, memory/context poisoning, insecure inter-agent communication, cascading failures, human-agent trust exploitation and rogue agents — [OWASP GenAI Security Project](https://genai.owasp.org/)

**Licence / IP**
- [R] The US Copyright Office's January 2025 report (Copyright and AI, Part 2: Copyrightability) concluded that output generated by AI without sufficient human creative control is not copyrightable and that prompts alone generally do not suffice; the D.C. Circuit affirmed the human-authorship requirement in Thaler v. Perlmutter (Mar 2025). Implication: wholly agent-written code may have weak copyright protection for its owner — [US Copyright Office: Copyright and Artificial Intelligence](https://www.copyright.gov/ai/)

**Legal/critical commentary**
- [S] Stanford Law CodeX, "Built by Agents, Tested by Agents, Trusted by Whom?" (8 Feb 2026), addresses accountability for StrongDM-style factories; content not retrieved — [Stanford Law](https://law.stanford.edu/2026/02/08/built-by-agents-tested-by-agents-trusted-by-whom/)

### Inferences
- A lineage platform is unlikely to store or process cardholder data, but in a card-payments firm it will connect to in-scope systems (warehouses, pipelines, CI) and will itself be subject to corporate change management. The safe design assumption is that PCI DSS 6.2.3/6.2.3.1 and 6.5.1 style controls apply: a named, qualified human other than the author approves each production change. "The author" in an agent factory should be interpreted conservatively as both the implementing agent and the human who directed it; an AI reviewer can supplement but not replace the accountable human approver.
- The factory generates better evidence than a conventional SDLC if it is captured deliberately: each merged change can link (1) the approved spec/requirement IDs, (2) the plan, (3) agent run transcripts and model/harness versions, (4) test, scenario and scanner results, (5) AI review findings and their disposition, (6) the human approver's identity and timestamp. This is the "requirement -> code -> test" traceability auditors ask for, produced as a by-product.
- Segregation of duties should be applied between agent roles as well as people: implementer agents without access to holdout scenarios, protected tests, CI configuration, deployment credentials or production data; reviewer agents read-only; deployment by pipeline identity only after human approval.
- Agents should never see production secrets or real data: collectors should be developed against recorded/synthetic fixtures and simulators, with credentials injected outside the sandbox.
- Because classifier-based guardrails demonstrably miss a meaningful fraction of risky actions (17% in Anthropic's own data), deterministic controls (network egress allowlists, branch protection, scoped credentials, policy-as-code in CI) must carry the compliance weight.

- No guidance from PCI SSC, the card schemes, US/EU/UK financial regulators or audit firms specifically on AI-agent-written code or "no human review" development was retrieved (searches not run; budget exhausted). Not found, rather than known not to exist.
- SOX IT general controls (change management, access, segregation of duties) are relevant by general knowledge, but no source was retrieved; the mapping should be confirmed with internal audit.
- EU-specific obligations (EU AI Act, the EU Digital Operational Resilience Act for ICT risk and third-party providers) were not researched.

- Vendor contractual positions (IP indemnities, data-retention and training terms for the coding-agent provider) were not researched and need legal/procurement review.

## 7. Practical guidance for THIS kind of system (data-lineage platform: collectors, parsers, evidence bus, versioned graph, PR impact bot, incident RCA service on AWS, mostly Python)

### Takeaway
A back-end data platform is close to the ideal factory target because most of its behaviour can be expressed as deterministic input-to-output contracts (SQL text -> lineage edges, events -> graph state) checkable against golden datasets, oracles and invariants, with external systems replaced by emulators; the parts that are not deterministic (PR comments, RCA narratives) need scenario holdouts and calibrated LLM judges. Autonomy should be phased: begin with human review of every plan and PR, and relax review by change class only as measured pass rates and escaped-defect data justify it.

### Cited Findings

**What makes a system factory-friendly**
- [F] A near-perfect, fast, machine-readable verifier and an external oracle are the main enablers; tests should print minimal output, log detail to files, tag errors on one line for grep, and support deterministic sub-sampling so agents do not spend hours on full runs — [Anthropic, Building a C compiler](https://www.anthropic.com/engineering/building-c-compiler)
- [F] Agent work quality is highest where "Claude can verify its own work" (tests, expected outputs); "Give Claude a check to run" and put the command for it in CLAUDE.md — [Claude Code docs: best practices](https://code.claude.com/docs/en/best-practices); [Claude Code docs: costs](https://code.claude.com/docs/en/costs)
- [F] Library-first, CLI-accessible, text/JSON in and out, contract tests before implementation (Spec Kit constitution articles I, II, IX) — [spec-kit spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md)
- [S] Mechanical architecture enforcement (layer-direction structural tests, custom linters) and a short AGENTS.md pointing into versioned docs — [OpenAI, "Harness engineering"](https://openai.com/index/harness-engineering/)
- [F] Greenfield is where agents perform best; brownfield and complex tasks are where rework rises (Stanford study via HumanLayer) — [HumanLayer, "Advanced Context Engineering"](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/ace-fca.md)
- [R] Devin-style agents do best with clear upfront requirements and verifiable outcomes — [Cognition blog](https://cognition.ai/blog/devin-annual-performance-review-2025)

**Emulators and simulators for AWS and data infrastructure**
- [F] Moto is "a library that allows your tests to easily mock out AWS Services" using the `@mock_aws` decorator; state is in-memory per test in a virtual account — [getmoto/moto README](https://github.com/getmoto/moto)
- [F] LocalStack is "a cloud service emulator that runs in a single container on your laptop or in your CI environment" (Lambda, S3, DynamoDB, Kinesis, SQS, SNS and more). As of Nov 2026 the open-source repository is archived/read-only as development consolidates into a unified image; a free "Hobby" plan is described for non-commercial use and a paid Pro tier adds APIs, so commercial CI use needs a licensing check — [localstack/localstack README](https://github.com/localstack/localstack)
- [F] testcontainers-python "facilitates the use of Docker containers for functional and integration testing" (example: PostgreSQL) — [testcontainers/testcontainers-python README](https://github.com/testcontainers/testcontainers-python)
- [S] StrongDM's DTU shows the pattern for third-party SaaS APIs: build behavioural twins to run scenarios at volume without rate limits or side effects, at significant build cost — [rywalker.com research note](https://rywalker.com/research/strongdm-factory)

**Writing acceptance scenarios and requirements agents can verify**
- [S] EARS as used by Kiro: "WHEN [condition/event] THE SYSTEM SHALL [expected behavior]"; third-party guides add IF/THEN for error cases and WHILE for ongoing states — [Kiro docs: feature specs](https://kiro.dev/docs/specs/feature-specs/); [kirotutorial.com](https://kirotutorial.com/concepts/specs/)
- [R] EARS (Mavin et al., Rolls-Royce, 2009) defines five patterns: ubiquitous ("The <system> shall ..."), event-driven ("When <trigger>, the <system> shall ..."), state-driven ("While <state>, ..."), unwanted behaviour ("If <trigger>, then the <system> shall ...") and optional feature ("Where <feature>, ...") — [Alistair Mavin: EARS](https://alistairmavin.com/ears/)
- [F] OpenSpec stores requirements with scenarios as delta sections per change; Spec Kit requires testable requirements, measurable success criteria and no unresolved `[NEEDS CLARIFICATION]` markers — [OpenSpec README](https://github.com/Fission-AI/OpenSpec); [spec-kit spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md)
- [F] Sprint contracts: implementer and evaluator agree testable "done" behaviours before code is written — [Anthropic, Harness design for long-running apps](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- [F] Feature lists as machine-readable JSON with a `passes` flag per end-to-end behaviour — [Anthropic, Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- [F] Eval tasks must be unambiguous (two experts agree on pass/fail), have a reference solution, and be balanced (test when a behaviour should and should not occur) — [Anthropic, Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

**Phasing autonomy**
- [F] Harness components encode assumptions about model limits and should be removed or added as models change ("stress-test those assumptions") — [Anthropic, Harness design for long-running apps](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- [F] Observed adoption curve: users grant more auto-approval with experience (20% -> 40%+ of sessions) while interrupting more selectively — [Anthropic, Measuring AI agent autonomy](https://www.anthropic.com/research/measuring-agent-autonomy)
- [F] "If you're new to agent teams, start with tasks that have clear boundaries and don't require writing code" (review, research), before parallel implementation — [Claude Code docs: agent teams](https://code.claude.com/docs/en/agent-teams)
- [F] AI-DLC allows routine Construction checkpoints to pass without stopping while keeping stage approvals elsewhere, i.e. graded gating by phase — [aidlc-workflows docs/guide/00-introduction.md](https://github.com/awslabs/aidlc-workflows/blob/main/docs/guide/00-introduction.md)
- [F] Regression suites should sit near 100% and capability suites start low; an eval at 100% "provides no signal for improvement" — [Anthropic, Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- [S] Shapiro's levels give a vocabulary for the target operating level per component (for example Level 3 human-reviews-diffs vs Level 4 human-as-PM) — [Simon Willison, 28 Jan 2026](https://simonwillison.net/2026/Jan/28/the-five-levels/)

### Inferences
(These are the researcher's application of the cited findings to the lineage platform; none is a sourced claim about lineage systems.)
- **Parsers (SQL/dbt/Spark -> column-level lineage):** treat as pure functions with a versioned golden corpus (query text + dialect -> expected edge set as JSON). Add differential testing against an independent oracle (hand-labelled truth, a reference open-source parser, or warehouse-reported lineage/access history), property-based tests (parse/print round-trips; determinism) and metamorphic tests (renaming aliases, reordering CTEs or select-list columns, inlining views must not change source-to-target lineage). Keep a human-owned holdout slice of the corpus the implementing agent cannot read. Report precision/recall per dialect as the satisfaction metric.
- **Collectors:** define each as "source API/event -> normalised evidence envelope" with JSON Schema contracts; develop against recorded fixtures and small behavioural twins of each source API (DTU pattern), never live credentials; contract tests replay fixtures and assert schema validity, idempotency and completeness.
- **Evidence bus:** schema registry with compatibility checks as a CI gate; replayable event logs as the canonical test input; properties to assert include idempotent re-delivery, ordering tolerance and dead-letter behaviour. Use an in-container Kafka-compatible broker via Testcontainers (or moto/LocalStack for Kinesis/SQS) after a licence check.
- **Versioned lineage graph:** make "replay the log from empty -> identical graph at version N" a core invariant (determinism), plus as-of query correctness, no dangling edges, monotonic versions and bitemporal consistency. Run against a containerised graph DB; use DuckDB or SQLite fixtures only where dialect differences from the production warehouse are irrelevant to the behaviour under test.
- **PR impact bot:** scenario tests over fixture repositories with a twin of the Git host API; deterministic assertions on the computed impacted-asset set (precision/recall against labels) and a calibrated LLM-judge rubric only for comment clarity; a "must not comment" set to test restraint.
- **Incident RCA service:** seeded-incident scenarios (inject a known upstream break into a replayable log; expected root-cause asset and path known) kept as holdouts; score top-k root-cause accuracy and trajectory "satisfaction"; pass^k for consistency because outputs are non-deterministic.
- **Non-functional requirements** must be stated as measurable checks agents can run: for example p95 parse latency on the golden corpus, throughput on a replayed log of fixed size, cold-start budget, cost per million events in an emulator-plus-estimate model, zero critical/high findings from SAST/dependency/IaC scanners, IaC policy-as-code passes (encryption, least-privilege IAM, no public resources), coverage and mutation-score floors on parser cores.
- **Repo shape:** a short AGENTS.md/CLAUDE.md with the run-the-checks commands; `docs/` or `specs/` as system of record (constitution, component specs in EARS, contracts, ADRs, plans); `contracts/` for JSON Schemas; `golden/` visible corpora; holdout corpora and scenarios in a separate repository or protected path mounted only into the verification station; structural tests enforcing package boundaries (collectors must not import graph internals, etc.).
- **Autonomy phasing:** Phase 0 build the harness (CI, emulators, golden data, hooks, sandbox) largely human-led; Phase 1 Shapiro Level 3 (human approves every plan and reviews every PR) for the first slices of each component; Phase 2 Level 4 for change classes whose holdout pass rate, AI-review false-positive rate and escaped-defect rate meet agreed thresholds over a trailing window, with sampled human code review but still mandatory human merge approval; never Level 5 for security-sensitive code (IAM, credential handling, deployment pipelines) or contract/schema changes.

### Gaps
- No published case study of a data-lineage or data-platform product built with a software-factory method was found.
- No source was retrieved on the suitability or fidelity limits of DuckDB as a warehouse stand-in, on Kafka emulation choices, or on graph-database test containers; these recommendations rest on general engineering knowledge and need validation in a spike.
- LocalStack's current commercial licensing terms should be checked directly; the README statement is the only evidence retrieved.
- No evidence was found for specific numeric thresholds at which to relax human review; thresholds must be set locally and revisited.
- EARS pattern definitions are recalled; Kiro's exact documented syntax should be confirmed at kiro.dev.

## 8. Metrics for running a factory

### Takeaway
No single published metric set for software factories exists; practitioners combine classic delivery metrics (DORA throughput and instability, rework) with factory-specific ones: scenario pass rate / "satisfaction", PR merge (acceptance) rate, AI-review finding and false-positive rates, human interventions per run, and cost per unit of work. Volume metrics (lines, PR counts) are widely reported by vendors but are the weakest indicators, given the telemetry showing volume rising alongside incidents.

### Cited Findings
- [R]/[S] StrongDM "satisfaction": the fraction of observed trajectories across all scenarios that likely satisfy the user, replacing a boolean test pass — [Simon Willison, 7 Feb 2026](https://simonwillison.net/2026/Feb/7/software-factory/)
- [S] StrongDM spend-per-engineer benchmark ($1,000/day) used as a utilisation indicator — [Simon Willison, 7 Feb 2026](https://simonwillison.net/2026/Feb/7/software-factory/)
- [S] OpenAI reported throughput as PRs per engineer per day (3.5), total merged PRs (about 1,500) and lines of code (about 1M) — [OpenAI, "Harness engineering"](https://openai.com/index/harness-engineering/)
- [F] Anthropic's harness reports duration and dollar cost per build and per QA round (for example $124.70 / 3 h 50 min total; QA rounds $3-4) — [Anthropic, Harness design for long-running apps](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- [F] Eval metrics: pass@k and pass^k; regression-suite pass rate (target near 100%); capability-suite pass rate; grader agreement with human experts — [Anthropic, Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- [F] AI-review metrics: share of PRs with substantive findings (16% -> 54%), findings per PR by size, share of findings marked incorrect (<1%), minutes and dollars per review — [Claude blog: Code Review](https://claude.com/blog/code-review)
- [F] Autonomy/oversight metrics: autonomous turn duration percentiles, auto-approve share, interruption rate, human interventions per session (5.4 -> 3.3), clarification requests — [Anthropic, Measuring AI agent autonomy](https://www.anthropic.com/research/measuring-agent-autonomy)
- [F] Guardrail metrics: false-positive and false-negative rates of the action classifier (0.4% FPR; 17% FNR on real over-eager actions) — [Anthropic, Claude Code auto mode](https://www.anthropic.com/engineering/claude-code-auto-mode)
- [F] Quality/rework metrics used in critiques: rework share of a PR (20% up to about 50% for one-shot AI PRs), incidents per PR, monthly incidents, bugs per developer, review comment volume, share of PRs merged without review, human review hours per change (6 h -> 20 min illustration) — [HumanLayer, "Why Software Factories Fail"](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/wsff.md)
- [R] Faros AI's 2025 telemetry metrics: tasks completed, PRs merged, PR review time, PR size, bugs per developer — [Faros AI](https://www.faros.ai/blog/ai-software-engineering)
- [S] DORA 2025 tracks delivery throughput and delivery instability and finds AI raises both — [DORA 2025 report](https://dora.dev/dora-report-2025/)
- [R] DORA's current software-delivery metrics are change lead time, deployment frequency, failed-deployment recovery time, change fail rate and (added 2024) rework rate — [DORA: software delivery performance metrics](https://dora.dev/guides/dora-metrics-four-keys/)
- [R] Cognition tracks PR merge rate (34% -> 67%) as its headline agent-quality metric — [Cognition blog](https://cognition.ai/blog/devin-annual-performance-review-2025)
- [F] Cost baselines: $13 per developer per active day typical; per-user cost via OpenTelemetry; token usage scales roughly linearly with team size — [Claude Code docs: costs](https://code.claude.com/docs/en/costs)
- [F] Maintainability has no fast oracle or benchmark, so it is not directly measurable by automated metrics today — [HumanLayer, "Why Software Factories Fail"](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/wsff.md)
- [F] Parser-style quality can be tracked as conformance-suite pass rate against an external corpus (compiler example: about 99% on standard suites) — [Anthropic, Building a C compiler](https://www.anthropic.com/engineering/building-c-compiler)

### Inferences
A recommended scorecard for the lineage-platform factory (definitions are the researcher's synthesis; each has a sourced precedent above):
- **Flow:** lead time from approved spec to merged change (median, p90); work packages merged per week; queue time waiting for human approval (the review bottleneck).
- **Verification:** visible-scenario pass rate; holdout-scenario pass rate / satisfaction score (and the gap between the two as an overfitting indicator); golden-corpus precision/recall per dialect; regression-suite pass rate; pass^k consistency for non-deterministic services; mutation score on parser cores.
- **Quality after merge:** escaped defect rate (defects found after merge per merged change); change fail rate; rework rate (share of merged agent code modified or reverted within N days); incidents per release.
- **Review:** first-pass acceptance (PRs merged without human-requested changes); AI-review findings per PR and share dismissed as incorrect; human review minutes per change; share of changes with sampled deep review.
- **Autonomy and safety:** human interventions per work package; blocked-action count by policy category; guardrail escapes found in audit; sandbox/network-policy violations attempted.
- **Cost:** tokens and dollars per merged change and per work-package class; share of spend on abandoned or reworked runs; AI review cost per PR.
- **Spec health:** spec coverage (share of merged changes traceable to an approved requirement ID; share of requirements with at least one automated scenario); spec drift (requirements whose scenarios no longer exist or fail; code paths with no owning requirement); open `[NEEDS CLARIFICATION]` count; documentation volume per component (sprawl indicator).
- Do not use lines of code or raw PR counts as success measures; the Faros and GitClear data show they rise with defects.

### Gaps
- No published benchmark values for these metrics in a production software factory (other than the vendor datapoints above) were found; targets will have to be set from the project's own baseline.
- No standard definition of "spec coverage" or "satisfaction score" was found beyond StrongDM's one-sentence description.
- DORA 2025's exact metric definitions and the DORA/Faros 2026 editions were not verified.

Sources: AI-DLC; Kiro; Spec Kit `[NEEDS CLARIFICATION]`. **HUMAN GATE G1: spec, acceptance scenarios and non-functional targets approved by a named owner;** humans (or a separate agent under human control) author the holdout scenarios and golden holdout data that implementers never see. Sources: StrongDM; ImpossibleBench.

3. **Planning and decomposition.** Planner agent emits work packages sized to one session / one PR (thin vertical slices), each with objective, owned files, inputs, outputs, verification command and budget; independent packages flagged for parallel execution. Sources: Anthropic delegation guidance; agent-teams sizing; Spec Kit `[P]`; HumanLayer slices. Human spot-check of the plan in early phases.
4. **Implementation in isolation.** One agent per package in its own worktree/container with least-privilege credentials, no production data, no access to holdouts, protected tests or CI configuration; claims via tracker or lock; progress notes and commits as artefacts. Sources: Carlini; Symphony; Claude Code sandboxing.
5. **Automated verification (deterministic first).** Type-check, lint, unit/contract/property/metamorphic tests, golden-corpus diff, emulator-backed integration tests, structural/architecture tests, SAST, dependency and secret scanning, IaC policy-as-code, SBOM. 6. **Holdout and scenario evaluation.** A separate verification station (different identity and mounts) runs holdout scenarios and oracle comparisons and computes satisfaction, precision/recall and pass^k; LLM judges only for natural-language outputs, calibrated against human labels. Sources: StrongDM; Anthropic evaluator and evals guidance.
7. **Independent AI review.** Fresh-context, read-only reviewer agents compare the diff with the spec and look for correctness, security and maintainability issues; findings are verified and severity-ranked; only blocking severities loop back. Sources: Anthropic Code Review; best-practices reviewer subagent.
8. **Evidence bundle.** Assemble spec IDs, plan, transcripts, model and harness versions, test/scenario/scanner results, AI-review findings and dispositions, cost. Sources: Symphony proof of work; AI-DLC audit trail.

Sources: Anthropic "still a human call"; OpenSSF; PCI DSS 6.2.3.1 (recalled).
10. **Integration and release.** Protected-branch merge by pipeline identity; staged deploy with canary/rollback. **HUMAN GATE G4: production change approval** under the organisation's change-management process. Sources: PCI DSS 6.5.1 (recalled); auto-mode block list (production deploys, push to main).

Sources: OpenAI; Anthropic harness design; Osmani; Anthropic evals. **HUMAN GATE G5: periodic review of metrics to raise or lower autonomy per change class.**

### (c) Risks and mitigations

| Risk | Evidence | Mitigation |
|---|---|---|
| Test gaming / overfitting to visible tests | ImpossibleBench; Anthropic "unacceptable to remove or edit tests"; Willison's critique | Holdout scenarios and golden data outside implementer reach; protected test paths enforced by permissions and hooks; track visible-vs-holdout gap; external oracle |
| Weak or wrong verifier ("solves the wrong problem") | Carlini | Invest human effort in the oracle and golden corpus first; reference solutions; two-expert agreement on scenarios |
| Self-approval / lenient AI evaluation | Anthropic harness design | Separate evaluator and reviewer identities; calibrate judges on human-labelled samples; human merge approval |
| Spec drift and Markdown sprawl | Thoughtworks Radar; Böckeler; Tessl | Spec-anchored with delta specs per change; spec-coverage and drift metrics; change classes with light ceremony for small changes; prune docs |
| Agents ignoring instructions | Böckeler; Claude Code docs | Move "must" rules into linters, structural tests, hooks, deny rules and CI gates |
| Compounding errors, regressions, entropy | Carlini; OpenAI; HumanLayer (3-6 month decay) | Small batches; CI regression suite near 100%; cleanup agents; architecture tests; periodic human design review |
| Comprehension debt / inability to debug incidents | Osmani; HumanLayer lights-off failure; Anthropic supervision paradox | Humans review plans and sampled code; vertical slices; ownership per component; do not go lights-off |
| Review bottleneck | Faros (review time +91%, recalled); PostHog | Upstream plan review; AI first-pass review; evidence bundles; risk-tiered human review; small PRs |
| Security vulnerabilities in generated code | Veracode (recalled); OpenSSF statistics | SAST/DAST, dependency and secret scanning as blocking gates; secure-coding rules in instructions; security-focused reviewer; human review of security-sensitive code |
