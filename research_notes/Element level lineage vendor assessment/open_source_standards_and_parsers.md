## 1. What is the column-level lineage support matrix of each OpenLineage integration (Spark, Flink 1.x/2.x, Airflow, dbt, Trino, Hive, Kafka Connect / Kafka Streams, Dagster), and what does the spec itself provide?

### Takeaway
As of OpenLineage 1.55.0 (2026-10-29), column-level lineage is emitted by Spark (default on, richest, with transformation types), Hive 3, Trino, dbt (SQL-parser based, "tested with simple projections only") and Airflow SQL operators (SQL-parser based); **Flink emits no column-level lineage in either the 1.x or 2.x integration**, and Flink core (master, release 2.3.0) has no column-lineage type in its native lineage API. There is no OpenLineage Kafka Connect or Kafka Streams integration in the OpenLineage repo (Debezium emits its own dataset-level events), and the OpenLineage Dagster integration was removed in 1.39.0.

- Transformation `subtype` (verbatim list). ### Inferences
- Column lineage in OpenLineage has two quality tiers: **plan-based** (Spark, Hive, Trino: derived from the engine's resolved plan, so SELECT *, CTEs and expressions resolve against real schemas) and **SQL-text-based** (Airflow SQL operators, dbt, Spark JDBC relations: derived by the Rust SQL parser, no transformation types for JDBC, facet dropped when the parser fails). A build should treat the second tier as lower confidence.
- For streaming (Flink, Kafka Connect, Kafka Streams) open-source runtime collectors deliver **dataset-level lineage plus schemas only**. Field-level lineage across streaming hops must come from another mechanism (schema matching as DataHub does for Kafka Connect, Flink SQL static analysis, or code analysis).
- The `dataset` array (1-2-0) and the new `LineageFacet` (1-0-0) both aim to remove the cartesian-product blow-up; consumers that only read `fields` will miss indirect lineage emitted in `dataset` when `datasetLineageEnabled=true`.
- `LineageFacet` on `DatasetEvent`/`JobEvent` is the first spec-native way to publish curated or statically derived field lineage without inventing a run, which fits CI-emitted (pre-merge) lineage. It is only two months old (2026-09-01), so consumer support should be assumed absent until verified.

### Gaps
- Whether the Flink PR apache/flink#26089 (column lineage for Flink SQL) or a follow-up FLIP has been accepted for a future Flink release: not found (cwiki.apache.org and issues.apache.org unreachable). The class name `TableColumnLineageEdge` cited by Gravitino does not exist in Flink master as of 2026-11-26.
- Which Trino statement types and which Hive constructs lose column lineage (no documented unsupported-construct list found for either).
- No documented list of unsupported Spark constructs (UDFs, Python UDFs, `mapPartitions`, RDD code) beyond the LogicalRDD and JDBC notes above.

## 2. Which OpenLineage consumers accept static lineage (JobEvent / DatasetEvent) versus RunEvents only?

### Takeaway
Among consumers that could be checked against primary sources, only **Marquez** stores `JobEvent` and `DatasetEvent` (since 0.43.0, December 2023). **DataHub, OpenMetadata, Amazon DataZone / SageMaker Unified Studio, Google's Data Lineage API, Egeria and Gravitino** are documented or coded as RunEvent consumers; Apache Polaris parses all three event types but its default provider discards them. For Microsoft Purview, Atlan, Collibra, Snowflake and Databricks no accepted-event-type statement could be retrieved.

### Inferences
- DataHub's OpenLineage endpoint is RunEvent-only in practice: a `JobEvent` or `DatasetEvent` posted to it would be parsed as a `RunEvent` (the three-subtype model class is not used by the controller). This is an inference from code reading, not a documented statement.
- Google's API is RunEvent-only by construction (single RPC named `ProcessOpenLineageRunEvent`); its storage model can hold field-level links, but whether OpenLineage `columnLineage` facets are mapped into those field links is not stated in the proto.
- A design that emits static `JobEvent`s from CI can today land them natively only in Marquez (and, by parsing, Polaris once persistence exists). For DataHub, OpenMetadata, DataZone and Dataplex, a CI job would have to wrap static lineage in a synthetic `COMPLETE` RunEvent or call the platform's native lineage API.
- OpenMetadata's default filter (`COMPLETE` only) and its requirement that both inputs and outputs be present mean START-only or schema-only events are dropped silently (a `200` with zero edges).

## 3. DataHub: how good is the SQL parser, does OpenLineage ingestion keep column lineage, can edges carry custom properties, is there a timeline / lineage-as-of API, and what is Cloud-only?

### Takeaway
DataHub Core (Apache-2.0, v1.9.0; PyPI `acryl-datahub` 1.9.0.1) has column-level lineage, impact analysis, incidents and a self-hostable MCP server; its SQLGlot-based parser claims "97-99% accuracy" from unpublished internal benchmarks and documents clear gaps (no column lineage for `MERGE INTO`, multi-statement scripts unsupported, WHERE/JOIN columns not counted). Lineage edges carry a confidence score, a query reference and audit stamps, and dataset-level edges carry a free property map, but **there is no point-in-time lineage**: the docs state the time picker "will not show you historical lineages". Observability (assertions, anomaly detection), AI features, the hosted MCP server, lineage-based propagation and the Service Catalog are Cloud-only.

### Cited Findings

**Parser**

- "DataHub's SQL parser is built on top of sqlglot and adds a number of additional features to improve the accuracy of SQL parsing." "**In our benchmarks, the DataHub SQL parser generates lineage with 97-99% accuracy and outperforms other SQL parsers by a wide margin.**" The page links a Medium post ("Extracting Column Lineage from SQL Queries") for details; no dataset, query count or method is given on the docs page. — [sql_parsing.md](https://github.com/datahub-project/datahub/blob/master/docs/lineage/sql_parsing.md)
- Supported (verbatim): "Table-level lineage for `SELECT`, `CREATE`, `INSERT`, `UPDATE`, `DELETE`, and `MERGE` statements"; "Column-level lineage for `SELECT` (including `SELECT INTO`), `CREATE VIEW`, `CREATE TABLE AS SELECT` (CTAS), `INSERT`, and `UPDATE` statements"; subqueries; CTEs; "`UNION ALL` constructs"; "`SELECT *` and similar expressions will automatically be expanded with the table schemas registered in DataHub." — [sql_parsing.md](https://github.com/datahub-project/datahub/blob/master/docs/lineage/sql_parsing.md)
- Not supported (verbatim): "Scalar `UDFs` - We will generate lineage pointing at the columns that are inputs to the UDF, but will not be able to understand the UDF itself."; "Table-valued functions, including tabular `UDFs` ... They are skipped"; "`json_extract` and similar functions"; "`UNNEST` - We will do a best-effort job, but cannot reliably generate column-level lineage"; "Structs - We will do a best-effort attempt"; "Snowflake's multi-table inserts"; "**Multi-statement SQL / SQL scripting**". — [sql_parsing.md](https://github.com/datahub-project/datahub/blob/master/docs/lineage/sql_parsing.md)
- Limitations (verbatim): "`MERGE INTO` statements - We don't generate column-level lineage for these."; `INSERT INTO (col1_new, col2_new) SELECT ...` supported only when the column list is absent or matches the SELECT; "In cases where the table schema information in DataHub is outdated or otherwise incorrect, we may not be able to generate accurate column-level lineage."; "**We do not consider columns referenced in filtering or organizational clauses such as `WHERE`, `GROUP BY`, `ORDER BY`, `JOIN`, `HAVING`, or `PARTITION BY` to be part of lineage.**"; "We generally only analyze static table references" (e.g. Snowflake `identifier('...')` gives no lineage). — [sql_parsing.md](https://github.com/datahub-project/datahub/blob/master/docs/lineage/sql_parsing.md)
- SDK: `DataHubGraph.parse_sql_lineage()` returns "`sql_parsing_result.debug_info.confidence_score` ... a 0-1 value indicating the confidence of the parser." "The `SqlParsingAggregator` is particularly useful, as it can also resolve lineage across temp tables and table renames/swaps", but "these utilities are not officially part of the DataHub SDK". — [sql_parsing.md](https://github.com/datahub-project/datahub/blob/master/docs/lineage/sql_parsing.md)
- Where it is used: "Most of our integrations, including Snowflake, BigQuery, Redshift, dbt, Looker, PowerBI, Airflow, etc, use the SQL parser to generate column-level lineage and usage statistics"; for other systems "the SQL queries connector can generate column-level lineage and table/column usage statistics from the query log." — [sql_parsing.md](https://github.com/datahub-project/datahub/blob/master/docs/lineage/sql_parsing.md)

### Inferences
- DataHub's lineage store is **current-state with last-updated timestamps**, not bitemporal. "Lineage as of date X" or "diff lineage between two versions" would need an external snapshot/diff layer (for example, exporting `upstreamLineage` aspects on a schedule, or consuming MCL change-log events and versioning them yourself).
- Because WHERE/JOIN/GROUP BY columns are excluded from DataHub's parser output but OpenLineage Spark emits them as `INDIRECT`, the same pipeline can show different column edges depending on the ingestion path. The converter's `includeIndirect` flag exists to reconcile this.
- The edge model can hold `confidenceScore` and a `query` reference per column edge, which is enough for a "source and confidence" overlay; valid-from/valid-to would need to be put in the dataset-level `properties` map or handled outside DataHub.
- The only pre-merge impact tool found is dbt-specific, tested on dbt 1.4, SSPL-licensed and configured for Acryl-hosted instances. For non-dbt code changes the practical route is calling `searchAcrossLineage` (GraphQL) or the MCP `get_lineage` tool from a CI job.

## 4. OpenMetadata / Collate: which parser(s), stored-procedure lineage, incremental ingestion, lineage versioning, and what is Collate-only?

### Takeaway
OpenMetadata (2.1.1, released 2026-11-25) extracts column lineage with `collate-sqllineage` 2.1.9, a fork of sqllineage that now tries **SqlGlot first, then SqlFluff, then SqlParse**; SQLGlot support arrived in 1.11.4 (2025-12-24). Stored-procedure, temp-table, cross-database and incremental lineage are configuration switches on the Lineage agent, and since 2.x there is a native OpenLineage HTTP endpoint (RunEvent only). ## 7. Parsers and static analyzers: mechanisms, limits, and are there independent accuracy benchmarks (SQLGlot, sqllineage, sqlfluff, sqlparser-rs / DataFusion, Calcite, ZetaSQL / GoogleSQL, Gudu SQLFlow, dbt, SQLMesh, LLM-based)?

### Takeaway
No independent, reproducible head-to-head benchmark of column-lineage accuracy across SQLGlot, sqllineage, Gudu SQLFlow and commercial parsers could be retrieved in this session; the only accuracy number found is DataHub's self-reported "97-99%". The open tools split into schema-aware resolvers (SQLGlot, Calcite, GoogleSQL, dbt v2 / Fusion on DataFusion, SQLMesh) and syntax-only parsers (sqlparser-rs, sqlfluff, sqlparse) that need a semantic layer added, with documented weak spots around `SELECT *` without schemas, non-SELECT statements, procedural SQL and dynamic SQL.

### Cited Findings
- **SQLGlot** (MIT; v30.35.0 released 2026-11-24; 9.8k stars; 797 PyPI releases since 2021): "a no-dependency SQL parser, transpiler, optimizer, and engine" translating "between over 30 dialects"; the repo has 33 dialect modules (athena, bigquery, clickhouse, databricks, dax, doris, dremio, drill, druid, duckdb, dune, exasol, fabric, hive, materialize, mysql, oracle, postgres, presto, prql, redshift, risingwave, singlestore, snowflake, solr, spark, spark2, sqlite, starrocks, tableau, teradata, trino, tsql), split into Official, Community and (since v28.6.0) Plugin dialects. — [sqlglot README](https://github.com/tobymao/sqlglot/blob/main/README.md); [sqlglot dialects](https://github.com/tobymao/sqlglot/tree/main/sqlglot/dialects); [sqlglot CHANGELOG](https://github.com/tobymao/sqlglot/blob/main/CHANGELOG.md); [PyPI sqlglot](https://pypi.org/project/sqlglot/)
- SQLGlot lineage API: `lineage(column, sql, schema, sources=None, dialect=None, scope=None, trim_selects=True, copy=True, on_node=None, **kwargs)`; "If `column` is None, returns a dict mapping every top-level output column name to its lineage Node". It runs `qualify.qualify(..., validate_qualify_columns=False, identify=False)` with the supplied schema, then walks scopes. It raises "Cannot build lineage, sql must be SELECT" / "Cannot build lineage, sql must be a query" for non-query statements, and "Cannot fetch lineage for unnamed projection". Star handling: "if the select is a star add all scope sources as downstreams"; `sources` lets callers inline upstream queries ("A mapping of queries which will be used to continue building lineage"). The module handles set operations, subqueries, UDTFs and pivots explicitly. Star expansion (`expand_stars`) is part of `qualify_columns` and depends on schema. — [sqlglot lineage.py](https://github.com/tobymao/sqlglot/blob/main/sqlglot/lineage.py); [sqlglot qualify_columns.py](https://github.com/tobymao/sqlglot/blob/main/sqlglot/optimizer/qualify_columns.py)
- **sqllineage** (MIT; 1.5.9 uploaded 2026-09-05; five releases in the last 14 months; 1.7k stars): "leverages pluggable parser libraries (`sqlfluff` and `sqlparse`)"; default dialect `ansi`; column lineage via `-l column`. Stated limit: "**Column-level lineage will not be 100% accurate because that would require metadata information** ... If not provided, column-to-table resolution will be conducted in a best-effort way, meaning we only provide possible table candidates for situation like `select *` or `select col from tab1 join tab2`." Design: "SQLLineage is working on the abstraction layer of unresolved AST, right after parsing phase is done ... ### Inferences
- SQLGlot has become the common substrate: DataHub, OpenMetadata (first-choice analyzer since 1.11.4), SQLMesh and the dbt add-ons all sit on it. Parser diversity across "different" open tools is therefore lower than it looks, and their failure classes are correlated.
- SQLGlot's `lineage()` only answers for query (SELECT) scopes; lineage for `INSERT`/`MERGE`/`UPDATE`/CTAS, multi-statement scripts, temp-table chains and stored procedures is the wrapper's job (DataHub's `SqlParsingAggregator`, OpenMetadata's stored-procedure handling). That wrapper layer is where the tools actually differ.
- Engine-plan approaches (Calcite column origins, GoogleSQL resolved AST, Spark logical plan, dbt v2 on a typed binder) avoid name-resolution guesses but cover one engine family each. A multi-engine baseline needs both: plan-based where an engine exposes it, SQLGlot-style elsewhere.
- dbt's licensing picture changed during 2026: the v2 Rust engine source is Apache-2.0 in the main dbt repo, while the binary distribution and editor features (including column-level lineage in the VS Code extension) are under a product license. Whether column-lineage computation can be used from an Apache-2.0-only build is not established.

## 8. Application-code lineage: what open-source approaches exist for field-level data flow from service code, and does any OSS emit OpenLineage from them?

### Takeaway
Open-source building blocks exist for the two halves of the problem — program-analysis engines that can trace data flow in code (Joern, CodeQL queries, Semgrep CE, tree-sitter) and schema-contract checkers (`buf breaking`, schema registries) — but **no open-source project was found that turns their output into field-level lineage or OpenLineage events**. The catalog vendors that claim code-derived lineage (Foundational; DataHub Cloud's Service Catalog) are commercial.

### Cited Findings
- **Joern** (Apache-2.0; tag `v4.0.693` dated 2026-11-26, near-daily releases): "a platform for analyzing source code, bytecode, and binary executables. It generates code property graphs (CPGs), a graph representation of code for cross-language code analysis ... mined using search queries formulated in a Scala-based domain-specific query language", built "for vulnerability discovery and research in static program analysis". — [joern README](https://github.com/joernio/joern/blob/master/README.md)
- **CodeQL**: "The code in this repository [standard libraries and queries] is licensed under the MIT License", but "The CodeQL CLI (including the CodeQL engine) is hosted in a different repository and is licensed separately. If you'd like to use the CodeQL CLI to analyze closed-source code, you will need a separate commercial license". — [codeql README](https://github.com/github/codeql/blob/main/README.md)
- **Semgrep Community Edition** (LGPL-2.1; `v1.187.0` dated 2026-11-24): "Semgrep Community Edition will miss many true positives as it can only analyze code within the boundaries of a single function or file"; cross-file, cross-function data-flow is in the commercial platform ("Improved core analysis capabilities (cross-file, cross-function, data-flow reachability)"). — [semgrep README](https://github.com/semgrep/semgrep/blob/develop/README.md)
- **Buf** (Apache-2.0; `v1.75.0` dated 2026-10-22): "`buf breaking` compares the current schema against a previous version and flags source, JSON, or wire-format incompatibilities"; "Run `buf breaking` against Git, a BSR module, a tarball, a zip file, or a Buf image before merge" (`buf breaking --against '.git#branch=main'`). — [buf README](https://github.com/bufbuild/buf/blob/main/README.md)
- **Debezium** (CDC from service databases) emits OpenLineage with table and topic schemas and reflects DDL changes "dynamically in the dataset schema" (see section 1). — [Debezium openlineage.adoc](https://github.com/debezium/debezium/blob/main/documentation/modules/ROOT/pages/integrations/openlineage.adoc)
- **Commercial, for contrast**: Foundational "ingests runtime OpenLineage events from pipelines that already emit them, combining that metadata with the column-level lineage it derives from static analysis of pipeline code" (also listed as an OpenLineage producer). DataHub's Service Catalog ("Introduced in DataHub Cloud v2.1", marked `saasOnly`) models "Repositories build services, services expose APIs, applications call those APIs, and APIs produce and consume datasets ... so you can trace an outage, a schema change, or a data dependency from source code all the way to a dashboard"; Cloud v2.4.0 adds "an API's input and output schema can point at existing Dataset entities, which then appear in lineage". — [OpenLineage consumers.tsx](https://github.com/OpenLineage/OpenLineage/blob/main/website/static/ecosystem/consumers.tsx); [DataHub service-catalog.md](https://github.com/datahub-project/datahub/blob/master/docs/features/feature-guides/service-catalog.md); [DataHub v_2_4_0.md](https://github.com/datahub-project/datahub/blob/master/docs/managed-datahub/release-notes/v_2_4_0.md)
- OpenLineage producers list (complete, 2026-11-26): Airflow, Anyscale, Dagster, dbt, Egeria, Feast, Flink, Google Cloud, Great Expectations, Hamilton, IBM, Keboola, Snowflake, Spark, Trino, SnapLogic, Matillion, Provero, oleander, Debezium, Foundational. No code-analysis (taint / data-flow) tool is among them. — [OpenLineage producers.tsx](https://github.com/OpenLineage/OpenLineage/blob/main/website/static/ecosystem/producers.tsx)
- The spec provides a landing place for code-derived lineage: `JobEvent` "typically by a compiler, CI pipeline, or metadata extraction tool", `SourceCodeLocationJobFacet`, `SourceCodeJobFacet`, and the new `LineageJobFacet` / `LineageDatasetFacet` for declared field relationships. — [object-model.md](https://github.com/OpenLineage/OpenLineage/blob/main/website/docs/spec/object-model.md); [spec/facets directory](https://github.com/OpenLineage/OpenLineage/tree/main/spec/facets)

### Inferences
- Field-level lineage for application code is a build-it-yourself area: use Joern or CodeQL data-flow queries (sources = deserialized request/DB fields, sinks = serialized responses, producer calls, ORM writes) and emit the result as OpenLineage `JobEvent`s with `LineageFacet` (or as a platform's native API calls). No reusable open adapter was found.
- Semgrep CE is unsuitable for cross-service field flow because its open engine is intra-file; Joern (fully Apache-2.0) and CodeQL (engine licence restricts closed-source use without a commercial licence) are the realistic engines.
- Contract checks (`buf breaking`, schema-registry compatibility) cover the "breaking change at the interface" half of impact analysis cheaply; they do not tell you which downstream columns consume a field, which still requires lineage.
- CDC (Debezium) gives table-to-topic lineage with schemas for service databases at runtime, which is the practical seam between application code and the analytical estate.

### Gaps
- Open-source tools that emit OpenLineage from CodeQL, Semgrep, Joern or tree-sitter analyses: not found (none in the OpenLineage ecosystem files; no web search possible).
- Schema-registry compatibility checks (Confluent Schema Registry, Apicurio), AsyncAPI and OpenAPI diff tools (for example oasdiff, asyncapi diff): not verified in this session (hosts unreachable; repos not read).
- tree-sitter-based lineage extractors and any academic work on field-level lineage from service code: not found.
- Published precision/recall for taint-analysis-based data lineage in application code: not found.

### Inferences
- No single open-source tool covers all four objectives at element level. The closest composition is: OpenLineage collectors (O1/O2 runtime), a SQLGlot-based static layer for what collectors miss (O1), an event-sourced versioned store modelled on Marquez (O2), SQLMesh/Recce-style or custom `JobEvent`-based diffing in CI (O3), and a catalog (DataHub or OpenMetadata) for incidents and impact views (O4).
- The weakest open areas, in order: streaming field-level lineage (Flink, Kafka), application-code lineage, lineage time travel/diff in the mainstream catalogs, and independent accuracy measurement.
